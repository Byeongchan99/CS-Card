이미 있는 요약 노트를 **같이 읽으며 보강하는 트랙**이다. `/노트정리`가 노트를 처음 쓰거나
통째로 정리하는 것이라면, 이 커맨드는 항목 하나씩 짚어 개념을 설명하고 그 설명을 노트에
반영한다. 사용자가 공부하는 게 목적이므로 설명이 먼저고 노트 수정은 그 결과다.

입력: $ARGUMENTS

## 1. 대상 확정

대분류에서 `summary-notes/<분야>.md`를 연다(파일명 규칙: `C#`→`C샵`,
`게임 수학·물리`→`게임-수학-물리`, `디자인 패턴`→`디자인-패턴`). 시작 항목을 지정하지
않았으면 노트 맨 앞부터. 먼저 항목 목록을 뽑아 어디서 시작할지 보여준다.

## 2. 한 항목씩 루프

**설명 → 사용자 반응·질문 → 리라이트 → 커밋·푸시 → 배포 확인**을 한 항목마다 돈다.
한 번에 한 항목만 다루고, 사용자가 다음으로 가자고 하기 전에는 넘어가지 않는다.
질문이 오면 리라이트를 미루고 그 질문부터 답한다 — 이해가 먼저다.

### 설명 (채팅)

- 채팅만 읽고 한 번에 파악되도록 **자기완결**로 쓴다. "노트를 보면" 식으로 노트를 참조하지 않는다
- 코드 블록을 반드시 넣는다. 결과가 있으면 주석으로 출력을 적는다
- 흐름·구조·대비가 있으면 그림을 그린다(채팅에서는 visualize 위젯)
- **문법·API 사용법이 아니라 개념·원리** — 무엇인지, 왜 그렇게 동작하는지, 트레이드오프가 무엇인지
- 오버 비유 금지. 깊이를 낮추지 말고 담백하게 쓴다

### 리라이트 (노트)

- 노트 형식은 CLAUDE.md의 요약 노트 규칙을 따른다
- 짧은 문단 + "키워드 — 설명" 불릿. 볼드 리드인과 `###` 소제목은 쓰지 않는다
- A vs B는 표로. 흐름·구조가 핵심인 항목에만 인라인 SVG나 Mermaid를 넣는다
- **"면접 각도" 같은 Q&A 섹션은 넣지 않는다** — 면접 문답 페이지가 담당한다
- 다른 노트에 이미 있는 주제는 재설명하지 말고 그쪽으로 넘긴다(겹치면 통합이 원칙)

### 검증 후 커밋

헤딩 수, 코드펜스 짝수, `<svg>`와 `</svg>` 짝, 한 줄에 물결 2개 없음(취소선으로 깨진다),
콜아웃 없음을 확인한 뒤 커밋·푸시한다. 빌드는 **배포된 자산을 직접 확인**한다 —
Actions API 폴링은 새 실행이 시작되기 전이면 직전 실행을 잡아 "성공"으로 오판하고,
반복하면 레이트 리밋(403)에 걸린다. 압축된 CSS는 셀렉터가 이스케이프되므로
(`[data-slug^=summary-notes\/]`) 검색 문자열을 잘게 쪼개 찾는다.

## 3. 사실관계 주의

- 다른 런타임·언어의 예시를 섞지 않는다. 범위가 다르면 "이건 X 기준"이라고 명시한다
  (예: 세대별 GC는 .NET CoreCLR 기준이고, 유니티 기본 런타임은 비세대 Boehm이라 다르다)
- OS·플랫폼마다 갈리는 동작도 같은 기준으로 구분한다(예: 열린 파일 잠금은 주로 Windows 동작)
- 개념을 잘못 아는 것보다 **적용 범위를 헷갈리는 쪽이 더 잘 안 걸러진다.** 설명 자체는
  정확해 보이기 때문이다. 다른 맥락의 예시를 끌어올 때 한 번 더 확인한다

## 4. 한 분야를 마치면

1. **순서·카테고리 검토** — 항목이 주제 묶음에 맞게 배치됐는지 본다. 순서를 바꿨으면
   "앞·뒤·다음 항목" 상호 참조를 전부 새 순서에 대조한다(방향이 뒤집히면 고친다)
2. **2단 구조** — 평평한 목록으로 훑기 어려우면 `##` 카테고리 + `###` 항목으로 바꾼다
3. **★ 표시** — 면접에서 개념·원리를 깊게 파고드는 항목에 붙인다. 머리말에 "나머지도
   ★ 항목의 꼬리질문에서 나오므로 건너뛰지 않는다"는 안내를 같이 둔다
4. **면접 문답 갱신** — `/면접문답 <분야>`로 그 분야 탭을 보강한 내용에 맞게 갱신한다

각 단계는 바로 적용하지 말고 무엇이 어긋났는지 먼저 보고한 뒤 사용자 판단을 받는다.
