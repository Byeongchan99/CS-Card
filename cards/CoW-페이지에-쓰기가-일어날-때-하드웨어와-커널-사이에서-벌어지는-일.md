## 질문
fork 시 커널은 공유 페이지의 PTE에 어떤 표시를 해두는가? 이후 부모든 자식이든 그 페이지에 쓰기를 시도하면 하드웨어와 커널 사이에서 순서대로 무슨 일이 벌어지는가? 그리고 이 메커니즘 때문에 CoW가 오히려 손해를 보는 상황은 언제인가?

## 핵심 답변
fork 시 커널은 공유 페이지들의 PTE를 양쪽 다 읽기 전용(write-protected)으로 바꿔둔다. 이후 어느 쪽이 쓰기를 시도하면 MMU가 쓰기 권한 없음을 감지해 protection fault가 나고, 커널 핸들러가 이를 CoW 폴트로 판별한 뒤 새 물리 페이지를 할당·복사하고 PTE를 교체하며 쓰기 권한을 복원한 다음 원래 명령을 재실행한다. 손해 보는 상황은 fork 직후 자식이 방대한 페이지에 전부 쓰기를 하는 경우로, 어차피 다 복사될 페이지를 폴트라는 비싼 우회로로 하나씩 복사하게 되어 eager copy보다 느려진다.

## 정리

### 내부 동작
핵심 표시는 write-protect다. fork 시 원래 쓰기 가능하던 공유 페이지를 일부러 양쪽 다 읽기 전용으로 막아둔다. 이 조작이 쓰기 시 폴트를 유발하는 트리거다.

```
1. CPU가 write-protected 페이지에 store 실행
2. MMU가 PTE의 쓰기 권한 없음 감지 → protection fault (트랩)
3. 커널 page fault 핸들러 진입
4. "진짜 접근 위반 vs CoW 페이지" 판별
   → VMA는 쓰기 가능인데 PTE만 읽기 전용이면 CoW로 판단
5. 새 물리 페이지 할당 + 기존 내용 복사
6. 해당 프로세스의 PTE를 새 페이지로 교체 + 쓰기 권한 복원
7. 트랩 걸렸던 store 재실행 → 이번엔 성공
```

### 왜 그런가
4번의 판별이 설계의 관건이다. 커널은 폴트가 났을 때 그것이 프로그램 버그(권한 없는 접근)인지 자기가 일부러 걸어둔 CoW 트랩인지 구분해야 한다. 그 판단 기준이 VMA와 PTE의 불일치다. 가상 메모리 영역 메타데이터상 쓰기 가능인데 실제 PTE만 읽기 전용이면 CoW 신호다.

### 트레이드오프
CoW는 "쓰기가 드물다"는 가정에 기댄다. 읽기 위주면 물리 페이지를 계속 공유해 큰 이득이다. 반대로 fork 직후 자식이 대부분의 페이지를 갈아엎으면, 전부 복사될 페이지를 "폴트 → 트랩 → 핸들러 → 복사"라는 우회로로 처리해 폴트 오버헤드만큼 eager copy보다 느려진다. 이 극단이 fork→exec 패턴이다(→ [[fork exec 패턴에서 CoW 폴트 비용을 회피하는 방법]]).

### 흔한 오해/함정
- "표시를 해둔다"를 얼버무리기 쉽다. 구체적으로는 PTE를 write-protect(읽기 전용)로 바꾸는 것이다.
- "페이지 폴트가 나서 복사한다"까지만 말하면 부족하다. MMU 트랩 → 핸들러의 CoW 판별 → 페이지 할당·복사·PTE 교체·권한 복원 → 명령 재실행의 순서를 짚어야 한다.
