## 질문
(추론) Player가 List<IObserver>를 직접 관리하는 대신 C# event(멀티캐스트 델리게이트)를 노출하면, 순회 중 수정 예외·즉시 반영 안 됨·죽은 옵저버 세 문제는 각각 어떻게 되는가?

## 핵심 답변
순회 중 수정 예외는 자동으로 사라지고, 즉시 반영 안 됨은 그대로 남으며, 죽은 옵저버 문제는 형태를 바꿔 오히려 더 숨는다. event는 구독 관리 메커니즘은 언어가 주지만 구독자의 수명과 전파 정책까지 관리해주지는 않는다.

## 정리
### 왜 그런가
순회 중 수정 예외 → 해결: 멀티캐스트 델리게이트는 -= 할 때 기존 invocation list를 제자리 수정하지 않고 새 델리게이트 인스턴스로 통째 교체한다. Invoke가 돌던 것은 교체 전 옛 리스트라 List<T>의 버전 충돌이 원천적으로 없다.

즉시 반영 안 됨 → 그대로: 위 "새 인스턴스로 교체" 성질이 이 결과를 데려온다. Invoke 도중 -=한 구독자는 이번 발행에서 여전히 콜백을 받는다. 직접 구현의 복사 후 순회와 같은 성질이다.

죽은 옵저버 → 더 악질적으로: += 구독은 Subject의 델리게이트가 옵저버(인스턴스 메서드의 this)를 강한 참조로 붙든다. -=를 깜빡하면 그 옵저버를 아무도 안 쓰는데도 GC가 수거하지 못한다(lapsed listener 누수). 게다가 구독 목록이 언어 뒤로 감춰져 "누가 붙어 있나"를 열어볼 수 없어 List 수동 관리보다 다루기 어렵다.

### 실무(게임 개발)에서 생기는 문제와 해결
유니티에서는 파괴된 오브젝트의 메서드가 이벤트에 남아 fake null 대상을 호출하다 사고가 나는 계열이 죽은 옵저버 문제에 해당한다. 그래서 유니티에서 event를 쓸 때는 OnDisable/OnDestroy에서의 구독 해제가 사실상 의무가 된다.

### 흔한 오해/함정
"event를 쓰면 옵저버 문제가 다 해결된다"는 오해. 순회 안전은 무료로 주지만 즉시 반영은 그대로 물려주고, 생명주기 관리는 감춰진 형태로 더 까다롭게 만든다.
