## 질문
Graphics.DrawMesh 같은 렌더링 API를 호출하면 그 명령이 실제 GPU에 도달하기까지 CPU 쪽에서 여러 계층을 거친다. 그 계층은 무엇이며, 드로우 콜 비용의 몸통이 왜 단순 함수 호출 오버헤드가 아니라 이 계층 — 특히 드라이버 — 을 넘는 데 있는가?

## 핵심 답변
렌더링 명령은 매니지드 게임 코드 → 엔진 네이티브 → 그래픽스 API → 그래픽스 드라이버 → GPU 순으로 여러 경계를 넘는다. 비용의 핵심은 드라이버에 있는데, 드라이버가 두 가지 비싼 일을 하기 때문이다. 하나는 애플리케이션이 준 상태·리소스 조합이 유효한지 매 호출 검증하는 것이고, 다른 하나는 API의 추상적 상태 설명을 그 머신에 꽂힌 특정 GPU의 독자 명령어 집합(ISA)으로 번역하는 것이다. 이 검증과 번역이 빈 for 루프 같은 순수 CPU 작업과 드로우 콜을 구분 짓는 지점이다.

## 정리

### 내부 동작
```
게임 코드 (C# / 매니지드)
      ↓  매니지드→네이티브 경계
엔진 네이티브 렌더링 계층 (Unity C++)
      ↓
그래픽스 API (D3D11, OpenGL, Vulkan, Metal ...)
      ↓
그래픽스 드라이버 (GPU 벤더 제공)  ← 검증 + 하드웨어 번역이 여기서 발생
      ↓
GPU 하드웨어
```
매니지드→네이티브 경계도 공짜는 아니지만, 전통적 API(D3D11, OpenGL)에서 드로우 콜 CPU 비용의 몸통은 드라이버의 암묵적 검증과 ISA 번역이다.

### 왜 그런가
GPU마다 독자적인 명령어 집합을 쓰기 때문에, API가 정의한 표준적·추상적 상태를 실제 하드웨어가 실행할 수 있는 명령으로 옮기는 번역 단계가 반드시 필요하다. 전통적 API의 드라이버는 이 번역과 안전성 검증을 런타임에, 호출마다 암묵적으로 수행하도록 설계되어 있었다.

### 실무(게임 개발)에서 생기는 문제와 해결
게임 개발자는 보통 이 계층을 직접 만지지 않지만, 이 구조를 알아야 왜 드로우 콜과 상태 변경이 비싼지, 왜 엔진이 배칭·정렬로 그것을 줄이는지를 이해할 수 있다.
