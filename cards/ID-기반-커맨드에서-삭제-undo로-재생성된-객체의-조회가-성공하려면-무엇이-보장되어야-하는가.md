## 질문
ID 기반 커맨드로 undo 스택을 구현한 에디터 툴에서 오브젝트 A를 이동(targetId = 7)한 뒤 삭제하고, undo를 두 번 눌렀다. 첫 undo가 삭제를 취소해 A를 되살린 뒤 두 번째 undo가 이동을 취소해야 한다. ID 7 조회가 성공하려면 무엇이 보장되어야 하며, 삭제 커맨드의 undo는 무엇을 해야 하는가?

## 핵심 답변
되살아난 오브젝트가 삭제 전과 동일한 식별자를 가져야 한다(ID 안정성). 그러려면 삭제 커맨드가 삭제 시점에 대상을 재구성할 만큼의 상태를 스냅샷으로 남기고, undo에서 복원한 객체에 원래 ID를 다시 부여해 레지스트리에 그 매핑으로 재등록해야 한다. 여기에 더해 삭제 시 그 ID를 재사용 풀에 반납하지 않아야 한다. 반납하면 undo 전에 만들어진 새 오브젝트가 7을 선점해 복원 시 충돌한다.

## 정리

### 왜 그런가
ID 방식에서 커맨드와 대상을 잇는 유일한 끈은 식별자다. 참조 방식이라면 되살린 것은 완전히 새로운 객체이므로 옛 참조로 절대 닿지 못하고, ID 방식이어도 새 ID가 발급되면 같은 이유로 끈이 끊어진다.

### 내부 동작
삭제 커맨드는 역연산(= 생성)만으로는 undo할 수 없다. 무엇을 생성할지는 스냅샷 없이 알 수 없기 때문이다. 실행 전 상태를 저장한다는 원칙이 삭제에도 그대로 적용된다.

### 트레이드오프
ID를 예약 상태로 묶어 두면 안전하지만 히스토리가 살아 있는 동안 번호가 회수되지 않는다. GUID처럼 재사용하지 않는 식별자를 쓰면 이 문제 자체가 사라지는 대신 식별자 크기와 조회 비용이 커진다.

### 흔한 오해/함정
참조를 ID로 바꾸는 것이 수명 관리를 없애 주는 것은 아니다. 객체 수명 관리가 ID 수명 관리로 옮겨 간 것이므로, 발급·예약·회수 시점을 히스토리와 맞춰 설계해야 한다.
