## 질문
지역 변수를 포획한 람다가 있다. 그 변수를 선언한 메서드가 리턴하면 스택 프레임은
사라지는데, 나중에 실행되는 람다는 어떻게 그 변수를 계속 읽고 쓸 수 있는가?
변수가 실제로 어디에 저장되고, 컴파일러가 무슨 구조를 만들어 이걸 성립시키는지
설명하라.

## 핵심 답변
포획된 지역 변수는 스택이 아니라 힙에 산다. 컴파일러가 소스에 없는 숨은 클래스
(관례상 `<>c__DisplayClass...`)를 만들고, 포획된 지역 변수를 그 클래스의 필드로,
람다 본문을 그 클래스의 메서드로 옮긴다. 원래의 지역 변수 접근은 전부 이 힙 객체의
필드 접근으로 치환된다. 람다는 델리게이트가 되어 이 힙 객체를 참조하므로, 메서드가
리턴해 스택 프레임이 사라져도 참조가 살아있는 한 객체와 변수가 함께 살아남는다.
변수를 복사하는 게 아니라 변수 자체가 힙으로 승격되는 것이다.

## 정리

### 왜 그런가
스택 프레임은 함수가 리턴하면 사라지므로, 나중에 실행될 람다가 붙잡아야 하는
변수를 스택에 둘 수 없다. 힙에 있는 객체는 살아있는 참조가 있는 한 GC가 수거하지
않는다. 그래서 변수를 힙 객체의 필드로 만들고, 람다(델리게이트)가 그 객체를
참조하게 하면 스택 프레임의 소멸과 무관하게 변수가 살아남는다.

### 내부 동작
컴파일러가 다음과 같이 재작성한 것과 개념적으로 같다.

```csharp
sealed class DisplayClass
{
    public int counter;                 // 포획된 지역 변수 → 필드
    public void Lambda() { counter++; } // 람다 본문 → 메서드
}

void Setup()
{
    var env = new DisplayClass();       // 힙 할당
    env.counter = 0;                    // 지역 변수 초기화 → 필드 대입
    button.onClick += env.Lambda;       // 델리게이트가 env를 참조
}
```

`Setup`의 스택에는 `env` 참조만 있고 실제 값은 힙 객체 안에 있다. `Setup`이
리턴해도 델리게이트가 `env`를 참조하므로 객체는 살아남고, 버튼을 누르면
`env.counter`가 증가한다. 같은 스코프의 여러 람다는 하나의 DisplayClass 인스턴스를
공유하며, 그래서 한 람다가 바꾼 값을 다른 람다가 본다.

### 실무(게임 개발)에서 생기는 문제와 해결
지역 변수를 포획하는 람다를 만들 때마다 DisplayClass 인스턴스가 힙에 할당된다.
소스에 `new`가 없는 숨은 할당이라 놓치기 쉽다. `Update`처럼 매 프레임 도는 경로에서
포획 람다를 만들면 프레임마다 이 객체가 쌓여 GC 스파이크로 돌아온다. 완화법:
아무것도 포획하지 않는 람다는 컴파일러가 static 델리게이트로 캐싱하므로 포획을
피하면 할당이 사라진다. 포획이 필요하면 람다를 매 프레임 위치가 아니라 한 번만
생성되는 곳으로 끌어올려 재사용한다.

### 흔한 오해/함정
"람다가 변수 값을 복사해 간다"는 것은 오해다. 값 복사가 아니라 변수 자체가 힙
객체의 필드로 승격되어 공유된다. 그래서 등록 후 원본을 바꿔도 람다가 나중에 보는
값에 반영된다. 또한 한 스코프의 포획 대상 지역 변수들은 하나의 DisplayClass에 함께
묶이므로, 가벼워 보이는 포획이 예상보다 큰 객체를 살려두거나 무관한 변수의 수명을
늘릴 수 있다.
