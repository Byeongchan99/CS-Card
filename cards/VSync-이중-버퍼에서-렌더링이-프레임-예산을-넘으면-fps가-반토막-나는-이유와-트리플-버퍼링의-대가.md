## 질문
60Hz 모니터(VBlank 약 16.7ms 주기)에서 VSync를 켠 이중 버퍼를 쓰는데, 한 프레임 렌더링에 일정하게 18ms가 걸린다. 화면 갱신 빈도는 대략 얼마가 되며 왜 그런가? 이때 버퍼를 하나 더 두는 트리플 버퍼링은 무엇을 개선하고 무엇을 비용으로 치르는가?

## 핵심 답변
약 30fps가 된다. 18ms에 완성된 프레임은 첫 VBlank(16.7ms)를 놓쳐 33.3ms에야 교체되고, 그동안 렌더러는 다음 프레임을 그릴 수 없다. 프론트 버퍼는 스캔아웃 중이고 백 버퍼에는 교체를 기다리는 완성 프레임이 있어서 쓸 버퍼가 없기 때문이다. 트리플 버퍼링은 세 번째 버퍼에 다음 프레임을 바로 그리게 해서 이 대기를 없애고, 갱신을 약 55fps 수준까지 올린다. 대가는 메모리 추가, 프레임 간격이 고르지 않은 데서 오는 미세한 끊김이다. 그리고 완성 프레임을 줄 세우는 FIFO 방식이라면, 렌더링이 주사율보다 빠를 때 입력 지연이 늘어난다.

## 정리
### 내부 동작
```
이중 버퍼 + VSync
시간(ms)  0        16.7      33.3      50.0      66.7
VBlank    |         |         |         |         |
렌더러    [---F1 18ms---]대기-[---F2 18ms---]대기-
교체                          ^F1                 ^F2      → 33.3ms마다 1회 = 30fps

트리플 버퍼 + VSync
렌더러    [--F1--][--F2--][--F3--][--F4--] ...  18ms마다 연속 생산
교체      VBlank마다 가장 앞선 완성 프레임 표시                → 약 55fps
```

### 왜 그런가
교체가 VBlank 격자에만 일어나므로 프레임 시간은 16.7ms의 정수배로 올림된다. 16.7ms를 조금만 넘겨도 33.3ms가 되어, 성능이 완만하게 줄지 않고 60에서 30으로 계단식으로 떨어진다.

### 트레이드오프
- **메모리:** 버퍼 하나만큼 더 든다.
- **프레임 페이싱:** 18ms 주기의 프레임이 16.7ms 격자에 맞춰 나가므로, 대부분은 한 주기, 일부는 두 주기 동안 보인다. 평균 fps는 올라도 judder가 생길 수 있다.
- **입력 지연:** 방식에 따라 다르다. FIFO(큐) 방식은 렌더링이 주사율보다 빠를 때 완성 프레임이 큐에서 기다리므로, 화면에 나가는 프레임이 오래된 것이 되어 지연이 늘어난다. 대기 프레임을 최신 것으로 덮어쓰는 방식(Vulkan의 MAILBOX 모드)은 지연이 늘지 않는 대신, 그려 놓고 버리는 프레임이 생긴다.

### 실무(게임 개발)에서 생기는 문제와 해결
프레임 예산은 평균이 아니라 최악의 프레임 기준으로 관리해야 한다. 가끔 튀는 18ms 프레임이 VSync 환경에서는 한 주기를 통째로 잃는 33ms 프레임이 된다. 반응성이 중요한 장르(격투, 리듬)는 큐 방식 트리플 버퍼를 피하거나 렌더 대기열 길이를 줄인다.
