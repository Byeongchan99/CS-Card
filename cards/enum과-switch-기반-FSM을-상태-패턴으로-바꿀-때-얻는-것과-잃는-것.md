## 질문
캐릭터 상태(Idle / Move / Jump / Attack / Hit)를 enum 필드 하나와 Update 안의 switch 문으로 관리하던 코드를, 각 상태를 별도 클래스로 만들고 인터페이스를 통해 현재 상태 객체에 위임하는 상태 패턴으로 바꾸면 구조적으로 무엇이 좋아지고 무엇을 잃는가?

## 핵심 답변
가장 실질적인 이득은 OCP나 SRP가 아니라 상태의 진입/탈출 훅이 생긴다는 점이다. switch 버전은 "그 상태에 머무는 동안 할 일"만 표현할 수 있어서, 진입 시 초기화 코드가 전이가 일어나는 모든 지점에 복사되고 새 전이 경로를 추가한 사람이 한 줄을 빠뜨리면 재현 조건이 좁은 버그가 된다. 상태 패턴은 모든 전이가 ChangeState 한 곳을 통과하도록 강제해서 Enter/Exit가 누가 부르든 반드시 한 번씩 실행되게 만든다. 대신 클래스 수가 늘고, 전이 조건이 여러 파일로 흩어지며, 인터페이스 가상 호출 비용이 붙는다. 상태가 서너 개뿐이고 진입/탈출 처리가 없다면 switch가 여전히 더 낫다.

## 정리

### 왜 그런가
switch FSM의 문제는 코드가 길어지는 것이 아니라 상태의 수명 주기를 표현할 자리가 없다는 것이다. 상태에는 들어갈 때 한 번, 머무는 동안 매 프레임, 나갈 때 한 번이라는 세 시점이 있는데 `case Attack:` 블록은 이 중 가운데 것만 자연스럽게 표현한다.

그래서 콤보 카운터 초기화나 히트박스 활성화 같은 진입 처리는 갈 곳이 없어지고, 전이가 일어나는 지점마다 손으로 복사된다.

```csharp
// switch 버전 — 진입 처리가 전이 지점마다 흩어진다
if (Input.GetButtonDown("Attack"))
{
    _state = State.Attack;
    _comboCount = 0;        // 이 두 줄을
    _hitbox.enabled = true; // Attack으로 가는 모든 곳에 써야 한다
}
```

진입 경로가 다섯 개면 다섯 곳에 있어야 하고, 여섯 번째를 추가한 사람이 한 줄을 빠뜨리면 특정 경로로 들어갔을 때만 히트박스가 안 켜진다. 원인은 공격 코드가 아니라 전이 코드에 있어서 디버깅도 어렵다.

### 내부 동작
```csharp
public interface ICharacterState
{
    void Enter();
    void Update();
    void Exit();
}

public class StateMachine
{
    private ICharacterState _current;

    public void ChangeState(ICharacterState next)
    {
        _current?.Exit();
        _current = next;
        _current.Enter();
    }
}
```

핵심은 인터페이스가 아니라 ChangeState가 유일한 통로라는 점이다. 전이가 이 한 곳을 반드시 통과하므로 Enter와 Exit는 정확히 한 번씩 짝지어 실행된다. 상태 패턴이 파는 것은 구조적 우아함이 아니라 누락 불가능성이다.

### 트레이드오프
얻는 것은 진입/탈출 처리의 누락 불가능성, 그리고 기존 상태의 행동을 고칠 때 다른 상태 파일을 열 필요가 없다는 것이다.

잃는 것은 클래스 수 증가, 전이 조건의 분산, 그리고 런타임 비용이다. switch는 점프 테이블 한 번이지만 상태 패턴은 인터페이스 가상 디스패치다. 캐릭터 하나로는 무의미하지만 수천 유닛이 각자 FSM을 돌리는 RTS나 오토배틀러에서는 캐시 미스와 함께 유의미해지고, 그 규모에서는 애초에 OOP FSM 대신 데이터 지향 구조로 간다.

### 실무(게임 개발)에서 생기는 문제와 해결
상태 3~4개에 전이가 단순하면 switch가 정답이다. UI 버튼이나 문 개폐에 상태 패턴을 쓰는 것은 오버엔지니어링이다.

플레이어 캐릭터나 보스처럼 상태가 다섯 개를 넘고 각 상태가 진입/탈출 처리를 가지면 상태 패턴으로 간다. 이때 상태 객체는 전이마다 new 하지 말고 미리 만들어 캐싱한다. 매 프레임 전이가 가능한 구조에서 상태 객체를 새로 만들면 그대로 GC 압력이 된다.

### 흔한 오해/함정
"상태 패턴을 쓰면 새 상태 추가 시 기존 코드를 안 고쳐도 된다"는 설명은 절반만 맞다. 상세는 꼬리 질문 카드에서 다룬다.
