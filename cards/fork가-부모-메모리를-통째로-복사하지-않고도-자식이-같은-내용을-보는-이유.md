## 질문
fork로 자식 프로세스를 만들 때 커널은 부모의 힙·데이터·스택 내용을 통째로 복사하지 않는다. 그런데도 자식은 부모와 똑같은 메모리 내용을 본다. 어떻게 가능하며, 내용을 복사하지 않는다면 프로세스 생성에서 스레드 대비 진짜로 비싼 작업은 무엇이 남는가?

## 핵심 답변
Copy-on-Write를 쓴다. fork 직후 부모와 자식의 가상 주소 공간은 분리되지만, 두 페이지 테이블 엔트리가 같은 물리 페이지를 가리키게 해서 동일한 내용을 보게 한다. 즉 페이지 테이블은 복사하되 물리 페이지 내용은 공유하고, 복사는 쓰기 시점까지 미룬다. 따라서 프로세스 생성에서 스레드 대비 비싼 작업으로 남는 것은 독립 주소 공간을 위한 페이지 테이블 구조 복사, PCB 생성, 스케줄링 정보 세팅 같은 커널 자료구조 작업이다.

## 정리

### 개념
Copy-on-Write(CoW): 복사가 필요해 보이는 자원을 즉시 복제하지 않고 여러 주체가 공유하다가, 누군가 수정을 시도하는 순간에만 실제로 복제하는 기법.

### 왜 그런가
fork가 부모의 전 주소 공간을 즉시 복사한다면 프로세스 생성이 훨씬 느려진다. 게다가 fork 직후 exec로 갈아엎는 흔한 패턴에서는 그 복사가 통째로 낭비된다. 그래서 복사를 실제 쓰기 시점까지 미루는 것이 이득이다.

### 내부 동작
fork 직후 자식은 새 페이지 테이블을 받지만 그 엔트리들은 부모와 같은 물리 페이지를 가리킨다. 가상 주소 공간은 논리적으로 분리됐지만 물리 메모리는 공유 상태다. 쓰기가 일어나면 그때 폴트를 통해 해당 페이지만 복제한다(→ [[CoW 페이지에 쓰기가 일어날 때 하드웨어와 커널 사이에서 벌어지는 일]]).

### 실무(게임 개발)에서 생기는 문제와 해결
CoW/fork는 클라이언트보다 게임 서버, 빌드 파이프라인, 툴 자동화가 자식 프로세스를 대량으로 띄우는 상황에서 직접 만난다. "복제를 미루고 공유하다가 필요할 때만 분리한다"는 발상은 [[오브젝트 풀링은 무엇이고 어떻게 GC 부담을 줄이는가]] 같은 자원 재사용 패턴과 사고방식이 닮아 있다.

### 흔한 오해/함정
- "fork는 부모를 통째로 복사한다"는 옛 설명이다. 현대 커널은 CoW로 내용 복사를 미룬다.
- 그래서 프로세스 생성 비용을 "메모리 복사"로 설명하면 틀린다. 실제 비용은 페이지 테이블/PCB 등 커널 자료구조에 있다.
