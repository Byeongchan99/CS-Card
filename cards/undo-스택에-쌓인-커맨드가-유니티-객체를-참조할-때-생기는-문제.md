## 질문
undo 스택에 커맨드를 쌓아두는 구현에서, 커맨드가 `GameObject`나 `Transform` 같은 유니티 객체를 Receiver 참조로 들고 있을 때 생기는 문제는 무엇인가?

## 핵심 답변
undo 스택이 커맨드를 붙잡고 있는 동안 대상이 `Destroy`될 수 있다. `Destroy`는 네이티브 객체만 없애고 C# 래퍼는 힙에 남으므로, 참조는 비어 있지 않은데 대상은 실재하지 않는 fake null 상태가 된다. 그 상태로 undo를 하면 파괴된 대상에 상태를 되돌리려 하게 된다. 문제는 이 상태를 어떤 null 체크로 잡느냐에 따라 결과가 갈린다는 점이다.

## 정리

### 왜 그런가
`UnityEngine.Object`가 오버로딩한 `==`는 네이티브 파괴 여부를 확인해 파괴된 객체를 null로 보고한다. 반면 `is null`과 `ReferenceEquals`는 연산자 오버로딩을 거치지 않으므로, 래퍼가 힙에 남아 있는 한 파괴된 객체를 살아 있다고 판정한다.

```csharp
public void Undo()
{
    if (_target == null) return;  // 오버로딩된 ==, fake null을 잡는다
    // if (_target is null) return;  // 패턴 매칭은 오버로딩을 우회해 통과시킨다
    _target.position = _previousPosition;
}
```

### 실무(게임 개발)에서 생기는 문제와 해결
에디터 툴의 undo 히스토리처럼 커맨드가 오래 살아남는 구조에서 특히 드러난다. undo 실행 직전에 대상 유효성을 검사하고, 유효하지 않을 때의 정책(건너뛰기, 스택에서 제거, 그 지점 이후 히스토리 무효화)을 미리 정해 두어야 한다. 검사 코드에서 `==`와 `is null`을 섞어 쓰지 않는 것이 전제다.

### 흔한 오해/함정
"예외 처리하면 된다"로 끝내면 정작 검사에서 fake null이 통과하는 경로를 놓친다. 파괴 여부 판정 자체가 유니티에서는 일반 C#과 다르게 동작한다.
