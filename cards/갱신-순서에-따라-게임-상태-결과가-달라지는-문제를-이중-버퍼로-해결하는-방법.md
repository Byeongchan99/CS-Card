## 질문
아래 코드에서 배우 셋이 Harry → Baldy → Chump → Harry 순서로 원형으로 서서 각자 화살표 방향의 상대를 바라본다. 1프레임 시작 전에 Harry만 맞은 상태다. 갱신 순서가 Harry, Baldy, Chump일 때와 Chump, Baldy, Harry일 때 1~3프레임의 출력은 각각 어떻게 되는가? 결과가 다른 근본 원인은 무엇이고, 이중 버퍼로 순서와 무관하게 만들려면 상태를 어떻게 나누고 언제 교체해야 하는가?

```csharp
class Actor
{
    public string Name;
    public Actor Facing;
    bool _slapped;

    public void Slap() => _slapped = true;

    public void Update()
    {
        if (_slapped)
        {
            Console.WriteLine($"{Name} slaps {Facing.Name}");
            Facing.Slap();
        }
        _slapped = false;
    }
}
```

## 핵심 답변
정방향 순서(Harry, Baldy, Chump)에서는 매 프레임 세 줄이 모두 출력된다. 마지막에 Chump가 때린 Harry는 이미 갱신을 마쳐서 맞은 상태가 다음 프레임까지 남기 때문이다. 역방향 순서(Chump, Baldy, Harry)에서는 때리는 시점에 상대의 갱신이 이미 끝나 있어서, 1프레임 Harry, 2프레임 Baldy, 3프레임 Chump로 한 프레임에 한 단계씩 전달된다. 근본 원인은 같은 프레임 안에서 쓴 값을 뒤에 실행되는 쪽이 즉시 읽는다는 것이다. 상태를 읽기용 current와 기록용 next로 나누고, 모든 Update가 끝난 뒤 일괄 교체하면 어떤 순서든 결과가 "한 프레임에 한 단계 전파"로 통일된다.

## 정리
### 내부 동작
```
정방향 (Harry, Baldy, Chump)
  1프레임: Harry slaps Baldy / Baldy slaps Chump / Chump slaps Harry
  2프레임: (동일)
  3프레임: (동일)

역방향 (Chump, Baldy, Harry)
  1프레임: Harry slaps Baldy
  2프레임: Baldy slaps Chump
  3프레임: Chump slaps Harry
```

### 왜 그런가
그래픽스의 이중 버퍼와 같은 구조다. 렌더러와 디스플레이 대신, 같은 프레임 안에서 먼저 갱신되는 오브젝트(쓰는 쪽)와 나중에 갱신되는 오브젝트(읽는 쪽)가 하나의 상태에 동시에 접근한다. 읽는 쪽이 "이번 프레임에 이미 바뀐 값"을 볼지 말지가 실행 순서로 결정된다.

### 실무(게임 개발)에서 생기는 문제와 해결
오브젝트 갱신 순서는 생성 순서, 컨테이너 내부 구현, 스크립트 실행 순서 설정 등에 묶여 있어서, 작은 변경으로도 바뀔 수 있다. 순서 의존 버그는 재현이 어렵다. 모든 개체가 같은 시점의 세계를 보고 판단해야 하는 시스템(물리, 셀룰러 오토마타, AI 영향력 맵, 상호작용하는 상태 머신)에서 이중 버퍼가 쓰인다.

### 트레이드오프
순서 독립성을 얻는 대신 전파가 프레임당 한 단계로 묶인다. 상태 메모리도 두 배가 든다.
