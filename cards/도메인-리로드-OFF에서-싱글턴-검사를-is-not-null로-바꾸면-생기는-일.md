## 질문
도메인 리로드를 끈 에디터에서, Awake에 `if (Instance != null) { Destroy(gameObject); return; }` 검사가 있는 MonoBehaviour 싱글턴(OnDestroy 없음)을 Title 씬에서 플레이 → 중지 → 다시 플레이했다. 두 번째 플레이에서 Title의 GameManager는 Instance가 되는가 자폭하는가? 검사를 `is not null`로 바꾸면 어떻게 달라지고, 이후 `Instance.Score`(C# 필드를 돌려주는 프로퍼티)와 `Instance.transform`에 접근하면 각각 어떻게 되는가?

## 핵심 답변
`!=` 버전은 정상적으로 Instance가 된다. static `Instance`에는 지난 플레이에서 파괴된 매니저의 C# 래퍼가 남아 있지만, 오버로딩된 `!=`가 네이티브 쪽이 죽은 것을 보고 null로 취급하기 때문이다. 설계가 아니라 오버로딩 덕에 우연히 맞는 것이다. `is not null`은 오버로딩을 우회해 순수 참조만 보므로 죽은 래퍼를 살아 있다고 판단하고, 새 매니저가 자폭해 살아 있는 매니저가 하나도 없게 된다. 이때 `Score`는 래퍼 안의 C# 필드라 예외 없이 지난 플레이의 값이 나오고, `transform`은 네이티브 객체를 거치므로 MissingReferenceException이 난다.

## 정리
### 내부 동작
```
static Instance ──▶ [C# 래퍼 (관리 힙)]
                      score = 340              ← 읽기 성공 (네이티브와 무관)
                      네이티브 연결 ──▶ ✕ 파괴됨  ← transform, StartCoroutine 등은 예외
```

### 왜 그런가
C# 래퍼와 네이티브 객체의 수명이 분리되어 있다. 일반 필드 읽기는 관리 힙의 래퍼만 건드리므로 확인 지점이 없다. 엔진 기능을 쓰는 멤버는 래퍼가 들고 있던 네이티브 포인터를 따라가야 하므로, 엔진 바인딩이 끊긴 포인터를 확인하는 순간 예외를 던진다.

### 흔한 오해/함정
`is null`, `is not null`, `?.`, `??`는 유니티의 `==` 오버로딩을 거치지 않는다. 일반 C# 스타일로 바꾸는 리팩터링이 유니티 오브젝트에서는 동작을 바꾼다. 그리고 "파괴된 객체에 접근하면 예외"라는 직관은 엔진을 거치는 멤버에만 맞다. 필드만 읽으면 조용히 낡은 값이 흘러나와 크래시보다 찾기 어렵다.
