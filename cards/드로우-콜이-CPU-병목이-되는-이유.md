## 질문
GPU는 삼각형 수백만 개도 순식간에 처리하는데, 왜 렌더링 최적화에서 "삼각형 총량"이 아니라 "드로우 콜 개수(호출 횟수)"가 문제가 되는가? 드로우 콜 하나가 발생할 때 CPU와 GPU 사이에서 무슨 일이 일어나며, 왜 이것이 GPU가 아니라 CPU 쪽 병목이 되는가?

## 핵심 답변
드로우 콜의 비용은 GPU가 그림을 그리는 것 자체가 아니라, CPU가 그 그리기 명령을 GPU가 알아먹는 형태로 준비·검증·번역·제출하는 데서 나온다. 이 준비 비용은 삼각형이 3개든 3만 개든 거의 동일한 고정 오버헤드다. GPU는 삼각형을 병렬로 처리하는 데 강하지만 드로우 콜 준비는 CPU가 직렬로 해야 하므로, 삼각형 총량이 적어도 드로우 콜이 너무 많으면 CPU가 먼저 병목이 되고 GPU는 다음 명령을 기다리며 논다.

## 정리

### 왜 그런가
GPU의 강점(수천 코어의 병렬 처리량)과 드로우 콜 비용(CPU의 호출당 직렬 준비 비용)은 서로 다른 축이다. 삼각형이 많아 느린 것은 fill rate나 정점 처리량의 문제이고, 드로우 콜이 많아 느린 것은 CPU 준비 비용의 문제다. 준비 비용은 그리는 삼각형 수와 거의 무관하게 호출마다 고정으로 든다.

### 내부 동작
드로우 콜 하나는 단순 함수 호출이 아니라 여러 소프트웨어 계층의 경계를 넘는 작업이다. Unity 기준으로 대략 매니지드 C# 코드 → 엔진 네이티브 렌더링 계층 → 그래픽스 API → 그래픽스 드라이버 → GPU 순으로 통과한다. 비용의 몸통은 드라이버 계층에 있고, 그 안에서 검증과 하드웨어 명령 번역이 특히 비싸다.

### 실무(게임 개발)에서 생기는 문제와 해결
드로우 콜이 CPU 바운드를 만들면 GPU가 놀아도 프레임이 안 나온다. 엔진은 드로우를 머티리얼별로 정렬해 상태 변경을 줄이고, 같은 머티리얼·메시를 묶는 배칭(정적/동적 배칭, SRP Batcher, GPU Instancing)으로 드로우 콜 수 자체를 줄인다.

### 흔한 오해/함정
"삼각형이 적으니 가볍다"는 오해. 저폴리 오브젝트라도 각각 다른 머티리얼로 수백 개를 개별 드로우하면 CPU가 병목이 된다. 문제는 폴리곤 수가 아니라 호출 횟수와 그 사이의 상태 변경이다.
