## 질문
피격처럼 어느 상태에서든 발생할 수 있는 전이를 상태별로 구현하면 중복이 생긴다. 이 중복을 없애려면 전이 검사를 어디에 두어야 하며, 그렇게 옮겼을 때 "전이 로직을 각 상태가 스스로 소유한다"는 성질에 어떤 손해가 생기는가?

## 핵심 답변
상태 머신의 공통 업데이트 단계에서 먼저 검사하고, 통과하면 현재 상태에 위임한다. 손해는 흔히 말하는 "전이가 흩어져서 한눈에 안 보인다"가 아니다. 상태 패턴은 원래부터 전이가 파일마다 흩어져 있었기 때문이다. 새로 생기는 손해는 흩어지는 규칙이 두 종류로 이중화된다는 것이다. 이전에는 어떤 상태의 탈출 경로를 알려면 그 상태 파일만 읽으면 됐지만, 이제는 어떤 상태 파일을 끝까지 읽어도 탈출 경로 전체를 알 수 없고 반드시 상태 머신 파일을 같이 읽어야 한다. 국소적으로 완결된 추론이 불가능해진 것이 정확한 비용이다.

## 정리

### 왜 그런가
피격, 사망, 스턴, 넉백, 컷신 진입은 거의 모든 상태에서 발동한다. 이를 상태별로 구현하면 N개 파일에 같은 코드가 복사되고, 더 나쁘게는 새 상태를 만들 때마다 "피격 체크 넣는 걸 잊지 마라"는 암묵적 의무가 생긴다. 명시되지 않은 의무는 반드시 잊힌다.

### 내부 동작
```csharp
public void Update()
{
    // 전역 전이 — 어떤 상태에 있든 먼저 검사
    if (_health.IsDead)      { ChangeState(_deadState); return; }
    if (_damageQueue.HasHit) { ChangeState(_hitState);  return; }

    _current.Update();
}
```

검사 순서가 곧 우선순위가 된다. 사망을 피격보다 먼저 놓아야 죽는 프레임에 피격 모션이 끼어들지 않는다. 그리고 전역 전이가 걸리면 return으로 현재 상태의 Update를 건너뛰어야 한다. 그렇지 않으면 이미 상태가 바뀐 뒤 이전 상태의 로직이 한 프레임 더 도는 사고가 난다.

### 트레이드오프
중복 제거와 국소적 추론 가능성은 여기서 정면으로 충돌한다. 전역으로 올리면 상태를 추가할 때 아무 의무도 생기지 않지만, 코드를 읽을 때는 항상 두 곳을 봐야 한다.

실무에서는 읽는 쪽을 포기하고 쓰는 쪽을 택하는 것이 보통이다. 누락 버그는 런타임에 터지고 재현이 어렵지만, 파일 두 개를 읽는 비용은 예측 가능하고 문서나 명명 규칙으로 완화할 수 있기 때문이다.

### 실무(게임 개발)에서 생기는 문제와 해결
Unity의 Animator에서 Any State가 정확히 이 개념이다. 어떤 노드에 있든 발동하는 전이를 별도 노드로 분리해 중복을 없앤 것이고, 대신 특정 노드의 나가는 화살표만 봐서는 전체 전이를 파악할 수 없다는 같은 비용을 치른다.
