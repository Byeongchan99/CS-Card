## 질문
IdleState, MoveState, JumpState가 구현된 상태 패턴 FSM에 DashState를 추가하고 Move 중 Shift로 Dash에 전이되게 하려면 어떤 파일을 수정해야 하는가? 그 결과 "상태 패턴은 OCP 위반을 해결한다"는 주장은 어디까지 참인가?

## 핵심 답변
MoveState를 열어 전이 조건을 추가해야 하고, 상태 객체를 캐싱하는 구현이라면 상태 머신에도 DashState 인스턴스 등록 코드가 들어간다. 즉 기존 코드 수정은 여전히 발생한다. 어떤 상태로 들어가는 진입 전이가 하나도 없으면 그 상태는 도달 불가능하므로, 쓸모 있는 상태는 반드시 최소 하나의 진입 전이를 갖고 그 조건은 기존 상태 안에 쓰여야 한다. 따라서 상태 패턴은 OCP 위반을 제거하는 것이 아니라 국소화한다. 수정 파일 수가 전체 상태 수에 비례하던 것이 새 상태의 진입 전이 수에 비례하도록 줄어든 것이다.

## 정리

### 왜 그런가
"의존성이 없는 상태를 추가할 때는 OCP가 지켜진다"는 조건을 끝까지 밀어붙이면 그런 상태는 존재할 수 없다는 결론이 나온다. 진입 전이가 없는 상태는 영원히 실행되지 않기 때문이다. 그러므로 상태 추가는 항상 어딘가의 기존 코드 수정을 동반한다.

### 내부 동작
DashState 추가 시 실제로 열어야 하는 곳은 두 군데다.

```csharp
// 1) MoveState — 진입 전이 조건
public void Update()
{
    if (Input.GetKeyDown(KeyCode.LeftShift) && _stamina >= 20f)
    {
        _machine.ChangeState(_machine.Dash);
        return;
    }
    // 기존 이동 로직
}

// 2) StateMachine — 인스턴스 캐싱 구현이라면 등록도 필요
public DashState Dash { get; private set; }

private void Awake()
{
    Dash = new DashState(this);   // 이 줄이 추가된다
}
```

Dash를 Idle에서도, Jump 중 캔슬로도 들어갈 수 있게 하면 그만큼 파일이 더 늘어난다. 수정 파일 수는 진입 전이 수에 비례한다.

### 트레이드오프
switch 버전은 상태가 20개든 100개든 새 상태를 추가할 때마다 같은 거대 블록을 연다. 상태 패턴은 상태 20개짜리 보스에 새 패턴을 추가할 때 진입 경로가 Idle 하나뿐이면 파일 하나만 열면 된다. 상태 수가 커질수록 격차가 벌어진다.

### 흔한 오해/함정
상태 패턴에서 OCP가 무조건 성립하는 축은 상태 추가가 아니라 기존 상태의 행동 변경이다. Move의 가속도 계산을 아무리 뜯어고쳐도 다른 상태 파일은 열 필요가 없다. 면접에서 OCP를 근거로 들 때는 이 구분을 하는 편이 정확하다.
