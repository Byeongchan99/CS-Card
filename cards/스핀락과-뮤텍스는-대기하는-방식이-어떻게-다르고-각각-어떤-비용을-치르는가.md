## 질문
멀티스레드 환경에서 임계 구역을 보호하는 스핀락과 뮤텍스가 있다. 락이 이미 잡혀 있어 대기해야 할 때, 두 방식은 "기다리는 방식"이 근본적으로 어떻게 다르며, 그 차이 때문에 각각 어떤 비용을 치르는가?

## 핵심 답변
스핀락은 실행 상태를 유지한 채 바쁜 대기(busy-wait)로 락이 풀릴 때까지 CPU를 계속 점유한다. 그래서 대기 동안 CPU 사이클이 낭비되지만, 재우고 깨우는 왕복이 없어 아주 짧은 대기에는 오히려 싸다. 뮤텍스는 CPU를 반납하고 sleep 상태로 전환되어 대기 큐로 빠진다. 그래서 대기 동안 CPU를 소비하지 않는 대신, 잠들고 다시 깨어나는 컨텍스트 스위치 왕복 비용을 치른다. 선택 기준은 예상 대기 시간과 컨텍스트 스위치 비용의 비교다.

## 정리
### 개념
- 스핀락: 락을 못 잡으면 running 상태로 짧은 확인 루프를 반복(busy-wait).
- 뮤텍스: 락을 못 잡으면 blocking, CPU 반납 후 sleep, 스케줄러 대기 큐로 이동.

### 왜 그런가
- 스핀락 비용: 대기 동안 코어를 점유해 CPU 사이클을 낭비. 대기가 길면 순수 낭비.
- 뮤텍스 비용: context switch out/in 왕복. 짧은 대기에는 이 왕복이 스핀보다 비싸다.
- 그래서 "대기가 짧을 것으로 기대되면 스핀, 길어질 수 있으면 블록"이 기본 판단.

### 트레이드오프
- 스핀락: 지연은 낮지만 CPU 낭비. 임계 구역이 짧을 때만 유리.
- 뮤텍스: CPU는 아끼지만 왕복 지연. 임계 구역이 길거나 대기가 불확실할 때 유리.
