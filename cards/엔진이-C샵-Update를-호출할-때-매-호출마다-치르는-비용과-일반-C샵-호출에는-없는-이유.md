## 질문
유니티의 C++ 엔진이 `MonoBehaviour.Update()`를 객체마다 호출할 때, 실제 메서드를 실행하기 전과 실행하는 과정에서 매 호출마다 어떤 작업을 하는가? 같은 메서드를 C# 코드 안에서 `obj.Tick()`처럼 직접 호출하면 왜 그 작업이 필요 없는가?

## 핵심 답변
엔진은 업데이트 리스트를 순회하면서 각 대상이 이번 프레임 도중 파괴되거나 비활성화되지 않았는지 확인한다. 앞서 실행된 다른 `Update`가 `Destroy`를 호출했을 수 있기 때문이다. 그다음 네이티브에서 관리 코드로 가는 호출 객체와 인자를 만들고, 스크립팅 런타임에 시그니처별로 생성된 invoker를 통해 메서드를 실행하도록 요청한다. 이 호출은 예외 처리 틀로 감싸진다. 반면 C# 안에서의 직접 호출은 컴파일 시점에 대상이 정해진 평범한 `call`이다. 생존 검사, 호출 객체 생성, 호출별 예외 처리 틀이 없으며 인라인될 수도 있다.

## 정리
### 내부 동작
```text
[엔진 BehaviourManager]
  for each behaviour in updateList:
      살아 있나? 활성인가?          ← 생존/활성 검사
      ScriptingInvocation 준비       ← 네이티브→관리 호출 객체
      runtime invoke (invoker)       ← 시그니처별 생성 함수 경유
        try { behaviour.Update(); }  ← 호출마다 예외 격리
        catch → 로그, 다음 대상으로

[매니저 Update 안]
  for (i...) _bullets[i].Tick(dt);   ← 그냥 call
```

### 트레이드오프
위 비용은 낭비가 아니라 안전장치의 값이다. 매니저 루프로 옮기면 이 안전장치를 직접 다시 만들어야 한다. 항목마다 `gameObject.activeSelf`로 검사하면 그 접근이 다시 네이티브 경계를 넘으므로 이점이 줄어든다.

### 흔한 오해/함정
구체적인 수치는 엔진 버전, Mono/IL2CPP 백엔드, 에디터인지 빌드인지에 따라 크게 달라진다. 유니티 블로그 "10000 Update() calls"는 Unity 5.2 기준 분석이며, 이후 최적화가 이루어졌다. "몇 ms 차이"를 외우기보다는 경계를 몇 번 넘는가라는 구조로 설명해야 한다.
