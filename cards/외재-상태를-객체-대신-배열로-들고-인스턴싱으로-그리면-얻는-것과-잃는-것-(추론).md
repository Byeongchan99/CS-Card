## 질문
경량 패턴을 적용한 나무 10만 그루 구조에서 Tree 객체를 아예 없애고, 각 TreeType이 외재 상태를 Matrix4x4[]와 Vector4[] 배열로만 들고 있다가 Graphics.RenderMeshInstanced로 한 번에 그린다고 하자. Tree 객체 10만 개 구조와 비교해 메모리와 CPU 측면에서 무엇을 얻고 무엇을 잃는가?

```csharp
class TreeType
{
    Mesh mesh;
    Material material;          // GPU 인스턴싱을 켠 공유 머티리얼
    Matrix4x4[] transforms;     // 위치·회전·크기
    Vector4[] tints;            // 색조
    void Draw() { /* Graphics.RenderMeshInstanced */ }
}
```

## 핵심 답변
10만 개의 관리 객체가 몇 개의 배열로 바뀌어 객체 헤더와 참조가 사라지고 GC가 추적할 객체 수가 크게 준다. 외재 상태가 연속 메모리에 놓여 순회 시 캐시 지역성이 좋아지고, 배열이 인스턴싱 드로우의 입력 형태 그대로라 나무별로 데이터를 모으는 과정도 없어진다. 대신 개체가 인덱스로만 존재하므로 삭제 시 인덱스가 어긋나는 문제를 핸들 같은 장치로 막아야 하고, 개체별 행동, 콜라이더, 엔진의 렌더러 단위 컬링을 잃어 직접 구현해야 한다.

## 정리
### 왜 그런가
경량 패턴은 내재 상태의 중복을 없앴지만 외재 상태를 담는 객체 껍데기는 남겨 둔다. 이 구조는 그 껍데기까지 없애고 외재 상태를 데이터 배열로만 다룬다.

### 실무(게임 개발)에서 생기는 문제와 해결
중간 원소를 지울 때 마지막 원소를 그 자리로 옮기면 바깥의 인덱스가 다른 나무를 가리키게 되므로, 인덱스 대신 핸들이나 세대 번호를 둔다. 한 번의 인스턴싱 드로우에 담을 수 있는 인스턴스 수에는 인스턴스당 데이터 크기에 따른 상한이 있어 큰 배열은 나눠 그린다.

### 트레이드오프
행동이 거의 없고 수가 압도적으로 많은 대상(식생, 파편, 군중 배경)에는 배열 구조가 유리하고, 개체마다 복잡한 행동과 상호작용이 필요한 대상에는 객체 구조가 여전히 다루기 쉽다. 이 방향은 데이터 지향 설계, 유니티 ECS와 같은 발상이다.
