## 질문
수백 스텝짜리 undo 스택을 가진 에디터 툴이나 리플레이 시스템에서, 커맨드가 유니티 객체를 직접 참조하는 구조가 메모리에 남기는 것은 무엇인가? 이를 설계 단계에서 줄이려면 커맨드가 Receiver를 어떤 형태로 들어야 하는가?

## 핵심 답변
커맨드 객체 자체, 각 커맨드가 보관한 실행 전 상태 스냅샷, 그리고 Receiver 참조가 모두 스택 길이만큼 상주한다. 특히 파괴된 대상의 C# 래퍼도 커맨드가 잡고 있는 동안 수거되지 않으므로, 네이티브 메모리는 풀렸는데 관리 힙에는 쓸모없는 래퍼가 계속 쌓인다. 해법은 커맨드가 직접 참조 대신 안정적인 ID를 들고, 실행·undo 시점에 레지스트리로 해석하는 것이다.

## 정리

### 내부 동작
```csharp
public class MoveCommand : ICommand
{
    private readonly int _targetId;       // 참조가 아니라 식별자
    private readonly Vector3 _delta;
    private Vector3 _previousPosition;

    public void Undo()
    {
        if (!ObjectRegistry.TryGet(_targetId, out Transform target)) return;
        target.position = _previousPosition;
    }
}
```

### 왜 그런가
커맨드를 순수 데이터로 만들면 유니티 객체 수명에 묶이지 않는다. 래퍼를 붙잡지 않으니 누수가 사라지고, 직렬화가 가능해져 리플레이 파일 저장이나 네트워크 전송, 에디터 세션을 넘는 히스토리 보존까지 열린다. 결정론적 리플레이와 롤백 넷코드가 커맨드를 이 형태로 다루는 이유다.

### 트레이드오프
ID를 객체로 바꾸는 조회 비용이 실행마다 붙는다. 더 중요한 것은 조회 실패 시의 정책을 설계자가 정해야 한다는 점이다. 이 정책이 없으면 fake null 문제가 조회 실패 문제로 이름만 바뀐 것이 된다.

### 실무(게임 개발)에서 생기는 문제와 해결
히스토리 길이에 상한을 두고 오래된 커맨드를 버리는 것이 기본이다. 상한과 ID 방식은 함께 쓰는데, 히스토리가 잘려 나갈 때 비로소 그 ID를 회수할 수 있기 때문이다.
