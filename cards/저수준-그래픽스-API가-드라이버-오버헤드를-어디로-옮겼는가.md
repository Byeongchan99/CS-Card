## 질문
(추론 문제) 전통적 API(D3D11, OpenGL)에서는 드라이버가 런타임에 매 드로우마다 검증·번역을 수행하는 것이 드로우 콜 오버헤드의 원인이었다. Vulkan/D3D12/Metal 같은 저수준 API는 이 드라이버 오버헤드를 줄이기 위해 "무엇을, 언제로/누구에게로" 옮겼는가?

## 핵심 답변
저수준 API는 드라이버가 런타임에 암묵적으로 하던 일을 세 갈래로 재배치한다. 첫째, PSO 생성을 초기화/로딩 타임으로 옮겨 검증·번역·셰이더 컴파일을 미리 끝내둔다. 그릴 때는 이미 검증된 PSO를 바인딩만 하므로 드로우 타임 상태 검증이 사라진다. 둘째, 명령 기록을 커맨드 버퍼로 분리해 여러 스레드에서 미리 기록하게 함으로써, 드라이버가 직렬로 처리하던 명령 생성 병목을 멀티코어에 분산한다. 셋째, 매 호출 검증 자체를 개발 중에만 켜는 validation layer로 빼고 릴리스에서는 끈다. 대가는 개발자가 리소스 상태 전환·동기화·메모리 관리를 직접 책임져야 한다는 것이다.

## 정리

### 왜 그런가
문제가 "드라이버가 런타임에 매번 검증·번역한다"였으니, 해결의 방향은 그 작업을 런타임에서 다른 시점(로딩 타임)과 다른 주체(애플리케이션, 멀티스레드)로 옮기는 것이다. 세 갈래 모두 이 하나의 논리에서 파생된다.

### 내부 동작
PSO를 앞서 통째로 링크하면 셰이더 입출력 기반 최적화가 가능해지고 draw time state validation이 제거된다(Vulkan 문서 명시). 명령 기록은 여러 커맨드 버퍼를 여러 스레드에서 동시에 채워 CPU 준비 비용을 분산한다. 저수준 API의 근본 동기 자체가 "직렬화된 call-preparation 병목을 없애 멀티코어를 제대로 쓰는 것"이다.

### 트레이드오프
얻는 것: 드라이버 오버헤드 감소, 멀티코어 활용, 예측 가능한 성능. 잃는 것: 개발자 부담 급증. 리소스 상태 전환(배리어), 동기화, 메모리 할당을 전부 수동으로 관리해야 한다. PSO를 미리 안 구우면 게임 중 첫 사용 머티리얼에서 컴파일 hitch가 발생한다.

### 실무(게임 개발)에서 생기는 문제와 해결
대부분의 게임 개발자는 이 저수준 API를 직접 만지지 않는다. Unity/Unreal 같은 엔진이 복잡성을 흡수하고 내부적으로 D3D12/Vulkan/Metal 백엔드를 쓴다. 개발자는 이 계층의 존재를 이해하는 선에서, 왜 배칭과 상태 정렬이 효과적인지의 근거로 삼으면 된다.

### 흔한 오해/함정
"저수준 API로 바꾸면 무조건 빨라진다"는 오해. 어느 쪽이 빠른지는 워크로드·GPU·드라이버·엔진 구현에 따라 다르며, 잘못 쓰면 전통적 API보다 느릴 수도 있다. 저수준 API의 이점은 자동이 아니라 개발자가 책임을 제대로 질 때만 실현된다.
