## 질문
피격, 사망, 스턴, 넉백, 컷신처럼 여러 상태에서 공통으로 발동하는 전이를 계속 상태 머신으로 올리다 보면 상태 머신에는 무엇이 남고 각 상태 클래스에는 무엇이 남는가? 그 결과물은 처음에 버렸던 switch 버전과 무엇이 같고 무엇이 다른가?

## 핵심 답변
상태 머신에는 조건과 가드와 목적지로 이루어진 전이 목록이 남고, 상태 클래스에는 행동만 남는다. 전이 판단이 다시 한 곳으로 모인다는 점에서 switch 버전으로 회귀한 것처럼 보인다. 하지만 switch 버전은 전이와 행동이 둘 다 한 파일에 있었고 최종 형태는 전이만 중앙에 있으며 행동은 여전히 분산되어 있다. 되돌아간 것은 절반이고, 되돌아가지 않은 절반이 이 구조의 가치다. 그리고 중앙의 전이를 if 나열이 아니라 데이터로 표현하면 전이 추가에 코드 수정이 필요 없어져 OCP가 이번에는 진짜로 성립한다.

## 정리

### 왜 그런가
파일 크기 증가가 무엇에 비례하는지가 갈린다. switch 버전은 전이 수와 행동 복잡도 둘 다에 비례해 한 파일이 커진다. 최종 형태는 중앙 파일이 전이 수에만 비례하고, 행동이 아무리 복잡해져도 각자의 파일에 머문다. 전이 수는 대체로 상태 수보다 훨씬 느리게 자라므로 이 차이가 크다.

### 내부 동작
중앙에 모인 전이를 데이터로 표현하면 성질이 한 번 더 바뀐다.

```csharp
// 전이 테이블 — 전이 추가가 코드 수정이 아니라 데이터 추가가 된다
_transitions.Add(new Transition(
    from: typeof(MoveState),
    to:   typeof(DashState),
    condition: () => Input.GetKeyDown(KeyCode.LeftShift) && _stamina >= 20f));

_transitions.AddAny(                       // from 없음 = 전역 전이
    to: typeof(HitState),
    condition: () => _damageQueue.HasHit,
    guard: s => s.CanBeHit);
```

전역 전이는 from이 비어 있는 전이일 뿐이고, 상태별 예외는 그 전이에 붙은 가드일 뿐이다. 앞선 갈래에서 따로 다뤘던 것들이 하나의 자료구조로 통합된다.

### 트레이드오프
전이가 데이터가 되면 컴파일 타임 검증을 잃는다. 오타, 도달 불가능한 상태, 조건이 겹쳐 우선순위가 모호해지는 전이를 컴파일러가 잡아주지 못하므로, 초기화 시점의 검증 코드나 그래프를 시각화하는 에디터 툴이 사실상 필수가 된다. 얻는 것은 기획자가 전이 규칙을 직접 만질 수 있다는 점이다.

### 실무(게임 개발)에서 생기는 문제와 해결
Unity의 Animator가 정확히 이 구조다. 노드는 애니메이션이라는 행동이고, 화살표는 전이 데이터이며, Any State는 from이 비어 있는 전역 전이이고, 전이에 걸린 Condition이 가드다. Mecanim을 써봤다면 이미 이 아키텍처를 사용한 것이다.

다만 Animator를 게임 로직 FSM으로 전용하는 것은 별개 문제다. 전이가 프레임 지연을 갖고 파라미터가 문자열 기반이라 타입 안전하지 않아서, 실무에서는 로직 FSM을 따로 두고 Animator는 표현만 담당하게 나누는 편이 일반적이다.

선택 기준으로 정리하면, 전역 전이가 세 개를 넘거나 전이 규칙 자체를 데이터로 다루고 싶어지는 시점이 전이 테이블로 넘어갈 때다. 상태 안에 다시 하위 상태가 필요해지면 계층형 FSM으로, 조건 판단이 우선순위와 트리 탐색을 요구할 만큼 복잡해지면 비헤이비어 트리로 가는 것이 일반적인 진행 경로다.
