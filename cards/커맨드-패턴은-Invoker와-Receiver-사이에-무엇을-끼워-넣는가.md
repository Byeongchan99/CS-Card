## 질문
커맨드 패턴은 호출하는 쪽(Invoker)과 실제 일을 하는 쪽(Receiver) 사이에 무엇을 끼워 넣는 패턴인가? 그리고 "요청을 객체로 만든다"는 구조 때문에 새로 가능해지는 일은 무엇인가?

## 핵심 답변
요청 자체를 `Execute()`를 가진 객체로 캡슐화해서 Invoker와 Receiver 사이에 끼워 넣는다. Invoker는 `ICommand` 추상만 알고 어떤 Receiver가 무슨 일을 하는지 모르며, Receiver도 자기가 누구에게 호출되는지 모른다. 요청이 값이 되었으므로 저장·전달·조작이 가능해지고, 여기서 undo/redo, 리플레이, 큐잉과 지연 실행, 로깅, 여러 커맨드를 묶는 매크로가 전부 파생된다.

## 정리

### 개념
직접 호출문은 실행되는 순간 사라지므로 어디에도 값으로 존재하지 않는다. 커맨드 패턴은 호출을 객체로 승격시켜 요청을 1급 값으로 만든다.

```csharp
public interface ICommand
{
    void Execute();
    void Undo();
}

// Invoker는 ICommand만 참조한다
_history.Push(command);
command.Execute();
```

### 왜 그런가
Invoker가 Receiver 타입을 컴파일 타임에 참조하지 않게 되면서 결합이 양방향으로 끊어진다. 입력 처리기는 플레이어 타입을 모르고, 플레이어는 입력·AI·리플레이 중 무엇이 자신을 호출하는지 모른다. 새 명령을 추가할 때 Invoker를 수정하지 않아도 되므로 OCP 측면의 이점도 여기서 나온다.

### 실무(게임 개발)에서 생기는 문제와 해결
키 리바인딩은 키와 커맨드 객체의 매핑만 바꾸면 되고, AI는 사람이 누르는 것과 같은 커맨드를 큐에 넣어 동일한 실행 경로를 탄다. 리플레이는 커맨드 로그를 순서대로 재생하는 것으로 구현된다.

### 흔한 오해/함정
커맨드 패턴의 목적을 undo/redo로만 기억하면 큐잉·지연 실행·로깅·매크로 용례를 놓친다. 이들은 모두 "요청이 저장·전달 가능한 값이 되었다"는 같은 성질에서 나온다.
