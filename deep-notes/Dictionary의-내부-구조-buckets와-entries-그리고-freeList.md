## O(1)은 해시가 키를 골고루 흩뿌린다는 가정 위에 서 있다

`Dictionary<TKey, TValue>`가 키 하나를 찾는 데 드는 시간이 원소 수와 무관하다는 것,
그것이 평균 O(1)의 의미다. 이게 가능한 이유는 조회가 세 단계로 끝나기 때문이다.
키의 해시코드를 계산하고, 그 해시로 어느 bucket에 속하는지를 산술 연산 한 번으로
정하고, 그 bucket 안에서만 키를 비교한다. 배열 전체를 훑지 않는다.

문제는 마지막 단계다. bucket 안에 원소가 하나뿐이라면 비교도 한 번이면 끝난다.
그런데 서로 다른 키가 같은 bucket으로 떨어지는 충돌이 일어나면, 그 bucket에 쌓인
후보들을 하나씩 비교해야 한다. 충돌이 심해지면 이 비교 횟수가 늘고, 극단적으로 모든
키가 한 bucket에 몰리면 조회는 O(n)으로 퇴화한다. 그래서 O(1)은 공짜가 아니라
"해시 함수가 키들을 bucket에 고르게 분산시킨다"와 "bucket 수가 원소 수에 비례해서
넉넉하다"는 두 전제 위에서만 성립한다. 뒤의 전제를 유지하는 장치가 resize다.

bucket 인덱스는 보통 `hashCode % buckets.Length`로 정한다. 해시코드의 부호 비트는
버려서(하위 31비트만 사용) 항상 음이 아닌 값으로 만든 뒤 bucket 수로 나눈 나머지를
쓴다. bucket 수를 소수(prime)로 잡는 이유가 여기 있다. 나머지 연산은 나누는 수가
소수일 때 입력 해시의 하위 비트 편향에 덜 휘둘려서, 결과가 더 고르게 퍼진다.

## buckets와 entries — 두 배열로 체인을 만든다

충돌한 원소들을 어딘가에 묶어둬야 한다. 교과서적 해시테이블은 각 bucket마다 연결
리스트를 달고, 충돌이 날 때마다 노드 객체를 `new`해서 포인터로 잇는다. .NET
`Dictionary`는 이 방식을 쓰지 않는다. 노드를 따로 할당하면 원소마다 힙 객체가 하나씩
생겨 메모리 곳곳에 흩어지고, 순회할 때 포인터를 따라 캐시 미스가 연발하며, 객체 수만큼
GC 부담이 늘어난다.

대신 두 개의 배열로 같은 체인을 표현한다.

`entries`는 실제 데이터가 앞에서부터 빽빽이 차는 배열이다. 각 슬롯(`Entry`)은 네 필드를
갖는다.

```csharp
private struct Entry {
    public int hashCode;   // 키 해시 (하위 31비트)
    public int next;       // 같은 bucket의 다음 entry 인덱스 (없으면 끝 표시)
    public TKey key;
    public TValue value;
}
```

`buckets`는 정수 배열이고, `buckets[b]`에는 b번 bucket 체인의 **첫 entry 인덱스**가
들어간다. 조회는 이렇게 흐른다. 해시를 계산해 bucket 번호 b를 구하고, `buckets[b]`로
체인의 첫 entry로 진입한 뒤, 그 entry의 `hashCode`를 먼저 비교하고 같을 때만 `key`의
`Equals`를 부른다. 다르면 `entries[i].next`가 가리키는 다음 인덱스로 건너뛴다. 체인
끝에 닿을 때까지 이걸 반복한다.

여기서 hashCode를 먼저 비교하는 게 작지만 실질적인 최적화다. `Equals`는 사용자 타입이면
비쌀 수 있고, 정수 하나 비교는 싸다. 저장해 둔 hashCode가 다르면 키가 같을 리 없으니
`Equals`를 아예 부르지 않고 건너뛴다.

"충돌은 연결 리스트로 처리한다"는 흔한 설명이 형태상 틀린 건 아니다. 논리적으로는 단일
연결 리스트가 맞다. 다만 그 리스트의 노드가 개별 힙 객체가 아니라 하나의 `entries` 배열
안 슬롯이고, 포인터 대신 정수 인덱스로 이어진다는 점이 핵심 차이다. 이 덕분에 체인을
따라가도 같은 배열 안을 오가므로 캐시 지역성이 좋고, 원소를 넣을 때마다 노드를 할당하지
않으니 GC가 볼 객체도 없다.

## 인덱스가 0-기반이냐 1-기반이냐 — 버전에 따라 다른 sentinel

`buckets`와 `next`는 "여기서 끝" 또는 "빈 bucket"을 표시할 sentinel 값이 필요한데,
이 관례가 .NET 버전 사이에 바뀌었다.

구세대(.NET Framework)는 0-기반이다. `buckets`와 `next`에 실제 인덱스를 그대로 넣고,
"없음"을 -1로 표시한다. 그래서 딕셔너리를 새로 만들면 `buckets` 배열을 전부 -1로 채우는
초기화가 필요했다.

신세대(.NET Core / .NET 5 이상)는 `buckets`를 1-기반으로 바꿨다. 저장값은 실제 인덱스에
1을 더한 값이고, 0이 "빈 bucket"을 뜻한다. 이렇게 하면 배열을 새로 할당했을 때
`int`의 기본값 0이 곧바로 "비어 있음"이 되므로, -1로 다시 칠하는 순회 초기화를 건너뛸 수
있다. 그래서 최신 구현에서 `buckets[b]`를 읽으면 실제 진입 인덱스는 `buckets[b] - 1`이다.

세부 관례는 이렇게 갈리지만 두 배열로 체인을 엮는다는 뼈대는 같다. 인덱스 규칙은 구현
디테일이고, 조회·삽입·삭제 흐름을 이해하는 데는 "buckets가 첫 entry를, next가 다음
entry를 가리킨다"만 잡고 있으면 충분하다.

## 삭제가 만드는 구멍 — freeList가 next 필드를 재활용한다

`entries`는 추가 순서대로 앞에서부터 채워진다. 그런데 한가운데 있는 원소를 `Remove`하면
배열 중간에 구멍이 뚫린다. 뒤 원소들을 한 칸씩 당겨 메우면 삭제 하나가 O(n)이 되어
버리므로, 당기지 않는다. 대신 빈 슬롯을 재사용 대상으로 관리한다.

핵심은 이 재사용 목록을 위해 **별도의 리스트 객체를 두지 않는다**는 점이다. 살아 있는
entry에서 `next`는 "같은 bucket의 다음 원소"를 가리키지만, 죽은(삭제된) entry에서는 같은
`next` 필드가 "다음 빈 슬롯"을 가리키도록 재활용된다. 한 필드가 상태에 따라 두 역할을
한다. 이 빈 슬롯들이 이루는 사슬이 freeList이고, `_freeList`는 그 머리 인덱스,
`_freeCount`는 남은 빈 슬롯 수다.

삭제 로직을 풀면 이렇다. 먼저 삭제 대상을 충돌 체인에서 떼어낸다. 그 대상이 체인의
머리였으면 `buckets[b]`를 대상의 `next`로 바꿔 잇고, 중간이었으면 앞 entry의 `next`를
대상의 `next`로 이어 건너뛰게 한다. 그런 다음 대상 슬롯을 freeList의 머리에 끼운다 —
대상의 `next`를 현재 `_freeList`로 바꾸고, `_freeList`를 대상 인덱스로 갱신하고,
`_freeCount`를 하나 늘린다.

```csharp
entries[last].next = entries[i].next; // 충돌 체인에서 분리 (머리면 buckets[b]를 대신 수정)
entries[i].next = freeList;            // freeList 사슬에 끼움 (next 재활용)
freeList = i;
freeCount++;
```

삽입은 이 목록을 먼저 소비한다. `_freeCount > 0`이면 `_freeList`가 가리키는 빈 슬롯을
꺼내 쓰고, `_freeList`를 그 슬롯의 `next`로 옮긴 뒤 `_freeCount`를 하나 줄인다. 빈
슬롯이 없을 때만 `entries`의 새 자리(`count` 위치)를 쓴다. 덕분에 삭제·삽입을 반복해도
`entries` 배열은 앞쪽에 촘촘히 유지되고, 삭제가 남긴 구멍이 방치되지 않는다.

## resize는 커지기만 한다 — Clear는 용량을 반납하지 않는다

원소가 늘어 bucket이 빽빽해지면 충돌이 잦아지고 조회가 느려진다. 그래서 원소 수가 일정
수준(대략 bucket 수)에 도달하면 resize가 일어난다. 새 크기는 대략 두 배로 늘린 뒤 그보다
크거나 같은 가장 가까운 소수로 맞춘다. resize는 더 큰 `buckets`·`entries` 배열을 새로
할당하고 기존 entry들을 새 bucket 배치로 다시 흩뿌린다. 이때 bucket 수가 바뀌므로
`hashCode % buckets.Length`의 결과도 달라져, 모든 원소가 새 bucket으로 재배정된다.

`List`와 마찬가지로 이 배열은 커지기만 하고 저절로 줄지 않는다. `Clear()`는 데이터를
비울 뿐 용량을 반납하지 않는다. `Array.Clear`로 `entries`를 밀고 `buckets`를 초기화하며
`count`·`freeCount`를 0으로 되돌리지만, 배열 자체는 이전 크기 그대로 남는다.

이 성질은 재사용 패턴에서 양날이다. 매 프레임 대량으로 채웠다가 비우는 코드를 생각해
보자.

```csharp
for (int i = 0; i < 10000; i++)
    dict.Add(i, someValue);
// ...
dict.Clear();
// 다음 프레임에 또 10000개 Add, 또 Clear, 반복
```

초기 용량을 지정하지 않으면 첫 프레임에서 0부터 1만까지 채우는 동안 배열이 여러 번
재할당·재배치된다 — resize 폭풍이다. 이 비용은 `new Dictionary<int, V>(10000)`처럼 처음부터
넉넉한 용량을 잡아두면 통째로 사라진다.

그런데 `Clear()`가 용량을 반납하지 않는다는 바로 그 성질 덕분에, 같은 딕셔너리를 계속
재사용하면 두 번째 프레임부터는 이미 1만짜리 배열이 잡혀 있어 resize가 한 번도 일어나지
않는다. 즉 이 코드에서 resize 비용은 사실상 첫 프레임 한 번뿐이다. 매 프레임 반복되는
진짜 비용은 `Clear()` 자체인데, 이건 1만짜리 배열을 훑는 O(n) 작업이라 공짜는 아니지만
재할당이 아니라 memset에 가까워 새 GC 대상을 만들지는 않는다.

그래서 이런 핫 패스의 정석은 두 가지다. 딕셔너리를 프레임마다 새로 만들지 말고 필드로
들고 재사용해 객체 할당 자체를 없애고, 예상 최대 크기를 아는 경우 생성 시 초기 용량을
지정해 첫 프레임 resize까지 없앤다. `List`에서 capacity를 미리 잡아 재할당을 피하는 것과
같은 논리가, buckets·entries 두 배열을 가진 `Dictionary`에도 그대로 적용된다.
