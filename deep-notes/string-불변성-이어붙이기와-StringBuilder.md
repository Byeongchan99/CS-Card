## string은 참조 타입인데 왜 값처럼 동작하는가

C#에서 `string`은 `class`, 즉 참조 타입이다. 변수는 힙에 있는 문자열 객체를 가리키는 참조를 담을 뿐이고, 대입은 그 참조를 복사한다. 그런데도 아래 코드는 값 타입에서 기대하는 것과 똑같이 동작한다.

```csharp
string a = "hello";
string b = a;
b += " world";
Console.WriteLine(a);  // "hello"
```

`b`를 바꿨는데 `a`가 멀쩡한 이유는 두 가지가 겹쳐서다. 첫째, `string b = a`는 문자열 내용을 복사하지 않는다. 참조만 복사하므로 이 시점에는 `a`와 `b`가 힙에 있는 같은 `"hello"` 객체를 가리킨다. 둘째, `string`은 불변(immutable)이라 `+=`가 기존 객체를 수정할 수 없다. 그래서 `b += " world"`는 원본을 건드리는 대신 `"hello world"`라는 새 객체를 만들어 `b`의 참조만 거기로 갈아끼운다. `a`는 여전히 원래 `"hello"`를 가리키고 있으니 값이 유지된다.

```
string a = "hello";   a ──→ ["hello"]
string b = a;         b ──→ ["hello"]        (같은 객체, 내용 복사 아님)
b += " world";        b ──→ ["hello world"]  (새 객체)
                      a ──→ ["hello"]        (그대로)
```

핵심은 "복사"의 대상이 문자열 내용이 아니라 참조라는 점, 그리고 겉보기의 값 의미론이 복사가 아니라 불변성에서 나온다는 점이다. 값 타입이라서가 아니라, 참조 타입이지만 아무도 기존 객체를 수정할 수 없기 때문에 원본이 안전한 것이다.

## 불변성이 반복 이어붙이기에서 O(n²)가 되는 이유

불변이라는 성질은 안전하지만, 반복문에서 문자열을 계속 이어붙이면 비용으로 되돌아온다.

```csharp
string result = "";
for (int i = 0; i < 10000; i++)
{
    result += i.ToString();
}
```

이 루프는 두 종류의 할당을 매 반복 만든다. `i.ToString()`이 임시 `string`을 하나 만들고, `result += ...`가 이어붙인 결과를 담을 새 `string`을 또 하나 만든다. 반복이 10000번이니 대략 20000개의 문자열 객체가 힙에 쌓이고, 이것이 나중에 GC가 수거해야 할 쓰레기가 된다.

그런데 객체 개수(O(n))보다 더 무서운 건 총 복사량이다. `result += ...`가 새 객체를 만들 때는 그냥 만드는 게 아니라 기존 `result`의 문자를 전부 새 버퍼로 복사한 뒤 뒤에 새 문자를 붙인다. `result`의 길이는 반복이 진행될수록 계속 자라므로, 복사되는 문자 수가 반복마다 늘어난다.

```
반복 1: 길이 ~1 복사
반복 2: 길이 ~2 복사
...
반복 n: 길이 ~n 복사
총합: 1 + 2 + 3 + ... + n = O(n²)
```

객체 개수는 O(n)이지만 CPU가 실제로 옮기는 바이트 양은 O(n²)로 늘어난다. 뒤로 갈수록 한 번의 `+=`가 점점 비싸진다. 문자열이 짧을 때는 티가 안 나지만 길이가 커지면 이 제곱 항이 지배한다.

## StringBuilder가 O(n)으로 낮추는 원리 — 상환 분석

`StringBuilder`는 불변 객체를 매번 새로 만드는 대신, 내부에 변경 가능한 버퍼(`char[]`)를 하나 들고 있다. `Append`는 그 버퍼의 빈 자리에 문자를 채워 넣을 뿐이라, 대부분의 호출은 새 할당 없이 끝난다. 버퍼가 꽉 차면 그때만 더 큰 버퍼(대략 2배)를 새로 잡고 기존 문자를 옮긴다. 이 확장 전략은 `List`가 내부 배열을 2배씩 키우는 것과 완전히 같은 메커니즘이다.

여기서 흥미로운 지점이 있다. StringBuilder도 확장할 때는 "기존 문자 전체 복사"가 똑같이 일어난다. `string += ` 루프와 복사라는 행위 자체는 다르지 않다. 그런데도 전체 비용이 O(n²)가 되지 않는 이유는 복사가 일어나는 빈도에 있다. 이것은 동적 배열의 상환 분석과 동일한 논리로 설명된다.

`char`를 n개 Append하는 전체 비용을 두 부분으로 나눠 보면:

```
일반 Append:  n번 × O(1)              = O(n)
확장 시 복사:  1 + 2 + 4 + ... + n     = 등비수열 합 ≈ 2n = O(n)
합계: O(n)
```

확장은 버퍼가 꽉 찰 때만, 즉 용량이 2배가 되는 지점에서만 일어난다. 그래서 복사 비용의 합이 등차수열이 아니라 등비수열이 되고, 등비수열은 마지막 항의 상수 배로 수렴한다. 개별 Append 중 일부는 O(n) 복사가 터지지만, 전체를 n으로 나눈 상환 비용은 O(1)이다.

`string += ` 루프와 나란히 두면 차이가 선명해진다.

```
string += :      1 + 2 + 3 + ... + n   (매 반복 복사)      = O(n²)
StringBuilder:   1 + 2 + 4 + ... + n   (2배 될 때만 복사)  = O(n)
```

둘 다 복사가 일어난다는 사실은 같다. 갈리는 것은 언제 복사하느냐다. `string`은 불변이라 매 반복 전체 복사가 강제된다 — 선택지가 없다. StringBuilder는 가변 버퍼 덕에 버퍼가 꽉 찰 때만 복사하고, 그 간격이 기하급수적으로 벌어진다. 복사 빈도가 산술적이냐 기하급수적이냐의 차이가 그대로 등차수열 합과 등비수열 합의 차이로, 즉 O(n²)와 O(n)의 차이로 나타난다. 같은 복사라도 얼마나 자주 하느냐가 복잡도를 바꾼다.

## 실무에서의 판단 기준

게임 코드에서 이 차이가 문제가 되는 곳은 정해져 있다. 루프 안에서, 특히 매 프레임 돌 수 있는 경로에서 문자열을 반복적으로 이어붙일 때다. 디버그 로그를 한 줄씩 누적하거나, UI 텍스트를 여러 조각으로 조립하거나, 직렬화 문자열을 만드는 경우가 대표적이다. 이럴 때는 `StringBuilder`를 쓰고, 최종 길이를 대략 알면 생성자나 `EnsureCapacity`로 초기 용량을 미리 잡아 확장 자체를 없애는 것이 정석이다. 초기 용량을 잡아두면 등비수열 합의 복사마저 사라진다.

반대로 몇 개 안 되는 조각을 한 번 합치는 경우라면 `StringBuilder`가 오히려 과하다. 조각 수가 고정되어 있으면 문자열 보간(`$"{a}{b}"`)이나 `string.Concat`, `string.Join`이 더 읽기 쉽고 내부적으로 필요한 크기를 한 번에 계산해 할당도 한 번으로 끝낸다. 판단 기준은 "이어붙이는 횟수가 루프에 의해 커지는가"다. 커지면 StringBuilder, 고정이면 보간이나 Concat이 맞다.

한 가지 흔한 오해는 `string += `가 항상 나쁘다는 것이다. 반복 횟수가 상수이고 작으면 새 객체 몇 개는 무시할 만하다. 문제는 반복 횟수가 입력 크기에 비례해 커질 때 O(n²)가 드러나는 것이지, 이어붙이기 연산 자체가 죄는 아니다.
