## 같은 것을 여러 벌 들고 있는 것이 문제다

숲 맵에 나무 10만 그루를 배치한다고 하자. 가장 단순한 구현은 나무 객체 하나가 자기 모델, 텍스처, 위치, 회전, 크기, 색조를 모두 들고 있는 것이다. 이 구조에서 나무 10만 그루가 전부 소나무라면, 수천 개 정점짜리 소나무 메시가 논리적으로 10만 번 등장한다. 그런데 이 10만 벌의 메시는 서로 한 바이트도 다르지 않다.

경량(Flyweight) 패턴은 이 낭비를 겨냥한다. 많은 객체가 똑같은 데이터를 각자 들고 있을 때, 그 데이터를 한 곳에 두고 객체들이 가리키게 만든다. 이름의 "경량"은 개별 객체가 가벼워진다는 뜻이다. 무거운 부분을 공유 객체로 빼냈기 때문이다.

```csharp
// 적용 전: 나무마다 모든 것을 들고 있다
class Tree
{
    Mesh mesh; Texture bark; Texture leaves;
    Vector3 position; Quaternion rotation; float scale; Color tint;
}

// 적용 후: 공유할 것과 개별로 둘 것을 분리한다
class TreeType   // 종류당 하나
{
    Mesh mesh; Texture bark; Texture leaves;
}

class Tree       // 나무마다 하나
{
    TreeType type;
    Vector3 position; Quaternion rotation; float scale; Color tint;
}
```

## 나누는 기준은 "모두가 쓰는가"가 아니라 "맥락에 따라 달라지는가"다

직관적으로는 "모든 나무가 쓰는 건 공유, 나무마다 다른 건 개별"이라고 말하기 쉽다. 이 설명은 나무 종류가 하나일 때만 맞는다. 소나무, 참나무, 자작나무가 섞이는 순간 모델과 텍스처는 더 이상 모든 나무가 쓰는 것이 아니다. 그래도 모델과 텍스처는 여전히 공유 대상이다.

진짜 기준은 그 값이 객체가 놓인 맥락, 즉 어디에 어떻게 배치되었는지에 따라 달라지는가이다. 소나무 메시는 그 소나무가 언덕 위에 있든 강가에 있든 똑같다. 반면 위치, 회전, 크기, 색조는 바로 그 배치 맥락 자체다. 앞쪽을 내재 상태(intrinsic state), 뒤쪽을 외재 상태(extrinsic state)라고 부른다.

이 기준을 적용하면 공유 단위가 자연스럽게 "전체"가 아니라 "종류"가 된다. 나무가 10만 그루든 100만 그루든 `TreeType`은 종류 수만큼, 이 예에서는 3개만 존재한다. 실무에서는 보통 종류 이름이나 ID를 키로 `TreeType`을 캐싱해 두고, 이미 있으면 재사용하고 없을 때만 만드는 팩토리를 둔다.

내재 상태는 여러 객체가 동시에 가리키므로 사실상 불변이어야 한다. 한 나무를 위해 공유 객체를 고치면 같은 종류의 모든 나무가 함께 바뀐다. 이 성질이 뒤에서 유니티 머티리얼 문제와 그대로 이어진다.

## 참조만 묶으면 아끼는 것은 참조 크기뿐이다

위 예제를 C#으로 읽으면 한 가지가 걸린다. `Mesh`와 `Texture`는 참조 타입이다. 적용 전 구조에서도 10만 개의 `Tree`가 같은 소나무 메시 에셋을 할당받았다면, 정점 데이터는 이미 메모리에 한 벌뿐이다. 필드에 들어 있는 것은 데이터가 아니라 그 데이터를 가리키는 참조다.

그렇다면 `TreeType`으로 묶어서 실제로 줄어드는 것은 나무 하나당 참조 개수다. 메시, 껍질, 잎 참조 3개가 `TreeType` 참조 1개로 바뀐다. 64비트 환경에서 참조 하나는 8바이트이므로 나무당 16바이트, 10만 그루면 1.6MB 남짓이다. 없는 것보다는 낫지만 "경량 패턴으로 메모리를 크게 줄였다"고 부를 만한 수치는 아니다.

```text
적용 전  Tree 1개 = [mesh 참조 8B][bark 참조 8B][leaves 참조 8B][외재 상태...]
적용 후  Tree 1개 = [type 참조 8B][외재 상태...]
절약     (3 - 1) x 8B x 100,000 ≈ 1.6MB
```

경량 패턴이 극적인 효과를 내는 조건은 두 가지가 동시에 성립할 때다. 내재 상태가 커야 하고, 그 내재 상태가 인스턴스마다 실제로 복사되어 여러 벌 존재해야 한다. 값 타입으로 큰 데이터를 필드에 들고 있거나, 인스턴스마다 사본을 새로 만들어 쥐고 있는 경우가 여기에 해당한다. 크기만 크고 이미 참조로 공유되고 있다면 줄일 것이 없다. 이 차이를 구분하지 못하면 경량 패턴의 효과를 과대평가하게 된다.

## 유니티에서 공유가 깨지는 순간: Renderer의 material 프로퍼티

유니티는 기본적으로 경량 패턴 위에서 돌아간다. 프리팹 인스턴스 10만 개가 같은 메시와 같은 머티리얼 에셋을 쓰도록 되어 있으면, 그 무거운 데이터는 한 벌씩만 존재하고 렌더러들은 그것을 가리킬 뿐이다. 앞 절의 표현을 빌리면, 복사가 일어나지 않고 있으므로 이미 이득을 보고 있는 상태다.

문제는 이 공유를 스크립트 한 줄이 조용히 깨뜨릴 수 있다는 점이다.

```csharp
void Start()
{
    // 나무마다 색조를 다르게 주려는 의도
    GetComponent<Renderer>().material.color = RandomTint();
}
```

`Renderer.material` 게터는 처음 접근될 때 공유 머티리얼을 복제하고, 그 사본을 이 렌더러에 다시 할당한 뒤 사본을 돌려준다. 10만 그루 모두에서 이 코드가 돌면 머티리얼 사본이 10만 개 생긴다. 경량 패턴의 언어로 말하면, 외재 상태인 색조 하나를 내재 상태인 머티리얼 안에 넣으려 했기 때문에 내재 상태 전체가 인스턴스 수만큼 복사된 것이다. 앞 절에서 말한 "큰 데이터가 인스턴스마다 복사되는" 조건을 스스로 만들어 낸 셈이다.

비용은 메모리에서 끝나지 않는다. 이렇게 만들어진 사본은 에셋처럼 취급되어 GameObject를 `Destroy`해도 함께 해제되지 않는다. 필요 없어진 사본을 직접 `Destroy`하는 것은 사용자의 책임이고, 한꺼번에 정리할 때는 `Resources.UnloadUnusedAssets`가 참조가 끊긴 사본을 회수한다. 또 렌더러마다 머티리얼이 달라지므로 같은 머티리얼을 전제로 하는 배칭과 GPU 인스턴싱이 더 이상 이 나무들을 한데 묶지 못한다.

반대로 `sharedMaterial.color`를 바꾸면 사본은 생기지 않지만, 공유 객체를 고친 것이므로 그 머티리얼을 쓰는 모든 나무의 색이 한꺼번에 바뀐다. 에디터 플레이 모드에서는 에셋 자체가 바뀐 채로 남는다. 내재 상태는 불변이어야 한다는 원칙을 어긴 결과다.

올바른 방향은 공유 머티리얼은 건드리지 않고 색조를 외재 상태로 따로 넘기는 것이다. 다만 그 방법은 렌더 파이프라인에 따라 갈린다. Built-in 파이프라인에서는 `MaterialPropertyBlock`으로 렌더러별 값을 넘기는 것이 표준적인 방법이다. URP나 HDRP 같은 SRP에서는 `MaterialPropertyBlock`이 해당 렌더러의 SRP Batcher 호환성을 없애므로 오히려 성능이 떨어질 수 있다. 이 경우 유니티 문서는 속성 값별로 다른 머티리얼을 쓰라고 안내한다. 색조를 몇 단계로 양자화해 머티리얼 변형 몇 개로 나누면 사본이 10만 개가 아니라 몇 개로 끝난다. 똑같은 메시를 정말 대량으로 그린다면 GPU 인스턴싱 경로를 택하고 인스턴스별 데이터로 색조를 넘기는 방법도 있다.

## 극단까지 밀면: 외재 상태를 객체가 아니라 배열로 든다

경량 패턴을 적용한 뒤에도 `Tree` 객체 10만 개는 남는다. 각 객체는 `TreeType` 참조와 외재 상태를 들고 있을 뿐이다. 그렇다면 `Tree`라는 객체 껍데기 자체를 없애고, 외재 상태를 종류별 배열로만 들고 있다가 `TreeType`이 한 번에 그리게 할 수도 있다.

```csharp
class TreeType
{
    Mesh mesh;
    Material material;          // GPU 인스턴싱을 켠 공유 머티리얼

    Matrix4x4[] transforms;     // 이 종류 나무들의 위치·회전·크기
    Vector4[] tints;            // 색조

    // Graphics.RenderMeshInstanced 로 배열을 통째로 넘겨 그린다
    void Draw() { }
}
```

얻는 것은 크게 세 가지다. 첫째, 10만 개의 관리 객체가 몇 개의 배열로 바뀌므로 객체마다 붙던 헤더와 참조가 사라지고, GC가 추적해야 할 객체 수가 극적으로 줄어든다. 둘째, 외재 상태가 연속 메모리에 나란히 놓이므로 순회할 때 캐시 지역성이 좋아진다. 셋째, 이 배열은 인스턴싱 드로우가 받는 입력 형태 그대로여서, 나무마다 데이터를 모아 GPU로 넘기는 중간 과정이 없어진다.

잃는 것은 "나무 하나"라는 정체성이다. 개체는 이제 배열 인덱스로만 존재한다. 중간 나무를 지울 때 마지막 원소를 그 자리로 옮기는 방식을 쓰면, 바깥에서 들고 있던 인덱스가 다른 나무를 가리키게 된다. 그래서 인덱스 대신 별도의 핸들이나 세대 번호를 두는 장치가 필요해진다. GameObject가 없으니 나무별 콜라이더, 컴포넌트, 엔진이 렌더러 단위로 해 주던 컬링도 사라져 직접 구현해야 한다. 또 한 번의 인스턴싱 드로우에 담을 수 있는 인스턴스 수에는 상한이 있어서(인스턴스당 데이터 크기에 따라 달라진다) 큰 배열은 여러 번에 나눠 그린다.

이 방향은 객체 대신 데이터 배열을 중심에 두는 데이터 지향 설계와 맞닿아 있고, 유니티의 ECS가 같은 발상을 대규모로 밀어붙인 것이다. 나무처럼 행동이 거의 없고 수가 압도적으로 많은 대상은 이 구조가 잘 맞고, 개체마다 복잡한 행동과 상호작용이 필요한 대상은 객체 구조가 여전히 편하다.

## 면접에서 한 번에 말하기

경량 패턴은 대량의 객체가 똑같은 데이터를 각자 들고 있을 때, 맥락과 무관한 내재 상태를 종류당 하나의 공유 객체로 빼내고 인스턴스에는 맥락에 따라 달라지는 외재 상태만 남기는 패턴이다. 효과는 내재 상태가 인스턴스마다 실제로 복사되고 있었을 때 크고, 이미 참조로 공유되고 있었다면 참조 크기만큼만 준다. 유니티에서는 메시와 머티리얼 공유가 기본으로 이 패턴을 따르며, `Renderer.material` 접근처럼 외재 상태를 내재 상태 안에 넣는 실수가 인스턴스 수만큼의 사본을 만들어 공유를 깨뜨린다.
