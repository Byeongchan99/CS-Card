## 왜 상태 패턴을 쓰는가

`enum` + `switch` FSM의 진짜 문제는 흔히 말하는 "코드가 길어진다"가 아니다. 길이는 증상이고, 원인은 상태의 수명 주기를 표현할 자리가 없다는 것이다.

상태에는 세 개의 시점이 있다. 들어갈 때 한 번(초기화), 머무는 동안 매 프레임(행동), 나갈 때 한 번(정리). `switch` 버전은 이 중 가운데 것만 자연스럽게 표현한다. `case Attack:` 블록은 "공격 중일 때 매 프레임 할 일"이지, "공격에 들어가는 순간 할 일"이 아니다.

그래서 콤보 카운터 초기화나 히트박스 활성화 같은 코드는 갈 곳이 없어지고, 전이가 일어나는 모든 지점에 손으로 복사된다.

```csharp
// switch 버전 — 진입 처리가 전이 지점마다 흩어진다
if (Input.GetButtonDown("Attack"))
{
    _state = State.Attack;
    _comboCount = 0;        // 이 두 줄을
    _hitbox.enabled = true; // Attack으로 가는 모든 곳에 써야 한다
}
// ... 다른 상태에서도, 또 다른 상태에서도 반복
```

진입 경로가 5개면 5곳에 있어야 하고, 6번째 경로를 추가한 사람이 한 줄을 빠뜨리면 "특정 경로로 공격에 들어갔을 때만 히트박스가 안 켜지는" 버그가 된다. 재현 조건이 좁아 QA에서 잘 안 걸리고, 원인은 공격 코드가 아니라 전이 코드에 있어서 디버깅도 어렵다.

상태 패턴은 이걸 구조적으로 봉인한다.

```csharp
public interface ICharacterState
{
    void Enter();
    void Update();
    void Exit();
}

public class StateMachine
{
    private ICharacterState _current;

    public void ChangeState(ICharacterState next)
    {
        _current?.Exit();
        _current = next;
        _current.Enter();
    }
}
```

전이가 `ChangeState` 한 곳을 통과하도록 강제되므로, `Enter`/`Exit`는 누가 어디서 부르든 반드시 정확히 한 번씩 실행된다. OCP니 SRP니 하는 명분보다 이게 훨씬 실질적인 이득이다. 클래스가 늘어나는 비용을 내고 사는 것은 "구조적 우아함"이 아니라 누락 불가능성이다.

잃는 것 중 런타임 비용도 언급할 가치가 있다. `switch`는 점프 테이블 한 번이지만 상태 패턴은 인터페이스 디스패치(가상 호출)다. 캐릭터 하나당으로는 무의미한 차이지만, 수천 개 유닛이 각자 FSM을 돌리는 RTS/오토배틀러에서는 캐시 미스와 함께 유의미해진다. 이 규모에서는 애초에 OOP FSM을 버리고 DOTS 같은 데이터 지향 구조로 간다.

## OCP는 제거되는 게 아니라 국소화된다

"상태 패턴을 쓰면 새 상태 추가 시 기존 코드를 안 고쳐도 된다"는 흔한 설명은 절반만 맞다.

어떤 상태로 들어오는 진입 전이가 하나도 없으면 그 상태는 도달 불가능하다. 쓸모 있는 상태는 반드시 최소 하나의 진입 전이를 갖고, 그 조건은 어딘가 기존 상태 안에 쓰여야 한다. 그러니 "기존 코드를 안 고치는 상태 추가"는 존재하지 않는다.

정확히 말하면 이렇다. 수정해야 할 파일 수가 전체 상태 수에 비례하던 것이, 새 상태의 진입 전이 수에 비례하도록 줄어든 것이다. 상태 20개짜리 보스에 새 패턴을 추가할 때, Idle에서만 들어갈 수 있다면 파일 하나만 열면 된다. `switch` 버전은 상태가 20개든 100개든 매번 같은 거대 블록을 연다.

그리고 OCP가 무조건 성립하는 축은 따로 있다. 기존 상태의 행동 변경이다. Move의 가속도 계산을 아무리 뜯어고쳐도 다른 상태 파일은 열 필요가 없다. 상태 패턴의 SRP는 여기서 확실하게 값을 한다.

## 전역 전이 — 중복을 없애면서 국소적 추론을 잃는다

피격, 사망, 스턴, 컷신 진입은 거의 모든 상태에서 발동한다. 이걸 상태별로 구현하면 N개 파일에 같은 코드가 복사되고, 상태를 추가할 때마다 "피격 체크 넣는 걸 잊지 마라"는 암묵적 의무가 생긴다. 이 의무는 반드시 잊힌다.

해법은 상태 머신의 공통 단계로 올리는 것이다.

```csharp
public void Update()
{
    // 전역 전이 — 어떤 상태에 있든 먼저 검사
    if (_health.IsDead)      { ChangeState(_deadState); return; }
    if (_damageQueue.HasHit) { ChangeState(_hitState);  return; }

    _current.Update();
}
```

대신 규칙 하나가 깨진다. 이전에는 "이 상태에서 나가는 모든 길을 알고 싶으면 그 상태 파일만 읽으면 된다"가 성립했다. 이제는 어떤 상태 파일을 끝까지 읽어도 탈출 경로 전체를 알 수 없고, 반드시 상태 머신 파일을 같이 읽어야 한다. 국소적으로 완결된 추론이 불가능해졌다는 것이 정확한 비용이다.

주의할 점은 이게 "전이가 흩어졌다"는 뜻이 아니라는 것이다. 상태 패턴은 원래부터 전이가 파일마다 흩어져 있었다. 새로 생긴 손해는 흩어지는 규칙이 두 종류로 이중화된 것이다.

## 전역 전이의 예외 — 밀어 넣기(push)와 물어보기(pull)

전역 전이를 넣으면 곧바로 예외가 필요해진다. 대시 중 무적, 경직 중 재피격 억제, 컷신 중 조작 무시 등이다.

첫 번째 발상은 보통 플래그다. 상태가 `Enter`에서 켜고 `Exit`에서 끄고, 머신이 그 값을 본다.

```csharp
// push — 상태가 머신의 필드를 갱신한다
public class DashState : ICharacterState
{
    public void Enter() { _machine.IsInvincible = true; }
    public void Exit()  { _machine.IsInvincible = false; }
}
```

작동은 하지만 동기화 대상이 생긴다. `Exit()`이 호출되지 않고 상태가 리셋되는 경로 — 사망 처리, 컷신 강제 진입, 오브젝트 풀 반환 후 재사용, 씬 전환 — 가 하나라도 있으면 플래그가 켜진 채 남는다. 결과는 영구 무적이고, 원인은 대시 코드에 없다. 값과 실제 상태가 따로 노는 이 구조는 [[네이티브 객체의 생존 여부를 C# bool로 캐싱할 때의 함정]]과 정확히 같은 종류의 버그다.

두 번째 발상은 머신이 현재 상태에게 물어보는 것이다.

```csharp
// pull — 상태가 값을 소유하고, 머신이 매 프레임 조회한다
public class DashState : ICharacterState
{
    private float _elapsed;

    // 선딜 0.05초는 맞고, 이후 0.2초만 무적
    public bool CanBeHit => _elapsed < 0.05f || _elapsed >= 0.25f;
}
```

동기화할 필드가 없으니 desync가 구조적으로 불가능하다. 게다가 이 형태라야 상태 단위보다 세밀한 해상도를 표현할 수 있다. 실제 액션 게임의 i-frame은 대시 전체가 아니라 대시의 일부 구간이고, `Enter`/`Exit`에서 켜고 끄는 값으로는 애초에 표현이 안 된다.

기본값을 두어 "새 상태가 아무것도 신경 쓰지 않아도 되게" 만드는 것도 중요하다. C# 8의 기본 인터페이스 멤버는 Unity 2021.2부터 지원되므로 Unity 6에서는 쓸 수 있지만, API 호환성 레벨에 따라 걸리는 경우가 있어 실무에서는 추상 클래스의 `virtual` 프로퍼티로 두는 쪽이 무난하다.

```csharp
public abstract class CharacterStateBase
{
    public virtual bool CanBeHit => true;      // 새 상태는 신경 쓸 필요 없음
    public virtual bool CanBeInterrupted => true;
}
```

마지막으로 개념 분리. 대시의 무적("판정이 안 맞는다")과 경직 중 재피격 억제("맞긴 맞는데 상태 전이를 다시 안 한다")는 다른 것이다. 후자는 데미지는 들어가고 애니메이션만 리셋 안 되는 설계가 흔하다. `bool` 하나에 둘을 얹으면 반드시 나중에 갈라진다.

## 극한 — 전이와 행동의 분리

전역 전이가 계속 쌓이면 상태 머신에는 "조건 + 가드 + 목적지"의 목록이 남고, 상태 클래스에는 행동만 남는다. 전이 판단은 다시 한 곳으로 모인다.

이게 `switch`로의 회귀처럼 보이지만 결정적 차이가 있다. `switch` 버전은 전이와 행동이 둘 다 한 파일에 있었고, 최종 형태는 전이만 중앙에 있고 행동은 분산되어 있다. 파일 크기 증가가 전이 수에만 비례하고 행동 복잡도에는 비례하지 않는다.

그리고 중앙의 전이를 `if` 나열이 아니라 데이터로 표현하면 성질이 또 한 번 바뀐다.

```csharp
// 전이 테이블 — 전이 추가가 코드 수정이 아니라 데이터 추가가 된다
_transitions.Add(new Transition(
    from: typeof(MoveState),
    to:   typeof(DashState),
    condition: () => Input.GetKeyDown(KeyCode.LeftShift) && _stamina >= 20f));

_transitions.AddAny(                       // from 없음 = 전역 전이
    to: typeof(HitState),
    condition: () => _damageQueue.HasHit,
    guard: s => s.CanBeHit);
```

이제 전이 추가에 기존 코드 수정이 필요 없다. OCP가 이번엔 진짜로 성립한다. 대가는 전이가 컴파일 타임에 검증되지 않는다는 것 — 오타나 도달 불가능한 상태를 컴파일러가 잡아주지 못하므로, 에디터 툴이나 초기화 시점의 검증 코드가 필요해진다.

Unity의 Animator가 정확히 이 구조다. 노드는 애니메이션(행동), 화살표는 전이 데이터, `Any State`는 전역 전이, 전이에 걸린 Condition은 가드다. Mecanim을 써봤다면 이미 이 아키텍처를 쓴 것이다. 다만 Animator를 게임 로직 FSM으로 전용하는 건 별개 문제로, 전이가 프레임 지연을 갖고 파라미터 문자열이 타입 안전하지 않아 실무에서는 로직 FSM을 따로 두는 편이 일반적이다.

## 실무에서의 선택 기준

상태 3~4개에 전이가 단순하면 `enum` + `switch`가 정답이다. UI 버튼, 간단한 문 개폐, 아이템 픽업에 상태 패턴을 쓰는 건 오버엔지니어링이다.

플레이어 캐릭터나 보스처럼 상태가 5개를 넘고 각 상태가 진입/탈출 처리를 갖는다면 상태 패턴으로 간다. 여기서 상태 객체는 매 전이마다 `new` 하지 말고 미리 만들어 캐싱해야 한다. 매 프레임 전이가 일어날 수 있는 구조에서 상태 객체를 새로 만들면 그대로 GC 압력이 되고, 이는 [[GC 스파이크와 프레임 예산]]에서 다룬 문제와 직결된다.

전역 전이가 3개를 넘거나 전이 규칙 자체를 기획자가 만지게 하고 싶어지면 전이 테이블로 간다. 상태 안에 다시 하위 상태가 필요해지면(공격 상태 안의 1타/2타/3타) 계층형 FSM으로, 조건 판단이 우선순위와 트리 탐색을 요구할 만큼 복잡해지면 비헤이비어 트리로 넘어가는 것이 일반적인 진행 경로다.
