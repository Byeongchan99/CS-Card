## 싱글턴은 전역 함수 모음이 아니라 전역에서 닿는 객체 하나다

게임에는 "하나만 있어야 하고 어디서든 접근해야 하는" 것이 많다. 게임 상태, 오디오, 세이브, 입력 같은 매니저들이다. 가장 단순한 해법은 모든 멤버를 static으로 둔 static 클래스다. 싱글턴은 같은 목적을 "인스턴스를 하나만 만들고 그것을 static 손잡이(`Instance`)로 노출한다"는 방식으로 푼다.

둘의 차이는 객체가 있느냐 없느냐에서 나온다. C#의 static 클래스는 abstract sealed로 컴파일되어 인스턴스를 만들 수 없고, `object` 외의 클래스를 상속할 수 없으며, 인터페이스도 구현할 수 없다. 객체가 없으니 인자로 넘길 수도 없다. 싱글턴은 객체이므로 인터페이스를 구현해 다형적으로 다룰 수 있고, 참조로 넘겨 주입할 수 있고, 다른 클래스를 상속할 수 있다. 유니티에서는 MonoBehaviour를 상속해 컴포넌트가 될 수 있다는 점이 특히 크다. [[싱글턴이 static 클래스로는 얻을 수 없는 것과 그 차이가 생기는 이유]]

그리고 객체이기 때문에 언제 만들고, 언제 바꾸고, 언제 없앨지를 코드가 정할 수 있다. 상태가 없는 유틸리티(수학 함수, 확장 메서드)에는 static 클래스가 맞고, 상태를 들고 교체·주입이 필요할 때 싱글턴이 의미가 있다.

## static 클래스의 초기화는 한 번뿐이라 리셋이 따로 필요하다

static 클래스의 정적 생성자는 CLR이 그 타입의 정적 멤버에 처음 접근하기 직전에 실행하고, 한 AppDomain 안에서는 다시 실행되지 않는다. 개발자가 다시 호출할 방법이 없으므로 "새 게임"을 하려면 별도의 `Reset()`이 필요하고, 초기값을 정적 생성자와 Reset 양쪽에 중복해 적어야 한다. 상태 필드가 30개로 늘고 팀원이 계속 추가하면 Reset에 새 필드를 빠뜨리는 실수가 반드시 생긴다.

싱글턴은 `Instance = new GameState()` 한 줄로 리셋된다. 새 객체를 만드는 과정에서 필드 초기화 식 전체가 다시 적용되므로 누락이 구조적으로 사라진다. 초기화 코드가 "다시 부를 수 없는 정적 생성자"에 있느냐, "몇 번이든 반복할 수 있는 인스턴스 생성"에 있느냐의 차이다. [[정적 생성자의 실행 시점과 새 게임 리셋에서 static 클래스와 싱글턴의 차이]]

## 교체로 리셋하면 캐싱된 참조가 조용히 갈라진다

교체 방식의 대가는 이전 인스턴스를 들고 있는 쪽이다.

```
StartNewGame 이전:  Instance ──▶ [GameState#1 Gold=340] ◀── GoldHUD._state
StartNewGame 이후:  Instance ──▶ [GameState#2 Gold=100→50]
                                 [GameState#1 Gold=340] ◀── GoldHUD._state (계속 생존)
```

HUD가 `Awake`에서 참조를 받아 두었다면 교체 후에도 이전 객체를 계속 읽는다. 로직은 새 객체를 바꾸고 화면은 옛 값을 보여 주는데, 예외는 전혀 나지 않는다. 순수 C# 객체에는 "파괴됨"이라는 상태가 존재하지 않기 때문이다. GC가 아는 생사는 도달 가능성 하나뿐이고, HUD가 붙잡고 있으니 이전 객체는 GC 기준으로 멀쩡히 살아 있다. "이제 쓰면 안 된다"는 것은 프로그래머 머릿속의 약속일 뿐 런타임은 알 방법이 없다. 유니티 오브젝트가 파괴되면 엔진이 네이티브 쪽에 그 사실을 기록하고 오버로딩된 `==`가 확인해 주는 것과 대조적이다.

해결은 세 방향이다. 참조를 캐싱하지 않고 매번 `Instance`로 접근하거나, 교체 시 이벤트를 발행해 구독자가 새 인스턴스를 다시 받게 하거나, 인스턴스를 고정하고 내부 상태만 리셋한다. 마지막은 누락 위험이 돌아오므로 상태를 내부 데이터 객체 하나로 묶어 그것만 교체하는 절충을 쓰기도 한다. [[싱글턴 인스턴스를 교체하면 이전 참조를 캐싱한 쪽에 생기는 일]]

## 테스트를 막는 것은 유일성이 아니라 전역 접근이다

싱글턴 비판에서 가장 자주 나오는 것은 테스트 문제다. `Shop.Buy`가 내부에서 `GameState.Instance.Gold`를 직접 읽으면 세 가지가 막힌다. 생성자와 setter가 private이라 테스트용 상태를 따로 만들 수 없고, static 상태가 테스트 사이에 새어 실행 순서에 따라 결과가 바뀌며, `Buy(int price)`라는 시그니처만 봐서는 GameState에 의존한다는 사실이 드러나지 않는다. 마지막 것을 숨은 의존성이라고 한다.

해결은 `Shop`이 필요한 것을 인터페이스로 받는 것이다. 인터페이스는 `Shop`이 실제로 쓰는 것만 담도록 좁게 잡아야 가짜가 가벼워진다(인터페이스 분리 원칙).

```csharp
public interface IWallet { int Gold { get; set; } }

public class Shop
{
    private readonly IWallet _wallet;
    public Shop(IWallet wallet) { _wallet = wallet; }

    // 잔액이 충분하면 차감하고 true를 돌려준다
    public bool Buy(int price)
    {
        if (_wallet.Gold < price) return false;
        _wallet.Gold -= price;
        return true;
    }
}

// 게임: new Shop(GameState.Instance)   테스트: new Shop(new FakeWallet(30))
```

[[Instance를 직접 참조하는 코드가 유닛 테스트하기 어려운 이유와 생성자 주입]]

이 구조에서도 게임 안의 GameState는 여전히 하나뿐이다. 유일성은 그대로인데 테스트 문제가 사라졌으니 원인은 유일성이 아니라 `Shop`이 고정된 전역 지점에 스스로 손을 뻗는 결합이었다. `GameState.Instance`라는 이름은 소비자 내부에서 사라지고 조립하는 쪽 한 곳으로 모인다. 유일성은 조립하는 쪽이 하나만 만들어 나눠 주는 방식으로 관리하면 되므로 전역 접근과 묶일 필요가 없다. private 생성자처럼 유일성을 강제하는 장치는 구체 타입을 주입받을 때 2차 장애물이 되지만, 인터페이스로 받으면 우회된다. [[의존성 주입은 싱글턴의 유일성과 전역 접근 중 무엇을 제거하는가]]

## 서비스 로케이터는 전역 접근의 위치만 옮긴다

`Services.Get<IWallet>()`처럼 static 저장소에서 꺼내 쓰는 서비스 로케이터는 겉보기엔 주입과 비슷하다. 구현체를 갈아 끼울 수 있으니 테스트 상태를 만드는 문제는 해결된다. 하지만 저장소가 static이라 등록을 빠뜨린 테스트가 앞 테스트의 가짜를 그대로 꺼내 쓰는 오염이 남고, 시그니처는 여전히 의존을 숨긴다. 더 나빠진 점도 있다. 생성자 주입은 인자를 빠뜨리면 컴파일 에러인데, 서비스 로케이터는 등록을 빠뜨려도 컴파일되고 `Get` 시점에 런타임 예외로 터진다.

의존성을 밖에서 넣어 준 것이 아니라 전역 저장소에서 꺼내 오도록 바꾼 것일 뿐이다. 그래도 기존 싱글턴 코드를 조금만 고쳐 교체 가능성을 얻을 수 있어 레거시 전환 단계에서는 쓸모가 있다. [[서비스 로케이터가 해결하는 테스트 문제와 그대로 남기는 문제]]

MonoBehaviour는 생성자를 쓸 수 없으므로 유니티에서는 Inspector 참조 연결, 초기화 메서드 호출, 또는 VContainer나 Zenject 같은 DI 프레임워크로 생성자 주입과 같은 구조를 만든다.
