## 블로킹 루프는 프레임을 하나도 끝내지 못한다

게임의 모든 객체는 같은 시간을 공유한다. 해골은 순찰하고, 플레이어는 입력을 받고, 화면은 초당 수십 번 다시 그려져야 한다. 메인 게임 루프는 이 일들을 한 프레임 안에 순서대로 처리하고 다음 프레임으로 넘어가는 구조다.

```csharp
while (gameRunning)
{
    ProcessInput();
    UpdateAllObjects();   // 이 안에서 Patrol()을 호출한다면?
    Render();
}
```

순찰을 직관적으로 `while (true)` 안의 두 `for`문으로 작성하면 이 구조가 무너진다. 문제는 해골이 너무 빨리 움직인다는 것이 아니다. `Patrol()`이 영원히 반환하지 않는다는 것이 문제다. 같은 스레드에서 호출되었다면 제어권이 게임 루프로 돌아가지 않으므로 다음 일이 벌어진다.

- 이번 프레임에서 `Patrol()` 뒤에 갱신될 객체들은 실행되지 않는다.
- `Render()`는 다시 호출되지 않는다.
- 다음 프레임의 입력 처리도 일어나지 않는다.

`SetX()`가 내부 좌표를 수없이 바꿔도 그 변화를 화면에 옮길 렌더링이 오지 않는다. 플레이어에게는 마지막 프레임에서 굳어 버린 화면만 보인다. 창 메시지 처리도 멈추므로 OS는 이 창을 응답 없음으로 표시한다.

이동 속도 문제는 그다음 단계의 문제다. 루프가 프레임마다 제어권을 돌려주게 만든 뒤에야 "한 프레임에 얼마나 움직이는가"라는 질문이 의미를 갖는다. 그 답이 `Time.deltaTime`이다.

## 실행 위치에 숨어 있던 상태를 필드로 꺼내야 한다

업데이트 메서드 패턴의 해법은 간단하다. 각 객체가 "한 프레임 분량만 진행하는" `Update()`를 갖고, 게임 루프는 매 프레임 모든 객체의 `Update()`를 한 번씩 호출한다. 어려운 부분은 다른 데 있다. 원래 코드에서 공짜로 얻던 상태를 직접 관리해야 한다는 점이다.

원래 코드에는 방향 변수가 없다. "지금 오른쪽으로 가는 중"이라는 정보는 프로그램이 현재 어느 `for`문을 실행하고 있는가에 담겨 있었다. 즉 명령어 포인터, 다시 말해 실행 위치 자체가 상태였다. 위치 `x` 역시 `Patrol()` 호출의 스택 프레임에 있는 지역 변수였다. 함수가 반환되지 않았기 때문에 이 두 상태는 계속 유지될 수 있었다.

`Update()`는 매 프레임 반환한다. 반환하는 순간 스택 프레임이 사라지므로, 지역 변수로 둔 위치와 방향은 매 호출마다 초기값에서 다시 시작한다. 그러면 해골은 초기 위치에서 한 칸 이동했다가 다음 프레임에 다시 초기화되기를 반복하며 사실상 고정된다. 그래서 두 상태를 모두 객체의 필드로 옮겨야 한다.

```csharp
public class SkeletonPatrol : MonoBehaviour
{
    [Header("Patrol")]
    [SerializeField] private float _speed = 5f;
    [SerializeField] private float _minX = 0f;
    [SerializeField] private float _maxX = 100f;

    // 프레임 사이에 살아남아야 하는 상태. 원래는 스택과 실행 위치에 있었다.
    private float _x;
    private bool _movingRight = true;

    // 매 프레임 순찰을 한 조각만큼 진행한다
    private void Update()
    {
        float step = _speed * Time.deltaTime;

        if (_movingRight)
        {
            _x += step;
            if (_x >= _maxX) { _x = _maxX; _movingRight = false; }
        }
        else
        {
            _x -= step;
            if (_x <= _minX) { _x = _minX; _movingRight = true; }
        }

        Vector3 p = transform.position;
        transform.position = new Vector3(_x, p.y, p.z);
    }
}
```

`_movingRight`가 바로 사라졌던 실행 위치를 데이터로 바꾼 것이다. 동작이 더 복잡해지면, 예를 들어 순찰하다 멈춰서 두리번거리고 다시 순찰하는 경우라면 이 bool은 enum이 되고 결국 상태 머신이 된다. 업데이트 메서드로 쪼갠 동작이 FSM이나 [[enum과 switch 기반 FSM을 상태 패턴으로 바꿀 때 얻는 것과 잃는 것|상태 패턴]]으로 자연스럽게 이어지는 이유가 이것이다. 제어 흐름 속에 숨어 있던 상태를 명시적인 데이터로 꺼냈기 때문이다.

## 코루틴은 컴파일러가 대신 써 주는 업데이트 메서드다

상태를 직접 필드로 옮기는 작업은 번거롭다. 유니티 코루틴을 쓰면 원래의 루프 모양을 거의 그대로 유지할 수 있다. `for`문 안에 `yield return null`만 넣으면 된다. `while (true)`가 그대로 있는데도 화면이 멈추지 않는 이유는 `yield return`이 매 반복마다 제어권을 유니티에 돌려주기 때문이다.

CPU에는 함수 실행을 중간에 얼려 두는 기능이 없다. 이 일은 C# 컴파일러가 처리한다. 반복자 메서드는 `IEnumerator`를 구현하는 숨겨진 클래스로 변환된다. 이때 지역 변수는 그 클래스의 필드로 옮겨지고, 실행 위치는 정수 상태 필드 하나로 기록된다. 유니티가 매 프레임 호출하는 `MoveNext()`는 평범한 메서드라서 매번 첫 줄부터 실행된다. 하지만 그 첫 줄이 상태 값에 따라 각 `yield` 바로 다음 위치로 점프하는 분기 테이블이다.

```csharp
// 컴파일러가 만드는 클래스의 개념적 모습 (실제 이름은 <>1__state, <x>5__1 같은 형태)
private sealed class PatrolIterator : IEnumerator<object>
{
    private int _state;   // 실행 위치: 0=시작, 1=첫 for문 yield 직후, 2=둘째 for문 yield 직후
    private int _xA;      // 첫 번째 for문의 지역 변수 x
    private int _xB;      // 두 번째 for문의 지역 변수 x
    public Skeleton skeleton;
    public object Current { get; private set; }

    public bool MoveNext()
    {
        switch (_state)
        {
            case 1: goto ResumeA;
            case 2: goto ResumeB;
        }
    LoopTop:
        _xA = 0;
    CheckA:
        if (_xA < 100)
        {
            skeleton.SetX(_xA);
            Current = null; _state = 1;
            return true;              // yield return null
        }
        _xB = 100;
    CheckB:
        if (_xB > 0)
        {
            skeleton.SetX(_xB);
            Current = null; _state = 2;
            return true;              // yield return null
        }
        goto LoopTop;
    ResumeA:
        _xA++; goto CheckA;
    ResumeB:
        _xB--; goto CheckB;
    }
    // Reset, Dispose 생략
}
```

앞 절에서 손으로 했던 일과 비교하면 같은 구조라는 것을 알 수 있다. 지역 변수는 필드가 되고, 실행 위치는 정수 상태가 된다. 람다가 지역 변수를 캡처할 때 컴파일러가 DisplayClass를 만드는 것과 같은 계열의 변환이다([[Setup이 끝난 뒤에도 람다가 지역 변수를 계속 쓸 수 있는 이유]]).

`MoveNext()`의 반환값은 유니티와 주고받는 약속이다. `true`는 아직 끝나지 않았으니 `Current`에 담긴 조건에 맞춰 다시 호출해 달라는 뜻이다. `false`는 반복자가 끝났으므로 코루틴을 정리하라는 뜻이다. `Current`가 `null`이면 다음 프레임의 `Update` 단계가 끝난 직후 재개된다. `WaitForSeconds` 같은 `YieldInstruction`이면 그 조건이 만족될 때 재개된다. 유니티 문서에 따르면 첫 `yield` 이전의 코드는 `StartCoroutine`을 호출한 쪽에서 실행되고, 이후 재개는 메인 루프 안의 DelayedCallManager가 맡는다.

코루틴이 공짜는 아니다. `StartCoroutine` 호출마다 반복자 객체와 코루틴 핸들이 힙에 할당되고, `new WaitForSeconds(...)`를 매번 생성하면 그만큼 GC 대상이 늘어난다. 같은 대기 객체를 캐싱해서 재사용하는 관행은 이 때문이다.

## 매직 Update 1만 번은 경계를 1만 번 넘는다

업데이트 메서드 패턴을 유니티의 `MonoBehaviour.Update()`로 구현하면, 객체마다 엔진이 직접 `Update`를 호출한다. 총알 1만 개가 각자 `Update`를 갖는 구조와, 매니저 하나만 `Update`를 갖고 `List`를 순회하며 각 총알의 `Tick(dt)`를 호출하는 구조는 로직이 같다. 그런데 후자가 일반적으로 훨씬 싸다.

차이는 호출이 C++ 엔진과 C# 관리 코드 사이의 경계를 몇 번 넘느냐에서 나온다. 유니티 블로그의 "10000 Update() calls" 분석(Unity 5.2 시기, IL2CPP 빌드)은 엔진이 `Update` 하나를 호출하기 전에 하는 일을 이렇게 설명한다.

- 유니티는 `Update`를 정의한 스크립트를 내부 업데이트 리스트에 캐시해 두고, 매 프레임 이 리스트를 순회한다. 리플렉션으로 매번 찾는 방식은 아니다.
- 각 대상에 대해 객체가 이번 프레임 도중 파괴되거나 비활성화되지 않았는지 확인한다. 앞서 실행된 다른 `Update`가 `Destroy`나 `SetActive(false)`를 호출했을 수 있기 때문이다.
- 네이티브에서 관리 코드로 넘어가는 호출 객체와 인자 구조를 만들고, 스크립팅 런타임에 그 메서드의 실행을 요청한다. 런타임은 메서드 시그니처별로 생성된 invoker 함수를 거쳐 실제 `Update`를 부른다.
- 이 호출은 예외 처리 틀로 감싸져 있다. 그래서 한 스크립트의 예외가 엔진 루프 전체를 무너뜨리지 않고, 로그만 남긴 뒤 다음 대상으로 넘어간다.

엔진은 C#의 타입 정보를 보고 이 호출을 정적으로 최적화할 수 없다. 그래서 1만 번의 호출 각각이 이 과정을 모두 거친다. 반면 매니저 루프 안의 `_bullets[i].Tick(dt)`는 이미 관리 코드 안에서 일어나는 평범한 메서드 호출이다. 생존 확인도, 호출 객체 생성도, 호출마다 예외 처리 틀을 만드는 일도 없다. 경우에 따라 인라인까지 될 수 있다. 경계는 매니저의 `Update`에서 단 한 번만 넘는다.

구체적인 수치는 엔진 버전, 백엔드(Mono/IL2CPP), 에디터인지 빌드인지에 따라 크게 달라진다. 유니티도 2015년 이후 이 경로를 최적화해 왔다. 다만 최근 포럼 측정에서도 1만 개 규모에서 수 배에서 열 배 수준의 차이가 보고되므로, 대량 객체에서는 매니저 루프가 유리하다는 결론은 여전히 유효하다. 수백 개 규모라면 차이가 프레임 예산에 비해 미미하므로, 프로파일러로 확인하기 전에 구조부터 바꿀 이유는 없다.

## 매니저 루프가 잃는 것 — 예외 격리와 엔진의 생존 검사

매니저 루프로 얻는 속도는 엔진이 공짜로 해 주던 일을 포기한 대가다. 이 점을 알아야 트레이드오프를 설명할 수 있다.

첫째는 예외 격리다. 개별 `Update` 방식에서는 3번 총알이 `NullReferenceException`을 던져도 엔진이 그 호출만 중단하고 로그를 남긴다. 4번부터 1만 번까지는 이번 프레임에도 정상적으로 이동한다. 매니저 루프에서는 예외가 `for`문 밖으로 전파되어 매니저의 `Update` 전체가 중단된다. 따라서 4번 이후의 총알은 이번 프레임에 모두 멈춘다. 이 예외도 결국 매니저의 `Update` 경계에서 엔진이 잡지만, 그 단위가 총알 하나가 아니라 매니저 하나라는 점이 다르다. 항목마다 `try/catch`를 두면 격리는 되돌아오지만 그만큼 비용이 다시 붙는다. 그래서 보통은 예외가 나지 않게 데이터를 관리하는 쪽을 택한다.

둘째는 생존과 활성 여부 검사다. 엔진은 파괴되거나 비활성화된 객체를 알아서 건너뛰었다. 매니저 루프에서는 이 일을 직접 해야 한다. 풀에 반환되거나 비활성화된 총알을 리스트에서 확실히 빼야 하고, 순회 도중에 리스트가 바뀌는 경우도 처리해야 한다. 순회 중 제거는 옵저버의 Notify 순회와 같은 종류의 문제라서 해법도 같다. 역순 순회, 지연 제거, 스냅샷 같은 방법을 쓴다([[Notify 순회 중 구독 변경으로 깨지는 것을 막는 Subject 설계 선택지]]). 매 항목마다 `gameObject.activeSelf`를 확인하는 식으로 엔진 검사를 흉내 내면 그 확인 자체가 다시 네이티브 경계를 넘으므로 이점이 줄어든다.

반대로 매니저가 주는 추가 이점도 있다. 갱신 순서를 코드가 명시적으로 결정한다는 것이다. 개별 `Update` 사이의 순서는 Script Execution Order로만 거칠게 조절할 수 있다. 그래서 "A가 B의 이번 프레임 값을 보는가, 지난 프레임 값을 보는가"가 모호해진다. 매니저 루프에서는 순서가 리스트 순서이므로 결정적이다.

## 언제 무엇을 쓰는가

객체 수가 적고 각자 행동이 다른 경우에는 `MonoBehaviour.Update()`가 가장 읽기 쉽다. 이 경우 엔진이 제공하는 예외 격리와 생존 검사의 가치가 호출 비용보다 크다. 순서가 있는 짧은 연출이나 대기처럼 "한 번 흘러가고 끝나는" 동작은 코루틴으로 쓰면 상태를 필드로 쪼개는 수고를 컴파일러가 대신해 준다. 다만 할당 비용과 생명주기 관리(오브젝트 비활성화 시 코루틴 중단)를 의식해야 한다. 총알이나 파티클형 적처럼 같은 종류의 객체가 수천 개 이상이고 로직이 단순하면 매니저 루프로 묶는다. 보통 [[오브젝트 풀링은 무엇이고 어떻게 GC 부담을 줄이는가|오브젝트 풀]]과 함께 써서 등록과 해제를 풀의 꺼내기와 반환에 묶는다. 이보다 더 큰 규모라면 데이터를 배열로 분리하고 Job System과 Burst로 넘기는 데이터 지향 설계(DOTS/ECS)가 다음 단계다. 이것은 업데이트 메서드 패턴과 달리 객체 단위의 가상 호출 자체를 없애는 방향이다.
