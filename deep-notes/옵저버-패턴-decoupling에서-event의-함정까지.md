## 옵저버 패턴이 분리하는 것 — 참조가 아니라 의존 방향

옵저버 패턴은 "상태가 변하는 사건"과 "그 사건에 반응하는 로직"을 분리한다. 플레이어 체력이
바뀌는 순간과, 그에 반응해야 하는 체력바 UI·사망 판정·업적 시스템·사운드는 서로 다른 관심사다.
이 둘을 한 클래스에 묶으면 `Player`가 반응자 전부를 필드로 참조하고 하나하나 직접 호출해야 한다.

여기서 흔히 "참조를 여러 개 들고 있어서 나쁘다"고 요약하는데, 문제의 본질은 참조의 개수가 아니라
**의존의 방향과 대상**이다. 강결합 버전의 `Player`는 `HealthBar`, `AchievementSystem`,
`SoundEffect` 같은 **구체 타입**을 이름으로 알고 있어야 한다. 그래서 체력 변화에 반응하는
시스템이 하나 늘 때마다 `Player`가 그 새 타입을 알게 되고, 플레이어의 본질과 무관한 의존성이
계속 불어난다. "사운드 이펙트를 추가"하는 단순한 요구가 `Player.cs`를 열어 참조와 호출을
심는 작업이 된다.

옵저버 버전에서는 이 방향이 뒤집힌다. `Player`(Subject)는 자기를 구독하는 쪽의 존재 자체를
모른다. 반응하는 쪽이 스스로 `Player`를 구독하고 빠진다. 새 반응자를 추가할 때 `Player` 코드는
한 줄도 바뀌지 않는다. 이것이 OCP(개방-폐쇄 원칙)를 지킨다고 말하는 상황이다 — 확장(새 옵저버
등록)에는 열려 있고, 발행자의 수정에는 닫혀 있다.


## Subject의 내부 구조와 OCP가 성립하는 진짜 이유

OCP는 결과이고, 그 결과를 떠받치는 것은 DIP(의존관계 역전 원칙)다. `Player`가 새 반응자에
무지할 수 있는 이유는, 구체 타입이 아니라 **공통 인터페이스라는 추상에 의존**하도록 구조를
바꿨기 때문이다.

```csharp
public interface IHealthObserver
{
    void OnHealthChanged(int current, int max);
}

public class Player
{
    private readonly List<IHealthObserver> _observers = new();

    public void Register(IHealthObserver observer) => _observers.Add(observer);
    public void Unregister(IHealthObserver observer) => _observers.Remove(observer);

    private void Notify()
    {
        foreach (var o in _observers)
            o.OnHealthChanged(_currentHp, _maxHp);
    }
}
```

Subject는 공통 인터페이스를 구현한 옵저버들의 리스트를 든다. 새 옵저버 등록은 그 리스트에
참조를 추가하는 것뿐이고, `Player`는 원소의 구체 타입을 특별 취급하지 않는다. 리스트의 정적
타입이 `IHealthObserver`이므로 `Player`는 `HealthBar`인지 `SoundEffect`인지 알 필요가 없다.
이 "구체 타입이 아니라 추상에 의존한다"는 한 줄이 DIP이고, 그 위에서 OCP가 자동으로 따라온다.


## Notify 순회 중 구독 변경이라는 함정

옵저버 패턴에서 실무적으로 가장 자주 터지는 곳은 `Notify` 순회 도중 구독 목록이 바뀌는
상황이다. 대표적으로 "체력이 0이 되면 이 옵저버는 임무가 끝났으니 콜백 안에서 자기 자신을
`Unregister`한다" 같은 요구가 그렇다. 위 코드에서 이 경우 `foreach`가 다음 원소로 넘어가려
`MoveNext()`를 호출하는 순간 `InvalidOperationException`이 발생한다.

원인은 옵저버 패턴 고유의 것이 아니라 `List<T>` 열거의 일반 성질이다. `List<T>`는 내부에
버전 정수를 두고 `Add`/`Remove`/`Clear` 같은 구조적 변경마다 그 값을 올린다. 열거자는 생성
시점의 버전을 스냅샷으로 들고 있다가 `MoveNext()`에서 현재 버전과 비교해 다르면 예외를 던진다.
리스트 내용을 실시간 감시하는 게 아니라 정수 하나를 비교하는 값싼 무결성 체크다. 그래서
옵저버를 설계할 때는 "발행 도중 구독 컬렉션이 변경될 수 있다"를 항상 전제해야 한다.


## 순회 안전을 확보하는 세 가지 Subject 설계

Subject 수준에서 이 함정을 애초에 깨지지 않게 만드는 선택지는 대략 셋이다.

첫째, 복사 후 순회(snapshot)다. `Notify` 시작 시 현재 옵저버 목록을 복사해 그 복사본을 돈다.
원본이 어떻게 바뀌든 복사본의 버전은 변하지 않으므로 예외가 나지 않는다. 셋 중 구현이 가장
단순해 실무 기본값이 된다. 대가는 복사 비용이다. `Notify`가 매 프레임 도는 고빈도 경로라면
이 복사가 프레임마다 GC 할당을 만들어 게임에서는 특히 아프다. 또한 복사 시점에 박제된 목록을
돌기 때문에, 순회 도중 빠진 옵저버도 이번 회차에는 콜백을 받는다.

둘째, 변경 보류(deferred modification)다. `Notify` 중 들어온 등록/해제 요청을 대기 큐에
쌓아뒀다가 순회가 끝난 뒤 일괄 반영한다. 순회 대상 리스트 자체는 건드리지 않으므로 버전
충돌이 없다. 단점은 상태 관리가 늘어나는 것과, 해제가 즉시 반영되지 않아 "이미 빠지려던
옵저버가 이번 발행에서 한 번 더 반응한다"는 미묘한 결과가 생긴다는 점이다.

셋째, 죽은 표시 후 청소(tombstone)다. 즉시 제거 대신 옵저버에 비활성 플래그만 세우고
순회 중엔 건너뛰며, 나중에 한 번에 정리한다. 컬렉션 구조를 바꾸지 않으니 예외가 없고 정리를
모아서 할 수 있지만, 죽은 원소가 리스트에 남아 순회 비용을 계속 내고, 정리 시점을 별도로
관리해야 하며, "구독 해제"와 "일시 비활성화"의 의미가 섞일 위험이 있다.

세 방어책 모두 "순회 도중 해제한 옵저버가 그 회차에는 여전히 콜백을 받는다"는 성질을
공유하거나(복사·보류) 명시적으로 건너뛴다(tombstone). 즉시성이 중요하면 이 점을 별도로
설계해야 한다.


## C# event로 갈아탔을 때 세 문제의 운명

C#에는 구독 컬렉션 관리를 언어가 대신 해주는 `event` + 멀티캐스트 델리게이트가 있다.
`Player`가 `List<IHealthObserver>`를 직접 관리하는 대신 `event Action<int,int> OnHealthChanged`
를 노출하면, 위 세 문제가 각각 다르게 처리된다.

순회 중 수정 예외는 자동으로 사라진다. 멀티캐스트 델리게이트는 `-=` 할 때 기존 invocation
list를 제자리에서 수정하지 않고 **새 델리게이트 인스턴스로 통째 교체**한다. `Invoke()`가 돌고
있던 것은 교체 전의 옛 리스트라, `List<T>`의 버전 충돌 같은 문제가 원천적으로 없다.

즉시 반영 안 됨은 그대로 남는다. 방금의 "새 인스턴스로 교체" 성질이 바로 이 결과를 데려온다.
`Invoke` 도중 `-=`한 구독자는 이번 발행에서 여전히 콜백을 받는다. 직접 구현할 때의 복사 후
순회와 정확히 같은 성질이다. `event`가 공짜로 주는 부작용이므로 인지하고 있어야 한다.

죽은 옵저버 문제는 형태를 바꿔 오히려 더 숨는다. `+=`로 구독하면 Subject의 델리게이트가
그 옵저버(인스턴스 메서드의 `this`)를 강한 참조로 붙든다. 옵저버 쪽에서 `-=`를 깜빡하면,
그 옵저버를 다른 누구도 쓰지 않는데도 Subject가 계속 잡고 있어 GC가 수거하지 못한다.
lapsed listener라 불리는 메모리 누수다. 직접 관리하는 `List<IHealthObserver>`에도 같은
위험이 있지만, `event`는 구독 목록이 언어 뒤로 감춰져 "지금 누가 붙어 있나"를 열어볼 수
없다는 점에서 더 다루기 어렵다. 유니티에서는 파괴된 오브젝트의 메서드가 이벤트에 남아
fake null 대상을 호출하다 사고가 나는 계열이 여기에 해당한다. 그래서 유니티에서 `event`를
쓸 때는 `OnDisable`/`OnDestroy`에서의 구독 해제가 사실상 의무가 된다.

정리하면 `event`는 순회 안전을 언어 차원에서 무료로 주고, 즉시 반영 문제는 그대로 물려주며,
생명주기 문제는 감춰진 형태로 더 까다롭게 만든다. "언어가 구독 메커니즘은 관리해주지만
구독자의 수명과 전파 정책까지 관리해주지는 않는다"가 이 셋을 관통하는 요약이다.
