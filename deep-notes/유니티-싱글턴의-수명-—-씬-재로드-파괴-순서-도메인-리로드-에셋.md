## MonoBehaviour가 되는 순간 수명을 엔진이 쥔다

유니티 매니저를 static 클래스가 아니라 싱글턴으로 만드는 실질적인 이유는 대개 MonoBehaviour를 상속할 수 있다는 데 있다. Inspector 직렬화로 튜닝 값과 프리팹·에셋 참조를 에디터에서 꽂아 넣을 수 있고, `Awake`·`Update`·`OnDestroy` 같은 생명주기 메시지를 받을 수 있고, `StartCoroutine`이 MonoBehaviour의 인스턴스 메서드이므로 코루틴을 돌릴 수 있다.

static 클래스가 이것들을 못 쓰는 이유는 두 층이다. 언어 쪽에서는 static 클래스가 `object` 외의 클래스를 상속할 수 없어 MonoBehaviour 상속이 컴파일 단계에서 막힌다. 엔진 쪽에서는 유니티가 GameObject에 붙은 컴포넌트 인스턴스를 들고 그 인스턴스에 메시지를 호출하고 그 인스턴스의 필드에 직렬화 데이터를 써 넣으므로, 인스턴스가 없으면 끼어들 방법이 없다. [[싱글턴 매니저가 MonoBehaviour를 상속하면 쓸 수 있는 기능과 static 클래스가 못 쓰는 이유]]

대가는 수명이다. 컴포넌트는 씬과 함께 생기고 사라지며, 그 시점과 순서는 엔진이 정한다. 아래의 문제들은 모두 "인스턴스의 수명은 엔진이 쥐고, 그것을 가리키는 `Instance`의 수명은 static이 쥔다"는 어긋남에서 나온다.

## 씬이 다시 로드되면 복제본이 스스로 빠져야 한다

씬에 배치한 싱글턴은 그 씬이 로드될 때마다 씬 파일에서 새로 만들어진다. 표준 구현은 `Awake`에서 기존 인스턴스가 있으면 자기를 파괴하고, 없으면 `Instance`가 되어 `DontDestroyOnLoad`로 살아남는다.

```
[Title 1회차] A.Awake → Instance = A, DontDestroyOnLoad(A)
[Game]        A 생존, score = 120
[Title 2회차] B(씬 파일의 복제본).Awake → Instance == A → Destroy(B) 예약
[프레임 끝]   B 실제 파괴 → A만 남음 (score 120)
```

두 번째 Title 로드 때 도는 것은 원본 A의 Awake가 아니라 새 복제본 B의 Awake다. Awake는 인스턴스당 한 번이다. 그리고 `Destroy`는 호출 즉시가 아니라 현재 프레임의 업데이트 루프가 끝난 뒤 실제로 처리되므로, 그 프레임 동안은 둘이 잠깐 공존한다. [[DontDestroyOnLoad 싱글턴이 있는 씬을 다시 로드하면 어느 인스턴스가 살아남는가]]

## 자폭한 복제본의 OnDestroy가 원본의 손잡이를 지운다

정리하겠다며 `OnDestroy`에 `Instance = null;`을 무조건 넣으면 이 지연이 사고가 된다. B는 Awake에서 자폭을 예약하고 끝났는데, 프레임 끝에 실제로 파괴되면서 B의 OnDestroy가 static `Instance`를 지운다. static 필드는 클래스에 하나뿐이므로 지워지는 것은 A가 쓰던 바로 그 참조다.

```
[1차 귀환, 프레임 N]   B.Awake → Instance == A → Destroy(B) 예약, return
[프레임 N 끝]          B 파괴 → B.OnDestroy → Instance = null   (A는 생존)
[프레임 N+1]           Instance.Score → NullReferenceException
[2차 귀환]             C.Awake → Instance == null → Instance = C
                       → A와 C 공존, C.score = 씬 초기값
```

B의 Awake는 이미 끝났으므로 null이 된 뒤 B가 자리를 되찾을 기회는 없다. 고치는 방법은 `if (Instance == this) Instance = null;`, 즉 내가 Instance일 때만 지우는 것이다. [[싱글턴 OnDestroy에서 Instance를 무조건 null로 만들면 생기는 사고]]

## 종료 시 파괴 순서는 보장되지 않는다

플레이 모드 종료나 게임 종료 때는 모든 오브젝트가 파괴되는데, 유니티는 서로 다른 오브젝트 사이의 파괴 순서를 보장하지 않는다. 지연 생성 getter(`_instance == null`이면 찾고, 없으면 새 GameObject를 만드는 방식)를 쓰는 싱글턴이 먼저 파괴되고, 그 뒤에 다른 오브젝트의 `OnDestroy`가 `Instance`를 부르면 getter가 새 매니저를 만든다. `_instance`에 남은 C# 래퍼를 오버로딩된 `==`가 null로 판정하고, `FindAnyObjectByType`도 파괴된 객체는 찾지 않기 때문이다. 순서가 반대면 아무 일도 없으니 버그는 간헐적으로만 나타난다.

실무에서는 생성하지 않는 조회(`HasInstance`)를 따로 두어 정리 코드에서는 그것만 쓰게 하고, `OnApplicationQuit`에서 종료 플래그를 세워 getter가 종료 중에는 생성하지 않게 한다. `OnApplicationQuit`은 종료 시 OnDisable·OnDestroy보다 먼저 호출되고 에디터에서 플레이 모드를 끌 때도 호출된다. 근본 원칙은 "OnDestroy에서 다른 오브젝트에 의존하지 않는다"이다. [[종료 시 OnDestroy에서 지연 생성 싱글턴에 접근하면 유령 오브젝트가 생기는 이유]]

## 손잡이가 static이면 상태는 도메인의 수명을 따른다

유니티 에디터에서 C# 스크립트는 도메인(AppDomain) 안에서 돈다. 기본 설정은 플레이 모드에 들어갈 때마다 도메인을 새로 만들어 static 상태를 지운다. 플레이 진입 속도를 위해 Enter Play Mode 설정에서 도메인 리로드를 끄면, static 필드의 값과 static 이벤트에 등록된 핸들러가 플레이 사이에 그대로 남고 정적 생성자도 다시 돌지 않는다.

static 클래스의 상태가 남는 건 당연하지만 싱글턴도 똑같이 남는다. 인스턴스는 객체여도 그것을 붙잡는 `Instance`가 static이기 때문이다. "싱글턴은 인스턴스니까 static 문제에서 자유롭다"는 기대는 여기서 깨진다. 빌드에서는 프로세스 종료와 함께 모두 사라지므로 이 문제는 에디터에서만 나타나고, 그래서 찾기 어렵다.

```csharp
// 도메인 리로드가 꺼져 있어도 플레이 진입 시 가장 이른 시점에 호출된다
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
private static void ResetStatics()
{
    Instance = new GameState();
}
```

## 죽은 래퍼는 필드 읽기에는 아무 신호도 주지 않는다

MonoBehaviour 싱글턴이 도메인 리로드 OFF와 만나면 한 겹이 더 생긴다. 두 번째 플레이 때 `Instance`에는 지난 플레이에서 파괴된 매니저의 C# 래퍼가 남아 있다. `Instance != null`은 오버로딩된 연산자라 이를 null로 보고 새 매니저에게 자리를 넘기므로 우연히 정상 동작한다. 그런데 `is not null`, `?.`, `??`처럼 오버로딩을 우회하는 문법으로 바꾸면 죽은 래퍼를 살아 있다고 판단해 새 매니저가 자폭하고, 살아 있는 매니저가 하나도 없게 된다.

```
static Instance ──▶ [C# 래퍼 (관리 힙)]
                      score = 340              ← 읽기 성공 (네이티브와 무관)
                      네이티브 연결 ──▶ ✕ 파괴됨  ← transform, StartCoroutine 등은 예외
```

이 래퍼로 `transform`이나 `StartCoroutine`처럼 네이티브 객체를 거치는 멤버를 부르면 MissingReferenceException이 나지만, C# 필드는 관리 힙의 래퍼 안에 있어 확인 지점이 없으므로 예외 없이 지난 플레이의 값이 나온다. 크래시보다 찾기 어려운 버그다. [[도메인 리로드 OFF에서 싱글턴 검사를 is not null로 바꾸면 생기는 일]]

## 에셋에 담은 상태는 또 다른 수명을 가진다

static 싱글턴 대신 ScriptableObject 에셋에 공유 상태를 두는 방식도 많이 쓴다. 이 상태의 수명은 static 필드와도 씬 오브젝트와도 다르다. 에디터는 플레이 진입 시 열린 씬만 백업했다가 종료 때 되돌리고 에셋은 백업하지 않으므로, 플레이 중 바뀌는 것은 에디터 메모리에 올라온 에셋 객체 그 자체다. 도메인 리로드가 새로 만드는 것은 C# 실행 환경이지 에디터가 들고 있는 에셋 데이터가 아니므로, 리로드를 켜 둬도 플레이 중 바꾼 값이 플레이를 끈 뒤에 남는다.

빌드에서는 에셋 데이터가 빌드 결과물에서 읽혀 오므로 런타임 변경은 프로세스 종료와 함께 사라진다. 에디터와 빌드의 동작이 반대인 셈이다. 정리하면 상태의 수명은 그 상태가 누구에게 소속되느냐로 정해진다. static 필드는 도메인에, 씬 오브젝트는 씬에, 에셋은 에디터의 에셋 데이터베이스에 속한다. 그래서 ScriptableObject는 읽기 전용 설정 데이터로 쓰고, 런타임 상태는 시작 시 `Instantiate`로 복제본을 만들거나 별도 객체에 두는 것이 일반적이다.
