## 이분 탐색은 "값 찾기"가 아니라 "경계 찾기"다

이분 탐색을 처음 배울 때의 형태는 "정렬 배열에서 값 x가 있는 인덱스를 찾고, 없으면 -1"이다. 이 표준형은 `a[mid] == x`를 만나는 순간 즉시 리턴한다. 문제는 이 "일치하면 종료"라는 성질이 이분 탐색의 본질이 아니라 특수한 경우라는 데 있다.

실무에서 훨씬 자주 만나는 건 등호 질의가 아니라 부등호 질의다. "x 이하인 원소 중 가장 큰 값(predecessor, floor query)", "x 이상인 원소 중 가장 작은 값(successor, ceiling query)", "x가 들어갈 위치(lower/upper bound)" 같은 것들이다. 이들은 배열에 x가 존재하지 않아도 답이 나와야 한다. 그래서 "찾으면 종료"가 아니라 "경계까지 좁힌다"가 기본 골격이 된다.

"x 이하 최댓값의 인덱스"를 구하는 코드는 이렇게 된다.

```csharp
int left = 0, right = a.Length - 1, answer = -1;
while (left <= right)
{
    int mid = left + (right - left) / 2;
    if (a[mid] <= x) { answer = mid; left = mid + 1; }  // 조건 만족 → 후보 기록, 오른쪽 계속
    else             { right = mid - 1; }                // 너무 큼 → 왼쪽으로
}
return answer;
```

표준 탐색과의 구조적 차이는 두 가지다. 첫째, 비교가 `==`가 아니라 `<=`다. 둘째, 조건을 만족했을 때 종료하지 않고 `answer = mid`로 후보를 기록한 뒤 `left = mid + 1`로 더 나은 후보(더 큰 인덱스)를 계속 찾는다. `answer`의 초기값이 -1인 것이 "조건을 만족하는 원소가 하나도 없다"는 경우를 자연스럽게 처리한다. `a = [1,3,5,7]`, `x = 4`면 mid=1(a=3)에서 후보를 잡고 오른쪽을 보다 a[2]=5>4에 막혀 answer=1(값 3)로 확정된다.

이 골격의 이름을 하나 붙여두면 이후 모든 변형이 같은 틀로 보인다. "조건을 만족하면 답 후보로 기록하고 한쪽 방향으로 계속 좁힌다." 무엇이 조건이고 어느 쪽으로 좁히느냐만 문제마다 갈아끼우면 된다.

## mid 계산의 오버플로우 — 인덱스가 아니라 값을 탐색할 때 터진다

`int mid = (left + right) / 2`는 정직해 보이지만 클래식한 버그를 품고 있다. `left + right`가 `int.MaxValue`(2,147,483,647)를 넘으면 오버플로우가 난다.

C#은 기본적으로 정수 산술 오버플로우를 예외 없이 조용히 랩어라운드시킨다(`unchecked`가 기본 컨텍스트다). 그래서 합이 넘치면 예외가 터지는 게 아니라 값이 소리 없이 음수로 감기고, `음수 / 2`도 음수이므로 `mid`가 음수가 된다. 그 상태로 `a[mid]`에 접근하는 순간에야 `IndexOutOfRangeException`이 난다. "조용히 틀린 mid → 배열 접근에서 터짐"이라는 2단 구조라, 원인과 증상이 떨어져 있어 디버깅이 까다롭다.

고치는 법은 합 자체를 피하는 것이다.

```csharp
int mid = left + (right - left) / 2;
```

`right - left`는 두 값의 차이라 원래 범위를 넘지 않고, 거기에 `left`를 더해도 결과는 `right` 이하다. 그래서 오버플로우가 원천 봉쇄된다.

여기서 실무적으로 중요한 통찰이 하나 있다. 이 버그는 **배열 인덱스를 탐색할 때는 사실상 나지 않는다.** 오버플로우하려면 `left + right`가 21억을 넘어야 하는데, 그러려면 배열 길이가 10억을 넘어야 하고 그건 `int[]` 기준 4GB가 넘는 배열이라 현실적으로 존재하지 않는다. 이 버그가 진짜로 발현되는 곳은 인덱스가 아니라 **값의 범위를 이분 탐색할 때**다. `left`, `right`가 인덱스가 아니라 "가능한 답의 크기"이고 그 상한이 수십억대면 합이 곧바로 int를 넘는다. 그래서 `left + (right - left) / 2`는 습관으로 들여야 하지만, 그 습관이 실제로 목숨을 구하는 건 다음에 나올 parametric search 계열이다.

## `left <= right` vs `left < right` — 마지막 한 칸이 사각지대가 되는 순간

루프 조건을 `while (left <= right)`에서 `while (left < right)`로 바꾸면, 나머지 코드가 같아도 답이 달라지는 입력이 생긴다.

이유는 탐색 구간을 닫힌 구간 `[left, right]`로 보고 그 안을 전부 소진하는 스타일에서, `left == right`인 순간은 "아직 검사하지 않은 원소가 정확히 하나 남은 상태"이기 때문이다. `<=`는 이 마지막 한 칸을 mid로 잡아 검사하고 종료하지만, `<`는 `left == right`가 되는 순간 그 칸을 건드리지 않고 루프를 끊는다.

`a = [1,3,5,7]`, `x = 7`로 추적하면 그 사각지대가 정확히 드러난다.

```
초기:  left=0, right=3, answer=-1
[1회]  mid=1, a[1]=3 ≤ 7 → answer=1, left=2
[2회]  mid=2, a[2]=5 ≤ 7 → answer=2, left=3
[3회]  left==right==3 인 상태
       <= 버전: 조건 참 → mid=3, a[3]=7 ≤ 7 → answer=3 (정답)
       <  버전: 조건 거짓 → 즉시 종료 → answer=2 (오답)
```

주의할 점은, 조건 하나만 `<`로 바꾸면 항상 "마지막 칸 누락"이라는 이 실패로 이어지는 건 아니라는 것이다. 예컨대 `x = 1`이면 두 버전의 답이 갈리긴 하지만, 그건 `left == right`까지 좁혀지기 전에 루프가 다른 경로로 끝나서다. `<` 조건을 안전하게 쓰려면 그 조건에 맞는 갱신 규칙과 답 확정 시점을 세트로 다시 설계해야 한다. 아무 스타일에나 `<`를 끼워 넣으면 마지막 한 칸이 항상 위험하다. 경계 조건, 갱신식(`mid+1`/`mid-1`/`mid`), 답을 읽는 시점 이 세 가지는 한 몸이라, 하나만 바꾸면 나머지가 어긋난다.

## parametric search — 배열이 아니라 답의 범위를 이분 탐색한다

지금까지는 "정렬된 배열의 인덱스"를 탐색했다. 이분 탐색의 진짜 위력은 탐색 대상이 배열일 필요가 없다는 데서 나온다. **판정 결과가 단조(monotonic)이기만 하면 답의 값 자체를 이분 탐색할 수 있다.** 이것을 parametric search 또는 "정답을 이분 탐색한다(binary search on the answer)"고 부른다.

예를 들어 위협도가 정해진 몬스터 배열을 순서를 유지한 채 K개의 연속 구간(웨이브)으로 나누되, "가장 무거운 웨이브의 합"을 최소화하는 문제를 생각해보자. 이건 배열을 뒤져서 어떤 원소를 찾는 문제가 아니다. 답이 될 수 있는 "허용 최대 웨이브 합"이라는 값을 이분 탐색한다.

세 가지를 정하면 골격이 완성된다.

첫째, 탐색 범위. `left = max(a)`, `right = sum(a)`. 어떤 웨이브든 최소한 가장 무거운 몬스터 하나는 담아야 하니 답이 `max(a)`보다 작을 수 없고, 전부 한 웨이브에 몰아넣으면 `sum(a)`이니 그보다 클 필요가 없다.

둘째, 판정 함수. `a[mid] <= x` 비교가 있던 자리에 `Feasible(mid)`가 들어간다. "웨이브 합이 mid를 넘지 않도록 앞에서부터 그리디하게 잘랐을 때 필요한 웨이브 수 need가 K 이하인가?"를 판정한다. 앞에서부터 넘치기 직전까지 욕심껏 채우고 자르는 그리디가 필요 웨이브 수를 최소화하므로, `need <= K`이면 mid는 실현 가능하다.

```csharp
// mid를 허용 최대 웨이브 합으로 두고, K개 이하로 나눌 수 있는지 판정
bool Feasible(int[] a, int k, int maxSum)
{
    int need = 1, cur = 0;
    foreach (int t in a)
    {
        if (cur + t <= maxSum) cur += t;      // 현재 웨이브에 계속 채운다
        else { need++; cur = t; }             // 넘치면 새 웨이브 시작
    }
    return need <= k;
}
```

셋째, 갱신 방향. 여기서 인덱스 탐색과 방향이 뒤집힌다. mid가 실현 가능하면 mid 자신도 답 후보이고, 우리는 더 작은 값도 되는지 궁금하므로 상한을 내린다(`right = mid - 1`, mid는 answer에 기록). 불가능하면 허용 합을 더 키워야 하므로 `left = mid + 1`. "조건을 만족하면 후보 기록 후 한쪽으로 좁힌다"는 골격은 그대로고, 다만 최댓값을 찾던 predecessor 문제와 달리 최솟값을 찾으므로 후보 기록이 붙는 브랜치가 왼쪽으로 간다.

```csharp
int left = Max(a), right = Sum(a), answer = right;
while (left <= right)
{
    int mid = left + (right - left) / 2;
    if (Feasible(a, K, mid)) { answer = mid; right = mid - 1; }  // 가능 → 후보, 더 작게
    else                     { left = mid + 1; }                 // 불가능 → 더 크게
}
return answer;
```

이 코드와 맨 처음의 predecessor 코드를 나란히 놓으면 뼈대가 같다는 게 보인다. `Feasible(mid)`가 `a[mid] <= x`의 자리를 대신하고, "조건 만족 → 후보 기록 후 한 방향 계속"이라는 패턴이 동일하다. 차이는 딱 하나, 찾는 게 최댓값이냐 최솟값이냐에 따라 후보 기록 브랜치에 `left = mid+1`이 붙느냐 `right = mid-1`이 붙느냐가 뒤집힐 뿐이다.

parametric search가 성립하는 전제는 판정 함수의 단조성이다. "mid가 가능하면 mid보다 큰 값은 전부 가능하고, mid가 불가능하면 mid보다 작은 값은 전부 불가능하다"는 성질이 있어야 경계가 하나로 정해진다. 이 단조성이 깨지는 문제에는 이분 탐색을 쓸 수 없다. 그리고 앞 절에서 미뤄둔 오버플로우 이야기가 여기서 실전이 된다. 이런 값 탐색에서는 `left`, `right`가 수십억대가 되기 쉬워 `(left+right)/2`가 실제로 오버플로우한다. 인덱스 탐색에서는 교과서적 주의사항에 그쳤던 것이 값 탐색에서는 실제 버그가 되는 이유다.
