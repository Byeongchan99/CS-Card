## 문제의 본질은 쓰는 도중의 상태를 누군가 읽는다는 것이다

어떤 상태를 갱신하는 일은 한 순간에 끝나지 않는다. 렌더러는 한 프레임을 수천 번의 드로우로 나누어 그리고, 게임 로직은 수백 개의 오브젝트를 하나씩 순서대로 갱신한다. 그 사이 어느 시점에서 보든 상태는 "이전 결과의 잔재 + 이번 결과의 일부"인 중간 상태다.

이 중간 상태를 읽는 쪽이 있으면 문제가 생긴다. 디스플레이는 렌더러의 진행 상황과 무관하게 일정한 주기로 프레임 버퍼를 위에서 아래로 읽는다(스캔아웃). 버퍼가 하나뿐이면 그리다 만 영역이나 clear 직후의 빈 화면이 그대로 노출되어 깜빡이고, 위쪽과 아래쪽이 서로 다른 시점의 내용으로 찢어진다. 근본 원인은 쓰기와 읽기가 같은 메모리에 동기화 없이 동시에 일어난다는 것이다.

이중 버퍼 패턴의 해법은 단순하다. 쓰는 버퍼(백)와 읽는 버퍼(프론트)를 분리한다. 읽는 쪽은 항상 완성된 상태만 보고, 쓰는 쪽은 아무도 읽지 않는 곳에서 자유롭게 작업한다. 쓰기가 끝나면 두 버퍼의 역할을 교체한다. 자세한 문답은 [[단일 프레임 버퍼에 그리면 생기는 문제와 이중 버퍼가 이를 제거하는 방식]]에 있다.

## 교체는 참조 하나를 바꾸는 원자적 연산이어야 한다

교체를 "백 버퍼의 내용을 프론트 버퍼로 복사"로 구현할 수도 있다. 하지만 이 방식에는 두 가지 문제가 있다.

첫째는 비용이다. 화면 전체의 픽셀을 매 프레임 읽고 쓰므로, 해상도에 비례하는 시간과 메모리 대역폭이 든다. 추가로 드는 것은 메모리 공간이 아니다. 버퍼 두 개는 어느 방식이든 이미 존재한다.

둘째가 더 치명적이다. 복사는 시간이 걸리고, 그동안 디스플레이는 프론트 버퍼를 계속 읽는다. 복사가 스캔아웃 구간에 걸치면 디스플레이는 "덮어쓰이는 중인 프론트 버퍼"를 읽게 된다. 처음에 피하려던 문제, 즉 쓰는 도중의 상태를 읽는 문제가 그대로 되살아난다.

그래서 교체는 포인터, 핸들, 인덱스 같은 참조 하나를 바꾸는 연산이어야 한다. 그래픽 하드웨어에서는 디스플레이 컨트롤러가 읽을 주소를 바꾸는 페이지 플립(page flip)이 이에 해당한다. 참조 값 하나를 쓰는 것은 사실상 원자적이어서 "반쯤 교체된" 중간 상태가 존재하지 않는다. 이것이 단지 빠르다는 것보다 본질적인 이유다. [[이중 버퍼의 교체가 픽셀 복사가 아니라 참조 전환이어야 하는 이유]]

## 이중 버퍼가 막는 것은 미완성 프레임이고, 찢김은 교체 시점이 막는다

교체가 원자적이어도 찢김은 여전히 생길 수 있다. 스캔아웃은 한 프레임에 걸쳐 진행되는데, 그 도중에 출력 대상이 A에서 B로 바뀌면 화면 위쪽은 A, 아래쪽은 B가 된다. 두 프레임 모두 완성된 상태이지만 한 화면에 섞인다.

정리하면 이중 버퍼가 구조적으로 보장하는 범위는 "미완성 프레임은 절대 노출되지 않는다"까지다. 두 완성 프레임이 섞이지 않게 하려면 교체를 디스플레이가 읽지 않는 구간에 해야 한다. 그 구간이 한 프레임의 스캔아웃이 끝나고 다음 프레임이 시작되기 전의 수직 귀선 기간(VBlank)이고, 교체를 이 구간에 맞추는 동기화가 VSync다.

여기서 원자적 교체의 가치가 다시 드러난다. VBlank는 짧은 구간이라서, 순간에 끝나는 참조 전환은 그 안에 확실히 넣을 수 있다. 반면 해상도와 대역폭에 비례하는 전체 복사는 그 안에 끝난다는 보장이 없다. [[이중 버퍼에서도 찢김이 생기는 경우와 교체를 VBlank에 맞춰야 하는 이유]]

## VSync 이중 버퍼는 예산을 조금만 넘겨도 fps를 계단식으로 깎는다

VSync를 켜면 교체가 VBlank에만 일어나므로, 렌더링 시간이 VBlank 주기를 조금만 넘겨도 대가가 크다. 60Hz(약 16.7ms 주기)에서 한 프레임에 18ms가 걸리는 경우를 보자.

```
시간(ms)  0        16.7      33.3      50.0      66.7
VBlank    |         |         |         |         |
렌더러    [---F1 18ms---]대기-[---F2 18ms---]대기-
교체                          ^F1                 ^F2
```

F1은 18ms에 완성되지만 첫 VBlank(16.7ms)를 놓쳐 33.3ms에야 교체된다. 그동안 렌더러는 다음 프레임을 그릴 수 없다. 프론트 버퍼는 스캔아웃 중이고, 백 버퍼에는 교체를 기다리는 완성 프레임이 들어 있어서 쓸 수 있는 버퍼가 없기 때문이다. 결과적으로 렌더러는 매 프레임 약 15ms를 놀고, 화면 갱신은 60에서 50 정도로 완만하게 줄지 않고 30으로 떨어진다. 이 계단식 하락은 프레임 예산 관리가 왜 평균이 아니라 최악의 프레임을 기준으로 해야 하는지를 보여준다.

버퍼를 하나 더 두는 트리플 버퍼링은 이 대기를 없앤다. 완성된 프레임이 세 번째 버퍼에서 교체를 기다리는 동안 렌더러는 남은 버퍼에 다음 프레임을 바로 그린다. 위 예에서는 18ms마다 새 프레임이 나오므로 갱신이 약 55fps 수준까지 올라간다. 대가는 다음과 같다.

- 버퍼 하나만큼의 메모리가 더 든다.
- 18ms 주기로 나오는 프레임이 16.7ms 격자의 VBlank에 맞춰 나가므로, 대부분의 프레임은 한 주기, 일부는 두 주기 동안 보인다. 평균 fps는 올라도 프레임 간격이 고르지 않아 미세한 끊김(judder)이 생길 수 있다.
- 입력 지연은 구현 방식에 따라 다르다. 완성 프레임을 순서대로 줄 세워 내보내는 큐(FIFO) 방식은, 렌더링이 주사율보다 빠를 때 프레임이 큐에서 기다리면서 화면에 나가는 프레임이 점점 오래된 것이 된다. 그래서 입력에서 화면까지의 지연이 늘어난다. 대기 중인 프레임을 최신 프레임으로 덮어쓰는 방식(Vulkan의 MAILBOX 프레젠트 모드가 이 방식이다)은 지연이 늘지 않는다. 대신 그려 놓고 한 번도 보여주지 않은 채 버리는 프레임이 생긴다.

## 같은 원리가 게임 상태의 갱신 순서 의존성을 없앤다

이중 버퍼는 그래픽스 전용 기법이 아니다. 게임 로직에서 오브젝트들이 서로의 상태를 읽고 쓰면서 순서대로 갱신될 때도 같은 문제가 생긴다. 이때 "읽는 쪽"은 디스플레이가 아니라 같은 프레임에 뒤늦게 갱신되는 다른 오브젝트다.

배우 셋이 원형으로 서서 맞으면 바라보는 상대를 때리는 상황을 보자.

```csharp
public void Update()
{
    if (_slapped)
    {
        Console.WriteLine($"{Name} slaps {Facing.Name}");
        Facing.Slap();      // 상대의 상태를 즉시 바꾼다
    }
    _slapped = false;
}
```

Harry → Baldy → Chump → Harry 순서로 서 있고, Harry가 처음에 맞은 상태라고 하자.

- 갱신 순서가 Harry, Baldy, Chump이면 연쇄가 한 프레임 안에 한 바퀴 돌고, 이 일이 매 프레임 반복된다.
- 순서가 Chump, Baldy, Harry이면 때리는 시점에 상대의 갱신이 이미 끝나 있다. 그래서 한 프레임에 한 단계씩만 전파된다.

같은 규칙, 같은 초기 상태인데 결과가 갱신 순서에 따라 달라진다. 원인은 같은 프레임 안에서 쓴 값을 뒤에 실행되는 쪽이 즉시 읽기 때문이다.

해법도 같다. 상태를 이번 프레임에 읽는 current와 이번 프레임의 결과를 기록하는 next로 나누고, 모든 오브젝트의 갱신이 끝난 뒤 일괄 교체한다. 그러면 갱신 순서와 무관하게 결과는 "한 프레임에 한 단계 전파"로 통일된다. 이 과정은 [[갱신 순서에 따라 게임 상태 결과가 달라지는 문제를 이중 버퍼로 해결하는 방법]]에서 다룬다. 같은 구조가 물리 시뮬레이션, 셀룰러 오토마타, AI 영향력 맵처럼 "모든 개체가 같은 시점의 세계를 보고 판단해야 하는" 시스템에 그대로 쓰인다.

## next를 비울지는 쓰기 방식이 정한다

상태 이중 버퍼에서 흔한 실수는 교체 후 next를 비우지 않는 것이다.

```csharp
public void Swap()
{
    _current = _next;
    _next = false;   // 빠뜨리면 한 번 맞은 배우는 영원히 맞은 상태가 된다
}
```

비우기를 빠뜨리면 한 번 `true`가 된 next가 매 프레임 current로 다시 복사된다. 피격이 사라지지 않고 누적되어, 결국 모든 배우가 매 프레임 때리게 된다. 순서도 중요하다. 복사보다 비우기를 먼저 하면 이번 프레임에 기록한 결과가 사라진다. [[상태 이중 버퍼의 Swap에서 next를 비우지 않으면 생기는 버그]]

그렇다고 항상 비워야 하는 것은 아니다. 1000×1000 격자의 셀룰러 오토마타처럼 매 프레임 모든 칸을 `_next[x, y] = Rule(...)`로 무조건 덮어쓰면, next에 남은 두 프레임 전의 값은 읽히기 전에 전부 지워진다. 이 경우에는 두 배열의 참조만 맞바꾸면 되고, 셀 수와 무관하게 O(1)로 교체된다. 매 프레임 100만 칸을 복사하거나 비우는 비용을 피할 수 있다.

기준은 쓰기 단계의 성격이다.

- **전체 덮어쓰기:** 모든 원소를 무조건 새 값으로 쓴다. 비우기가 필요 없다.
- **부분 쓰기 또는 누적 쓰기:** 이벤트가 있을 때만 일부 원소를 쓰거나(`Slap()`처럼), `|=`, `+=`로 누적한다. 쓰이지 않은 원소의 잔재가 이번 결과로 오인되므로 교체 후 비워야 한다.

[[대형 격자 이중 버퍼에서 참조 교체를 고르는 이유와 next 비우기가 필요한 기준]]

## 연쇄를 한 프레임에 끝내려면 프레임 안에서 교체를 반복한다

이중 버퍼는 순서 독립성을 주는 대신 전파 속도를 프레임당 한 단계로 묶는다. 폭탄 100개가 일렬로 연쇄 폭발하면 60fps 기준으로 끝까지 약 1.7초가 걸린다. 연쇄 전체가 같은 프레임에 끝나야 하면서도 순서 독립성은 유지해야 한다면, "갱신 → 교체"를 프레임당 한 번이 아니라 한 프레임 안에서 더 이상 새 변화가 없을 때까지 반복하면 된다. 반복 한 번이 연쇄 한 단계에 해당하므로 결과는 순서와 무관하다.

비용은 반복 횟수다. 매 반복마다 N개 전부를 검사하면 비용은 N × 연쇄 길이가 되고, 일렬 연쇄 같은 최악의 경우 O(N²)이 된다. 이 비용이 한 프레임에 몰리므로 스파이크가 생긴다. 실무에서는 반복 횟수에 상한을 두고, 남은 전파는 다음 프레임으로 넘기는 안전장치를 함께 둔다.

더 효율적인 방법은 이번 단계에 새로 터진 폭탄만 다음 단계의 검사 대상으로 삼는 것이다. 이는 단계(레벨) 단위로 진행하는 BFS와 같은 구조다. BFS의 한 레벨이 이중 버퍼의 한 세대(교체 한 번)에 해당하고, 각 폭탄을 한 번씩만 처리하므로 O(N + 간선)으로 끝난다. 같은 폭탄이 두 번 터지지 않도록 방문 표시가 필요하다는 점도 BFS와 같다. 최종적으로 터지는 폭탄의 집합은 도달 가능성으로 정해지므로 처리 순서와 무관하다. 다만 피해 누적이나 효과음 순서처럼 폭발마다의 부수 효과가 처리 순서에 민감하다면, 레벨 단위로 끊어서 처리해 결정성을 지켜야 한다. ## 남은 경계: 두 스레드 사이의 교체

메인 스레드가 다음 프레임 상태를 쓰고 렌더 스레드가 직전 프레임 상태를 읽는 구조에서도 이중 버퍼가 쓰인다. 이때는 참조 교체가 원자적이라는 것만으로는 부족하다. 쓰는 쪽은 기록을 끝냈고 읽는 쪽은 읽기를 끝냈다는 두 조건이 모두 만족되는 동기화 지점에서만 교체해야 한다. 그렇지 않으면 한쪽이 아직 읽고 있는 버퍼에 다른 쪽이 쓰기 시작해서 처음의 문제가 다시 나타난다. 이 주제는 이번 노트의 범위 밖이다.
