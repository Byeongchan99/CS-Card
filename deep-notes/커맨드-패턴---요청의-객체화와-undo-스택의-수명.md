## 요청을 값으로 만들지 않으면 실행 시점을 고를 수 없다

버튼을 눌렀을 때 플레이어가 움직이는 코드를 가장 짧게 쓰면 UI 쪽이 플레이어를 직접 호출한다.

```csharp
// Invoker가 Receiver를 직접 안다
if (Input.GetKeyDown(KeyCode.Space))
    _player.Jump();
```

이 코드에는 "점프한다"는 요청이 어디에도 값으로 존재하지 않는다. 요청은 호출문이라는 문법 구조로만 표현되고, 호출문은 실행되는 순간 사라진다. 그래서 요청을 저장할 수도, 다른 곳으로 넘길 수도, 나중에 실행할 수도, 되돌릴 수도 없다.

커맨드 패턴은 이 호출을 객체로 승격시킨다. `Execute()` 하나를 가진 인터페이스를 두고, 요청마다 그 구현 객체를 만든다. Invoker는 `ICommand`만 알고, 어떤 Receiver에게 어떤 일이 가는지는 모른다.

```csharp
public interface ICommand
{
    void Execute();
    void Undo();
}
```

Invoker와 Receiver 사이에 끼워 넣는 것은 이 `ICommand` 추상과 그 구현 객체다. 결합이 끊어지는 방향이 중요하다. 입력 처리기는 플레이어 타입을 컴파일 타임에 참조하지 않고, 플레이어는 자기가 입력으로 호출되는지 AI로 호출되는지 리플레이로 호출되는지 알지 못한다.

여기서 열리는 기능들은 전부 "요청이 값이 되었다"는 하나의 성질에서 파생된다. 저장할 수 있으니 undo 스택과 리플레이 로그가 되고, 전달할 수 있으니 큐잉·지연 실행·네트워크 전송이 되고, 조작할 수 있으니 여러 커맨드를 하나로 묶는 매크로 커맨드가 된다. undo/redo만 커맨드 패턴의 목적으로 기억하면 큐잉과 로깅 쪽 용례를 놓친다.

## 커맨드는 실행 시점에 자기 완결적이어야 한다

큐에 넣어두고 나중에 실행한다는 말은, 실행에 필요한 모든 정보가 커맨드 객체 안에 이미 담겨 있어야 한다는 뜻이다. 필드 단위로 보면 두 종류다.

하나는 Receiver 참조 — 누구에게 보내는 요청인지. 다른 하나는 인자 — 무엇을 얼마나 하는지. 이동 명령이라면 방향과 거리가 여기 들어간다.

```csharp
public class MoveCommand : ICommand
{
    private readonly Transform _target;   // Receiver
    private readonly Vector3 _direction;  // 인자
    private readonly float _distance;     // 인자

    public MoveCommand(Transform target, Vector3 direction, float distance)
    {
        _target = target;
        _direction = direction;
        _distance = distance;
    }

    public void Execute() => _target.position += _direction * _distance;
    public void Undo() => _target.position -= _direction * _distance;  // 이 구현은 틀린다
}
```

생성 시점에 인자를 고정한다는 것은 "요청이 발생한 순간의 의도"를 동결한다는 의미다. 실행이 3프레임 뒤든 리플레이 재생 시점이든 같은 의도가 재현된다. 인자를 필드로 갖지 않고 실행 시점에 전역 상태에서 읽어오면 커맨드는 자기 완결성을 잃고 큐잉과 리플레이가 모두 깨진다.

undo까지 지원하려면 필드가 하나 더 필요하다. 위 코드의 `Undo()`가 왜 부족한지가 다음 문제다.

## 역연산 undo는 명령한 값과 실제 결과가 갈리는 순간 깨진다

`Undo()`를 "저장해둔 방향의 반대로 같은 거리만큼"으로 구현하는 방식을 역연산(inverse operation) 방식이라 한다. 이 방식은 실행 직후 곧바로 undo하는 경우에만 안전하다.

깨지는 상황은 두 갈래다.

첫째, 실행 이후 외부 요인이 상태를 바꾼 경우다. 이동 명령이 끝난 뒤 넉백을 맞거나 물리 시뮬레이션이 위치를 옮기거나 다른 커맨드가 같은 대상을 건드리면, 현재 위치에서 역벡터를 더한 결과는 실행 전 위치가 아니다.

둘째, 외부 개입이 전혀 없어도 깨진다. 이동이 벽 충돌로 도중에 막혔다면 실제 변위는 명령한 거리보다 작다. 그런데 `Undo()`는 명령한 거리를 기준으로 되돌리므로 원래보다 뒤로 밀려난다. 이쪽이 더 근본적인 원인이다. 역연산 방식은 "명령한 값 = 실제로 일어난 결과"를 암묵적으로 가정하지만, 실제 게임 로직에서 이 가정은 클램프, 충돌, 상한선, 반올림 때문에 흔히 깨진다.

그래서 실무 기본형은 역연산이 아니라 실행 전 상태 스냅샷이다. 커맨드가 변경 전 위치를 직접 들고, undo는 그 값을 그대로 대입한다. 역연산은 연산이 수학적으로 정확히 가역이고 대상이 그 커맨드만 건드리는 좁은 조건에서만 쓴다. 메모리는 스냅샷이 더 쓰지만, 역연산의 오차는 누적되어 undo를 여러 번 했을 때 상태가 서서히 어긋나는 형태로 나타난다.

## 스냅샷은 시점과 깊이를 둘 다 맞춰야 한다

스냅샷 방식에는 두 가지 함정이 있다.

시점 — 기록은 생성자가 아니라 `Execute()` 안에서, 상태를 변경하기 직전에 해야 한다. 생성자에서 기록하면 커맨드가 큐에서 대기하는 동안 대상의 위치가 바뀌어 기록이 낡은 값이 된다. 커맨드가 만들어지는 시점과 실행되는 시점을 분리하는 것이 이 패턴의 장점인데, 그 분리 때문에 기록 시점도 실행 쪽으로 붙어야 한다.

깊이 — 기록한 것이 스냅샷인지 살아 있는 대상으로의 창구인지 구분해야 한다. `Transform`을 필드에 담으면 그것은 상태의 복사가 아니라 객체로의 참조다. 나중에 읽으면 이미 변한 값을 읽는다. 기록해야 하는 것은 `transform.position`이라는 `Vector3` 값이다.

```csharp
public void Execute()
{
    _previousPosition = _target.position;  // 변경 직전, 값으로 복사
    _target.position += _direction * _distance;
}

public void Undo() => _target.position = _previousPosition;
```

여기서 "값 타입이면 안전하다"로 정리하면 반만 맞다. `Vector3`은 struct라서 대입이 곧 복사라 안전하지만, 값 타입이라도 내부에 배열이나 클래스 참조를 품고 있으면 대입은 얕은 복사이고 내부 데이터는 여전히 공유된다. 판단 기준은 값 타입 여부가 아니라 저장된 내용이 이후의 변경과 분리되는가다. 컬렉션이나 복합 상태를 스냅샷할 때는 명시적으로 깊은 복사를 해야 한다.

## undo 스택은 Receiver의 수명을 붙잡는다

커맨드가 실행 전 상태를 들고 있다는 것은 그 객체가 undo 스택에 남아 있는 동안 계속 살아 있다는 뜻이다. 그리고 커맨드는 Receiver 참조도 함께 들고 있다. 그래서 undo 스택은 대상 오브젝트의 수명을 간접적으로 붙잡는다.

유니티에서는 이것이 두 가지 문제로 나타난다.

첫째, 대상이 파괴되어도 참조는 남는다. `UnityEngine.Object`는 C# 래퍼와 네이티브 객체 두 겹으로 존재하고, `Destroy`는 네이티브 쪽만 없앤다. 커맨드가 잡고 있는 래퍼 객체는 그대로 있으므로 참조는 비어 있지 않은데 대상은 실재하지 않는 [[유니티의 fake null은 무엇이고 왜 발생하는가]] 상태가 된다. undo를 시도하면 대상 없이 상태를 되돌리려는 셈이 된다.

문제는 이 상태를 어떤 null 체크로 잡느냐에 따라 결과가 갈린다는 데 있다. `UnityEngine.Object`가 오버로딩한 `==`는 네이티브 파괴 여부를 확인해 파괴된 객체를 null로 보고해 준다. 반면 `is null`과 `ReferenceEquals`는 연산자 오버로딩을 거치지 않으므로 래퍼가 힙에 있는 한 "살아 있다"고 판정한다. undo 직전 유효성 검사에서 이 둘을 섞어 쓰면 파괴된 대상에 접근하는 경로가 열린다.

```csharp
public void Undo()
{
    if (_target == null) return;  // 오버로딩된 ==, fake null을 잡는다
    // if (_target is null) return;  // 패턴 매칭은 오버로딩을 우회해 통과시킨다
    _target.position = _previousPosition;
}
```

둘째, 파괴가 없어도 메모리가 쌓인다. 수백 스텝짜리 undo 스택이 있는 에디터 툴이나 리플레이 시스템에서 상주하는 것은 커맨드 객체 자체, 각 커맨드가 보관한 스냅샷 상태, 그리고 Receiver 참조 전부다. 파괴된 대상의 래퍼도 커맨드가 잡고 있는 동안 수거되지 않으므로, 네이티브 메모리는 풀렸는데 관리 힙에는 쓸모없는 래퍼가 계속 남는다. 스택이 길수록 이 누수는 선형으로 늘어난다.

## 참조를 ID로 바꾸면 무엇이 풀리고 무엇이 남는가

설계 단계의 해법은 커맨드가 Receiver를 직접 참조하지 않고 안정적인 식별자로 들고, 실행·undo 시점에 레지스트리를 통해 해석(resolve)하는 것이다.

```csharp
public class MoveCommand : ICommand
{
    private readonly int _targetId;       // 참조가 아니라 식별자
    private readonly Vector3 _delta;
    private Vector3 _previousPosition;

    public void Undo()
    {
        if (!ObjectRegistry.TryGet(_targetId, out Transform target)) return;
        target.position = _previousPosition;
    }
}
```

이렇게 하면 커맨드가 유니티 객체 수명에 묶이지 않는 순수 데이터가 된다. 래퍼를 붙잡지 않으니 누수가 사라지고, 직렬화가 가능해져 리플레이 파일로 저장하거나 네트워크로 전송하거나 에디터 세션을 넘어 undo 히스토리를 보존하는 것도 가능해진다. 결정론적 리플레이와 롤백 넷코드가 커맨드를 이 형태로 다루는 이유가 여기 있다.

대가는 있다. ID를 객체로 바꾸는 조회 비용이 매 실행마다 붙고, 조회가 실패했을 때의 정책을 설계자가 직접 정해야 한다. 조용히 건너뛸지, 스택에서 제거할지, 그 지점 이후의 히스토리를 무효화할지는 툴의 성격에 따라 다르다. 이 정책을 정하지 않으면 fake null 문제가 "조회 실패" 문제로 이름만 바뀐 것이 된다.

## 삭제의 undo는 ID 안정성까지 복원해야 한다

ID 방식이 참조 방식과 질적으로 다른 지점은 객체를 없애고 되살리는 시나리오에서 드러난다. 오브젝트를 이동한 뒤 삭제하고 undo를 두 번 누르는 경우를 보자. 첫 undo가 삭제를 취소해 오브젝트를 되살리고, 두 번째 undo가 이동을 취소해야 한다.

이동 커맨드는 식별자로 대상을 찾는다. 그러므로 두 번째 undo가 성공하려면 되살아난 오브젝트가 삭제 전과 동일한 식별자를 가져야 한다. 참조 방식이라면 되살린 것은 완전히 새로운 객체이므로 옛 참조로는 절대 닿지 못하고, ID 방식이어도 새 ID가 발급되면 마찬가지로 끊어진다.

따라서 삭제 커맨드는 두 가지를 져야 한다. 삭제 시점에 대상을 재구성할 만큼의 상태를 스냅샷으로 남기는 것, 그리고 undo에서 복원한 객체에 원래 식별자를 다시 부여하고 레지스트리에 그 매핑으로 재등록하는 것이다. 여기서도 "역연산이 아니라 실행 전 상태를 저장한다"는 원칙이 그대로 적용된다. 삭제의 역연산은 생성이지만, 무엇을 생성할지는 스냅샷 없이 알 수 없다.

한 겹 더 있다. 식별자 발급기 쪽 제약이다. 삭제할 때 그 ID를 재사용 가능 풀에 반납해 버리면, undo 전에 만들어진 새 오브젝트가 그 번호를 선점해 복원 시점에 충돌이 난다. undo 히스토리에 그 ID를 쓰는 커맨드가 남아 있는 동안 번호는 예약 상태로 묶여 있어야 하고, 히스토리가 잘려 나갈 때 비로소 회수된다. 참조를 ID로 바꾸는 것은 객체 수명 관리를 ID 수명 관리로 옮기는 일이기도 하다. GUID처럼 재사용하지 않는 식별자를 쓰면 이 문제가 사라지는 대신 식별자 자체의 크기와 조회 비용이 커진다.
