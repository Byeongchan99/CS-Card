## 클로저는 왜 필요한가

이벤트나 콜백을 등록하는 코드는 이런 모양을 자주 띤다.

```csharp
void Setup()
{
    int counter = 0;
    button.onClick += () => counter++;
}
```

`Setup`은 버튼에 람다를 하나 걸어두고 곧바로 리턴한다. 그런데 이 람다는 `Setup`이
끝난 한참 뒤, 유저가 버튼을 누를 때마다 실행된다. 이때 람다는 여전히 `counter`를
증가시킨다. 즉 함수가 자기 바깥의 지역 변수를 붙잡아 두고, 그 함수가 사는 동안
변수도 같이 살려두는 동작이 필요하다. 함수와 그 함수가 붙잡은 변수들이 한 덩어리로
묶인 것을 클로저라고 부른다.

문제는 이게 순진하게 생각하면 불가능하다는 데 있다. 지역 변수 `counter`는 `Setup`의
스택 프레임에 놓인다. 스택 프레임은 함수가 리턴하면 사라진다. 사라진 프레임의
변수를 나중에 실행되는 람다가 어떻게 계속 건드릴 수 있는가. 스택에 있는 한 이건
성립할 수 없다.

## 스택이 안 되면 힙으로 — 그리고 무엇이 그것을 살려두는가

논리 사슬은 단순하다. 스택은 함수가 끝나면 사라지니까 `counter`를 스택에 두면 안 된다.
그러면 힙에 둔다. 힙에 있는 객체는 살아있는 참조가 하나라도 있는 한 GC가 수거하지
않는다. 그러니 `counter`를 힙에 있는 어떤 객체의 필드로 만들고, 그 객체를 누군가
계속 참조하게 하면 `Setup`이 끝나도 `counter`는 살아남는다.

여기서 빠지기 쉬운 칸이 "무엇이 그 힙 객체를 참조하는가"다. 답은 람다 자신이다.
람다는 델리게이트 객체가 되어 `button.onClick`에 등록된다. 그 델리게이트가 힙 객체를
참조하고, 버튼이 살아있는 한 델리게이트가 살아있고, 델리게이트가 살아있는 한 힙
객체가 살아있고, 따라서 `counter`도 살아있다. 참조의 사슬이 스택 프레임의 소멸과
무관하게 변수를 붙들어 두는 것이다.

## 컴파일러가 실제로 만드는 것 — DisplayClass

이 "힙에 있는 어떤 객체"를 C# 컴파일러가 직접 만들어낸다. 소스에는 없지만 컴파일
결과물에는 존재하는 숨은 클래스이고, 이름은 관례적으로 `<>c__DisplayClass...`
형태다. 포획된 지역 변수는 이 클래스의 필드가 되고, 람다 본문은 이 클래스의
메서드가 된다. 원래 코드의 지역 변수 접근은 전부 이 객체의 필드 접근으로 치환된다.

위 코드는 개념적으로 이렇게 다시 쓰인 것과 같다.

```csharp
// 컴파일러가 생성하는 숨은 클래스
sealed class DisplayClass
{
    public int counter;                 // 포획된 지역 변수가 필드가 된다
    public void Lambda() { counter++; } // 람다 본문이 메서드가 된다
}

void Setup()
{
    var env = new DisplayClass();       // 힙에 할당
    env.counter = 0;                    // "지역 변수" 초기화가 필드 대입이 된다
    button.onClick += env.Lambda;       // 델리게이트가 env를 참조한다
}
```

이제 스택에는 `counter`라는 정수가 없다. `env`라는 참조 하나만 있고, 실제 `counter`
값은 `env`가 가리키는 힙 객체 안에 있다. `Setup`이 리턴해서 스택의 `env` 참조가
사라져도, `button.onClick`에 등록된 델리게이트가 같은 `env` 객체를 참조하므로
객체는 살아남는다. 버튼을 누르면 `env.Lambda()`가 돌고 `env.counter`가 증가한다.

이름의 유래도 짚어둘 만하다. DisplayClass의 "Display"는 화면 출력과 무관하고,
디버거 팀이 쓰던 용어에서 왔다. 디버깅할 때 포획된 변수를 이상한 이름의 클래스
필드가 아니라 원래의 지역 변수처럼 보여주기 위한 특별 취급 대상이라는 의미다.

## 값 복사가 아니라 변수 자체의 승격이다

흔한 오해가 "람다가 `counter`의 값을 복사해 간다"는 것이다. 아니다. 람다는 값을
복사하는 게 아니라 변수 자체를 공유한다. 위 구조를 보면 명확하다. 스택에 정수를
두고 그 값을 어딘가로 복사하는 게 아니라, 애초에 그 변수가 힙 객체의 필드로
"승격(hoisting)"된 것이다. 그래서 `Setup` 안에서 람다 등록 후에 `counter`를 또
건드리면, 람다가 나중에 보는 값에도 그 변화가 반영된다. 둘이 같은 필드를 보기
때문이다.

같은 스코프의 람다가 여럿이면 이들은 하나의 DisplayClass 인스턴스를 공유한다.
서로 다른 람다가 같은 지역 변수를 포획하면, 그 변수는 공유된 한 객체의 한 필드다.
그래서 한 람다가 바꾼 값을 다른 람다가 본다. 클로저가 "환경을 공유한다"는 말이
이 뜻이다.

## 게임 개발에서의 함정 — 숨은 힙 할당

이 구조가 편리하지만 공짜가 아니다. 지역 변수를 포획하는 람다를 만들 때마다
DisplayClass 인스턴스가 힙에 할당된다. 소스 코드에는 `new`가 없어서 눈에 안 보이는
할당이다. `Update` 같은 매 프레임 도는 경로에서 지역 변수를 포획하는 람다를
만들면, 프레임마다 이 숨은 객체가 쌓이고 결국 GC 스파이크로 돌아온다. 앞서 다룬
[[GC 스파이크와 프레임 예산]]의 전형적 원인 중 하나가 바로 이 포획 할당이다.

완화 방향은 세 가지다. 첫째, 아무 지역 변수도 포획하지 않는 람다는 상태가 없으므로
컴파일러가 델리게이트 인스턴스를 static으로 한 번만 만들어 캐싱한다. 즉 포획이
없으면 DisplayClass 할당도, 프레임마다의 델리게이트 할당도 생기지 않는다. 그래서
매 프레임 만들어지는 콜백은 가능하면 지역 변수를 안 붙잡게 짜는 게 유리하다.
둘째, 포획이 꼭 필요하면 람다를 루프 안이 아니라 한 번만 생성되는 위치로 끌어올려
같은 델리게이트를 재사용한다. 셋째, 인스턴스 필드만 참조하고 지역 변수는 안 붙잡게
바꾸면 DisplayClass는 안 생기고 델리게이트 하나만 생긴다.

주의할 함정 하나 더. 한 스코프에서 람다가 지역 변수 하나만 포획해도, 컴파일러는
그 스코프의 포획 대상 지역 변수들을 하나의 DisplayClass에 함께 묶는다. 그래서
가벼워 보이는 포획이 예상보다 큰 객체를 살려두거나, 의도치 않은 변수까지 수명이
늘어나는 일이 생긴다. 할당을 줄이려면 포획 범위를 좁은 블록 스코프로 격리해 필요한
변수만 승격되게 하는 기법을 쓴다.
