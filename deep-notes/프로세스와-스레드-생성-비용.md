## 왜 이 구분이 중요한가

프로세스와 스레드의 생성 비용 차이는 그냥 시험용 암기 항목이 아니다. 서버가 요청마다 프로세스를 띄울지 스레드를 띄울지, 게임에서 백그라운드 작업(에셋 로딩, 경로탐색, 네트워크)을 어떻게 분리할지가 여기서 갈린다. "왜 스레드가 가벼운가"를 물리 메모리와 페이지 테이블 수준까지 설명할 수 있으면, 그 위에 얹힌 동기화·경쟁 상태·CoW 같은 주제가 전부 한 줄기로 꿰진다.

## 스레드가 가벼운 진짜 이유

프로세스의 주소 공간은 코드·데이터·힙·스택으로 나뉘고, 한 프로세스 안의 스레드들은 이 중 코드·데이터·힙을 공유하고 스택만 따로 가진다. 여기까지는 흔히 아는 그림인데, 두 가지가 더 있다.

스레드가 개별적으로 갖는 건 스택만이 아니라 실행 문맥 전체다. 각 스레드는 자기 레지스터 세트(프로그램 카운터 PC, 스택 포인터 SP 포함)와 커널 안의 스레드 제어 블록(TCB)을 가진다. 스레드를 "실행 흐름 하나"로 정의하는 건 이 실행 문맥 때문이지, 스택 때문만이 아니다.

그리고 비용의 핵심 — 프로세스가 비싼 건 힙/데이터의 내용을 복사해서가 아니다(뒤의 CoW가 그걸 안 하니까). 비싼 건 독립된 주소 공간을 만들기 위한 페이지 테이블 구조 복사, PCB 생성, 스케줄링 정보 세팅 같은 커널 자료구조 작업이다. 스레드는 주소 공간을 공유하니 이 페이지 테이블 작업을 통째로 건너뛴다. 이게 "가볍다"의 실체다.

## Copy-on-Write — 복사를 미루는 기술

`fork()`가 부모의 힙·데이터·스택을 즉시 복사한다면 프로세스 생성은 지금보다 훨씬 느릴 것이다. 그래서 커널은 복사를 쓰기 시점까지 미룬다.

fork 직후: 자식은 새 페이지 테이블을 받지만, 그 엔트리(PTE)들은 부모와 같은 물리 페이지를 가리킨다. 가상 주소 공간은 논리적으로 분리됐지만 물리 메모리는 공유 상태다. 그리고 결정적으로, 커널은 공유되는 페이지들의 PTE를 **양쪽 다 읽기 전용(write-protected)**으로 바꿔둔다. 원래 쓰기 가능하던 페이지를 일부러 막는 이 조작이 나중의 트리거가 된다.

누군가 그 페이지에 쓰려고 하면:

```
1. CPU가 write-protected 페이지에 store 실행
2. MMU가 쓰기 권한 없음 감지 → protection fault (트랩)
3. 커널 page fault 핸들러 진입
4. "진짜 접근 위반 vs CoW 페이지" 판별
   → VMA는 쓰기 가능인데 PTE만 읽기 전용이면 CoW로 판단
5. 새 물리 페이지 할당 + 기존 내용 복사
6. 해당 프로세스 PTE를 새 페이지로 교체 + 쓰기 권한 복원
7. 트랩 걸렸던 store 재실행 → 성공
```

4번의 판별이 CoW 설계의 관건이다. 커널은 폴트가 났을 때 "이게 프로그램 버그(권한 없는 곳에 접근)인지, 내가 일부러 걸어둔 CoW 트랩인지"를 구분해야 한다. 그 판단 기준이 VMA와 PTE의 불일치다 — 가상 메모리 영역 메타데이터상으로는 쓰기 가능한데 실제 PTE만 읽기 전용이면, 이건 CoW라는 신호다.

## CoW가 손해 보는 경우와 fork → exec

CoW는 "쓰기가 드물다"는 가정에 기댄다. 부모/자식이 대부분 읽기만 하면 물리 페이지를 계속 공유하니 큰 이득이다. 하지만 fork 직후 자식이 방대한 페이지에 전부 쓰기를 하면, 어차피 전부 복사될 페이지를 "폴트 → 트랩 → 핸들러 → 복사"라는 비싼 우회로로 하나씩 복사하게 된다. 이 경우엔 eager copy보다 폴트 오버헤드만큼 더 느리다.

이 "자식이 곧바로 전부 갈아엎는" 케이스의 대표가 `fork()` 직후 `exec()`다. 셸이 명령어를 실행하는 전형적 패턴인데, exec는 자식의 주소 공간을 통째로 새 프로그램으로 교체한다. 그러면 fork가 힘들여 해둔 작업 — 페이지 테이블 복사, 전 페이지 write-protect — 이 통째로 헛수고가 된다.

여기서 회피의 초점이 미묘하다. "쓰기를 줄이자"가 아니라 공유 준비 자체를 건너뛰자가 정답이다. 운영체제 차원에서는 `vfork()`(페이지 테이블조차 복사 안 하고 부모 주소 공간을 잠깐 빌림), 그리고 이식성·안전성을 갖춘 현대적 대안인 `posix_spawn()`이 이 역할을 한다. 프로그래머 차원에서는 무거운 프로세스에서 직접 fork → exec 하지 말고, 미리 가벼운 헬퍼 프로세스를 띄워 거기서 spawn하는 패턴을 쓴다(부모가 가벼우면 CoW로 걸 페이지도 적으니까).

## 실무 — 게임 개발과의 연결

게임 클라이언트 자체는 보통 멀티프로세스보다 멀티스레드를 쓴다. 렌더 스레드, 잡 시스템 워커, 에셋 스트리밍, 네트워크 스레드가 전부 한 주소 공간을 공유한다 — 앞서 본 "스레드가 힙/데이터를 공유해서 가볍다"가 바로 이 설계의 근거다. 반대로 공유하기 때문에 데이터 경쟁이 생기고, 그래서 유니티의 C# Job System은 아예 공유 데이터 접근을 컴파일 타임에 제약하는 방식(NativeContainer, safety system)으로 이 문제를 우회한다.

CoW와 fork → exec는 클라이언트보다 서버 쪽에서 직접 만난다. 게임 서버, 빌드 파이프라인, 툴 자동화가 자식 프로세스를 대량으로 띄울 때 fork의 CoW 비용과 spawn 선택이 실제 성능 문제로 나타난다. 클라이언트에서도 간접적으로는, "무거운 상태를 공유하는 실행 흐름을 값싸게 늘리는 것"이라는 CoW의 발상 자체가 프리팹 인스턴싱이나 [[오브젝트 풀링은 무엇이고 어떻게 GC 부담을 줄이는가]] 같은 "복제를 미루고 공유하다가 필요할 때만 분리한다"는 패턴과 사고방식이 닮아 있다.
