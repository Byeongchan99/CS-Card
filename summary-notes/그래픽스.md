## 변환 파이프라인과 지오메트리

3D 정점이 화면 좌표로 바뀌고 지오메트리가 만들어지는 파이프라인 전반부.

### 모델 → 뷰 → 투영 변환 ★

3D 점 하나가 화면 픽셀이 되기까지 좌표의 기준을 여러 번 바꾸는 과정. 도구는 4×4 행렬. 정점 셰이더는 모델·뷰·투영 행렬을 곱해 클립 좌표까지만 만들고, 그 뒤 클리핑·w 나눗셈·뷰포트 변환은 셰이더 밖 고정 기능 하드웨어가 처리. 셰이더 코드에 `/w`가 안 보이는 이유.

| 단계 | 변환 | 하는 일 |
| --- | --- | --- |
| 모델 M | 로컬 → 월드 | 물체를 월드의 위치·회전·크기로 배치. 행렬은 `T * R * S`로 쓰고 오른쪽부터 적용돼 크기 → 회전 → 이동 순 |
| 뷰 V | 월드 → 뷰 | 카메라가 원점에서 정해진 축(OpenGL 관례 -Z)을 보도록 기준을 옮김. 카메라 월드 변환의 역행렬 |
| 투영 P | 뷰 → 클립 | 시야 공간을 정육면체로 펼 준비. 원근이면 카메라 거리를 w에 담아 둠 |

- TRS 순서 — 회전·크기는 원점을 중심으로 동작해서 물체가 아직 자기 원점에 있을 때 먼저 해야 함. 이동을 먼저 하면 회전이 월드 원점을 축으로 돌아 제자리 회전이 아니라 공전이 됨
- NDC — x·y는 -1에서 1, z 범위는 API마다 다름(OpenGL은 -1에서 1, D3D·Vulkan은 0에서 1). 3D를 2D로 납작하게 만드는 게 아니라 z를 남긴 채 펴는 것이라 깊이 테스트에 그대로 쓰임

숫자로 따라가면 원근감이 어디서 생기는지 보임. 아래는 Unity `Matrix4x4`로 계산한 OpenGL 관례 예시(유니티 카메라가 실제로 쓰는 뷰 행렬은 손잡이 방향 때문에 z 부호를 한 번 더 뒤집음).

```csharp
// 물체 월드 (2,0,0) · 카메라 월드 (0,0,10)에서 -Z 방향 · 세로 FOV 90° · near 1 · far 100
Matrix4x4 M = Matrix4x4.TRS(new Vector3(2, 0, 0), Quaternion.identity, Vector3.one);
Matrix4x4 V = Matrix4x4.TRS(new Vector3(0, 0, 10), Quaternion.identity, Vector3.one).inverse;
Matrix4x4 P = Matrix4x4.Perspective(90f, 1f, 1f, 100f);

Vector4 world = M * new Vector4(1, 1, 0, 1);   // (3, 1, 0, 1)
Vector4 view  = V * world;                     // (3, 1, -10, 1)
Vector4 clip  = P * view;                      // (3, 1, 8.18, 10)  정점 셰이더 출력, w = 거리
Vector4 ndc   = clip / clip.w;                 // (0.3, 0.1, 0.818)

Vector4 far   = P * new Vector4(3, 1, -20, 1); // 같은 x·y, 두 배 먼 점 → w = 20
// far / far.w = (0.15, 0.05, 0.919)  화면 중앙에 두 배 가까워짐 = 멀수록 작아 보임
```

동차좌표 (x, y, z, w) — 3×3 행렬은 원점을 늘 원점으로 보내서 이동을 담지 못함. w를 붙여 4×4로 만들고 넷째 열에 이동량을 두면 회전·크기·이동이 곱 하나에 담김. 이 w가 투영 뒤엔 카메라 거리로 재활용돼 원근 나눗셈을 맡음.

- 점은 w=1 — 넷째 열(이동)이 더해짐
- 방향(법선·광선)은 w=0 — 이동이 0배라 무시되고 회전·크기만 받음. 방향은 평행 이동해도 같은 방향이어야 하므로 맞는 동작

```csharp
M * new Vector4(0, 0, 1, 1);   // (2, 0, 1, 1)  점: 이동 적용
M * new Vector4(0, 0, 1, 0);   // (0, 0, 1, 0)  방향: 이동 무시
```

클리핑이 w 나눗셈 앞에 오는 이유 — 카메라 뒤의 점은 w가 음수라 나누면 부호가 뒤집혀 앞쪽 엉뚱한 자리에 찍히고, 카메라 평면 위의 점은 w=0이라 나눌 수조차 없음. 그래서 나누기 전 클립 공간에서 잘라냄("클립 좌표"라는 이름의 유래).

공간을 셋으로 나누는 건 필수가 아님 — CPU에서 미리 곱한 MVP 하나만 넘겨도 결과는 같고 실제로 흔함. 그래도 나눠 두는 이유:

- 갱신 시점이 다름 — M은 물체마다, V는 카메라가 움직일 때, P는 FOV·화면비가 바뀔 때만. 바뀐 것만 다시 계산
- 중간 공간이 필요한 계산 — 라이팅은 빛과 법선을 같은 공간(월드·뷰)에 두고 하고, 절두체 컬링·클리핑은 클립 공간 기준. 하나로 합치면 중간 좌표를 못 꺼냄

카메라를 원점에 두는 이유:

- 뒷단계 공식 고정 — 투영 행렬은 눈이 원점에서 한 축을 본다고 가정해 렌즈(FOV·화면비·near·far)만으로 정해짐. 카메라의 위치·방향은 전부 V가 흡수
- 연산량은 같음 — 카메라를 옮기는 것과 세상을 반대로 미는 것은 같은 역행렬 곱
- 정밀도는 뷰 변환만으로 좋아지지 않음 — 월드 좌표가 이미 큰 float(예: 100000.0)이면 잃은 자릿수는 GPU에서 뷰 변환해도 안 돌아옴. 먼 곳의 지터를 막는 건 카메라 상대 렌더링: CPU에서 double로 `V * M`을 먼저 곱해 큰 이동량끼리 상쇄시킨 뒤 float으로 넘기거나, 월드 원점을 카메라 쪽으로 옮김

원근 vs 직교 — 시선이 한 점(눈)에서 퍼지면 절두체(잘린 피라미드), 평행하면 직육면체.

| | 원근 | 직교 |
| --- | --- | --- |
| 시야 공간 | 절두체(잘린 피라미드) | 직육면체 상자 |
| 원근감 | 멀수록 작아짐 | 거리 무관, 크기 그대로 |
| NDC로 펴기 | 거리로 눌러 모음 → w 나눗셈 | 축마다 스케일·이동만 |
| w | w에 거리(z)가 들어감 | w=1 고정, 나눗셈 무효 |
| 쓰임 | 3D 시점, 사람 눈 | 2D·UI·CAD·아이소메트릭 |

- 피라미드 모양 — 한 점(눈)에서 사각형 화면 네 모서리로 뻗은 광선이 사각뿔을 이룸. 멀수록 넓어지는 이 모양이 곧 원근감
- 앞뒤가 잘린 이유 — near 평면은 w가 0에 가까운 카메라 바로 앞 영역을 잘라내고, far 평면은 깊이 범위의 끝을 정해 무한히 먼 곳까지 그리지 않게 함. 깊이 정밀도는 far/near 비율에 좌우되며 특히 near를 당길수록 나빠짐(깊이 버퍼 항목)
- w 나눗셈 — 이 피라미드를 정육면체로 펴는 수단. 원근에만 의미가 있고, 직교는 이미 상자라 w=1로 두어 나눗셈이 아무 일도 안 함

### 정점 셰이더 vs 프래그먼트 셰이더 ★

정점 셰이더는 정점 하나를 받아 정점 하나를 내보내는 함수, 프래그먼트 셰이더는 삼각형이 덮은 픽셀 하나마다 색을 정하는 함수. 둘 사이에서 고정 기능이 삼각형을 픽셀로 쪼개고(래스터화) 정점 출력값을 픽셀 위치에 맞게 섞어(보간) 넘김.

| | 입력 | 출력 | 실행 단위 |
| --- | --- | --- | --- |
| 정점 셰이더 | 정점 하나의 속성(위치·법선·UV) | 클립 좌표(필수) + 픽셀로 넘길 값 | 정점당 1번 |
| 프래그먼트 셰이더 | 세 정점 출력을 보간한 값 | 색(`discard`·깊이 쓰기도 가능) | 프래그먼트당 1번 |

- 프래그먼트 — 삼각형 하나가 픽셀 하나에 남기는 후보. 여러 삼각형이 같은 픽셀에 겹치면 프래그먼트도 여러 개라 셰이더가 그만큼 더 돎(오버드로우)
- 화면 좌표는 정점 셰이더가 만들지 않음 — 정점 셰이더 출력은 클립 좌표까지고, 화면 좌표는 뒤의 고정 기능이 만듦(앞 항목)

```hlsl
VSOut VS(VSIn v)                            // 정점마다 1번. 입력 1개 → 출력 1개
{
    VSOut o;
    o.pos    = mul(MVP, float4(v.pos, 1));  // 필수 출력: 클립 좌표
    o.normal = mul(NormalMatrix, v.normal); // 픽셀로 넘길 값 (모델 행렬의 역전치로 변환)
    o.uv     = v.uv;
    return o;
}

float4 PS(VSOut i) : SV_Target              // 프래그먼트마다 1번. i는 세 정점 출력의 보간값
{
    float3 n = normalize(i.normal);         // 단위 벡터도 선형 보간하면 길이가 1보다 짧아져 다시 정규화
    return tex.Sample(samp, i.uv) * max(0, dot(n, lightDir));
}
```

실행 횟수는 보통 프래그먼트 쪽이 압도적. 화면 전체를 덮는 사각형 하나면 정점 셰이더는 4번, 프래그먼트 셰이더는 1920 × 1080 = 2,073,600번. "픽셀 단계는 비싸다"가 최적화 상식이 된 이유이고, 포워드 vs 디퍼드·Z 프리패스가 다 비싼 프래그먼트 셰이더를 덜 돌리려는 기법.

- 비용의 비례 대상 — 정점 비용은 지오메트리 양에, 픽셀 비용은 해상도·오버드로우에 비례. 해상도를 낮췄을 때 빨라지면 픽셀 쪽 병목. 동적 해상도·업스케일링(DLSS·FSR)이 픽셀 비용을 직접 줄이는 수단

- 보간기 비용 — 정점에서 넘기는 값마다 보간기 슬롯을 쓰고 슬롯 수엔 한도가 있으며, 픽셀마다 보간하는 대역폭도 듦

정점 셰이더는 정점을 옮길 순 있어도 개수는 못 바꿈. 몇 번 실행될지는 셰이더가 아니라 CPU가 보낸 드로우콜이 정함 — 정점 버퍼 없이 `Draw(3)`만으로 정점 ID에서 화면 전체를 덮는 삼각형을 만들 수도 있음.

```hlsl
float4 FullscreenVS(uint id : SV_VertexID) : SV_Position
{
    float2 uv = float2((id << 1) & 2, id & 2);          // id 0,1,2 → (0,0) (2,0) (0,2)
    return float4(uv * float2(2, -2) + float2(-1, 1), 0, 1);
}   // 결과 (-1,1) (3,1) (-1,-3): 화면 영역을 통째로 덮음. 4번째 정점은 셰이더 안에서 못 만듦
```

입력 1개 → 출력 1개로 고정한 이유:

- 병렬성 — GPU가 정점마다 독립 스레드를 배정해 각자 자기 정점만 앎. "사이에 끼워 넣기"가 성립하지 않고, 개수를 바꾸려면 스레드 간 조율이 필요해 병렬성이 깨짐
- 재사용 — 출력이 입력 하나에만 의존하는 순수 함수라, 인덱스 버퍼로 여러 삼각형이 공유한 정점은 한 번 계산한 결과를 다시 씀(포스트 트랜스폼 캐시). 사각형이 6번이 아니라 4번 실행되는 이유
- 연결 유지 — 출력 개수가 입력 개수와 같아야 인덱스 버퍼의 삼각형 연결이 유지되고 뒷단계가 버퍼를 미리 잡아둘 수 있음

없애기는 흉내만 가능 — 삼각형 세 정점을 같은 위치로 보내면 넓이 0이라 픽셀이 하나도 안 생김(GPU 파티클에서 죽은 입자를 지우는 방법). 늘리기는 테셀레이션·지오메트리·메시 셰이더라는 가변 출력 전용 단계가 담당(다음 항목).

static float Edge(Vector2 a, Vector2 b, Vector2 p)
    => (b.x - a.x) * (p.y - a.y) - (b.y - a.y) * (p.x - a.x);

Vector2 A = new(1, 1), B = new(9, 2), C = new(4, 8);
float area2 = Edge(A, B, C);                 // 53  (삼각형 넓이 × 2)

Vector2 p = new(4.5f, 4.5f);                 // 픽셀 (4, 4)의 중심 = 그림의 P
float wA = Edge(B, C, p);                    // 14.5  ← A의 맞은편 변
float wB = Edge(C, A, p);                    // 14
float wC = Edge(A, B, p);                    // 24.5   (합 = 53)
bool inside = wA >= 0 && wB >= 0 && wC >= 0; // true → 프래그먼트 생성

float lA = wA / area2, lB = wB / area2, lC = wC / area2;   // 0.274, 0.264, 0.462 → 보간 가중치
// A=빨강, B=초록, C=파랑이면 P의 색 = (0.27, 0.26, 0.46)

GPU에서 싸게 도는 이유:

- 증분 평가 — 엣지 함수는 p에 대해 선형이라 x로 한 칸 가면 상수만큼 변함(위 예에서 Edge(B, C, p)는 −6씩). 픽셀마다 곱셈을 다시 하지 않고 덧셈으로 훑음
- 타일 단위 — 화면을 타일(예: 8×8)로 나눠 모서리 4개만 검사하고, 넷 다 한 변의 바깥이면 타일째 버림. 남은 타일은 픽셀을 병렬 판정해 2x2 쿼드로 픽셀 셰이더에 넘김(앞 항목)
- 중심 한 점 — 부호 3번이면 끝나고 "한 픽셀 한 번 셰이딩"이 유지됨. 픽셀 중심(+0.5)에서 재므로 이미지가 반 픽셀 밀리지 않음

경계에 걸린 픽셀은 규칙으로 정함.

- Top-Left 규칙 — 중심이 공유 변 위에 정확히 놓인 픽셀은 위쪽 가로 변이나 왼쪽 변을 가진 삼각형에만 줌(D3D 기준). "≥ 0"이면 두 삼각형이 다 칠해 반투명이 두 번 섞이고, "> 0"이면 아무도 안 칠해 틈이 생김
- 서브픽셀 스냅 — 정점 좌표를 고정소수점으로 스냅(D3D11은 8비트)해 두 삼각형이 공유 변의 엣지 함수를 비트 단위로 똑같이 계산. 경계에 틈이 안 생김(watertight)

한 점 판정의 대가:

- 계단(에일리어싱) — 절반 가까이 덮여도 중심이 밖이면 0, 조금 넘으면 1
- 얇은 삼각형(슬리버) — 폭이 1픽셀보다 좁으면 중심점 사이로 빠져 듬성듬성 찍히거나 사라짐
- 완화 — 픽셀당 판정점을 늘리는 MSAA(안티에일리어싱 항목)
- 넓이와 중심 — 면적 50% 초과면 중심은 반드시 안. 삼각형과 픽셀의 교집합은 볼록이라 중심이 밖이면 중심을 지나며 교집합을 한쪽에 모는 직선이 있고, 정사각형 중심을 지나는 직선은 어느 방향이든 넓이를 반으로 가르기 때문. 정확히 50%면 중심이 변 위일 수 있고 Top-Left 규칙이 정함. 역은 거짓 — 중심만 스치는 슬리버는 면적이 작아도 켜짐

무게중심 좌표는 화면에서 잰 넓이라, 원근 투영에선 화면 위 비율과 3D 표면 위 비율이 다름. 화면 비율 그대로 UV를 섞으면 기울어진 면의 텍스처가 휘고 출렁임(원근 보정을 하드웨어로 못 하던 초기 콘솔의 텍스처 왜곡).

- 왜 — 투영이 w로 나누는 연산이라 3D에서 선형인 값이 화면에선 선형이 아님. 먼 쪽이 화면에 압축돼 화면 중간점이 3D에선 가까운 쪽에 치우침
- 해법 — 값 ÷ w와 1 ÷ w는 화면에서 선형. 둘을 선형 보간한 뒤 픽셀마다 나눠 원래 값을 되찾음. 래스터화 단계의 고정 기능이 자동으로 해서 셰이더 코드엔 안 보임

```csharp
// 바닥 양 끝: N(w=1, uv=0), F(w=4, uv=1). w = 뷰 공간 깊이. 화면에서 중간점 t = 0.5
float wN = 1, wF = 4, uvN = 0, uvF = 1, t = 0.5f;

float affine   = Mathf.Lerp(uvN, uvF, t);            // 0.5    화면 비율 그대로 → 틀림

float uvOverW  = Mathf.Lerp(uvN / wN, uvF / wF, t);  // 0.125  (uv/w는 화면에서 선형)
float oneOverW = Mathf.Lerp(1 / wN, 1 / wF, t);      // 0.625  (1/w도 화면에서 선형)
float correct  = uvOverW / oneOverW;                 // 0.2    → 깊이 1 / 0.625 = 1.6과 일치
```

- 보정이 필요 없는 경우 — 삼각형 안에서 w가 일정하면 두 결과가 같음. 직교 투영, 화면과 평행한 면, 원근에서도 w가 일정한 방향(바닥을 가로지르는 같은 깊이의 줄)
- 깊이는 예외 — NDC z는 이미 z/w라 화면에서 선형이므로 그대로 보간. 깊이 정밀도가 가까운 쪽에 몰리는 것도 같은 이유(깊이 버퍼 항목)
- `noperspective` — 보정을 끄고 화면 선형으로 섞는 HLSL 보간 한정자. 화면 공간 효과에 씀

### 테셀레이션·지오메트리 셰이더

정점·프래그먼트 사이에 낀 선택 단계로, GPU에서 지오메트리를 생성·증식(정점 셰이더로는 못 하는 일). 테셀레이션은 패치를 잘게 쪼개 정점을 늘려 가까울수록 곡면·변위를 디테일하게(원경은 적게). 지오메트리 셰이더는 프리미티브 하나를 받아 정점을 더하거나 없애 새 프리미티브를 방출(외곽선·풀·파티클)하나, 실측 성능이 나빠 많은 파이프라인이 컴퓨트 셰이더로 대체.

**왜 테셀레이션은 빠르고 지오메트리 셰이더는 느린가** — 둘 다 증식이지만 방식이 다름. 가르는 건 "가변이냐"가 아니라 "예측 가능·고정 하드웨어냐, 임의·프로그래머블이냐".
- 테셀레이션: Hull 셰이더가 정한 팩터(숫자)만 알면 고정 기능 Tessellator가 규칙적 격자로 쪼개 → 출력 개수·토폴로지가 사전 확정(Domain 셰이더는 정점당 1:1)
- 지오메트리 셰이더: 셰이더 코드가 런타임에 임의 개수를 임의 토폴로지로 방출 → 미리 알 수 없고 직렬화 발생

**변위 매핑** — 하이트맵을 읽어 정점을 실제로 밀어올려 진짜 굴곡을 만듦(실루엣·자기 그림자가 진짜). 정점 단계에서만 가능.
- 테셀레이션과 함께면 Domain 셰이더(정점 대량 생성 직후 위치 확정), 없이 촘촘한 메시면 정점 셰이더(VTF)
- 프래그먼트 단계 기법은 정점을 안 늘리는 가짜 → 바깥 실루엣은 평평: 노멀 맵(법선만 속임), 패럴랙스/릴리프(UV를 시선 각도만큼 어긋내 깊이감 흉내, 릴리프/POM은 레이마칭으로 자기 가림까지)
- 싼 순서: 노멀 맵 < 패럴랙스 < 릴리프/POM < 변위

**메시 셰이더(최신)** — 정점·테셀레이션·지오메트리 앞단을 걷어내고 컴퓨트 스타일 2단계로 대체.
- 태스크(증폭) 셰이더가 얼마 만들고 뭘 버릴지 결정(클러스터 컬링·LOD), 메시 셰이더가 작은 클러스터(메시렛, 정점·삼각형 64~128개)를 직접 생성해 래스터화로 넘김
- 메시렛 단위라 정점 변환 전에 절두체·뒷면·오클루전 컬링을 싸게 함 + 컴퓨트 모델이라 지오메트리 셰이더의 유연함을 성능 손해 없이 얻음
- 언리얼 5 Nanite가 대표. 최신 하드웨어(Turing·RDNA2 이상) 필요

### 컴퓨트 셰이더

렌더 파이프라인 밖에서 GPU를 범용 병렬 계산에 쓰는 셰이더(GPGPU). 정점·픽셀 단계와 무관하게 수천 스레드로 데이터를 병렬 처리 — 파티클 시뮬레이션, 컬링, 포스트 프로세싱, 물리에. 결과를 버퍼·텍스처에 써 이후 렌더 단계에 넘김.

## 텍스처와 매핑

2D 텍스처를 3D 표면에 입히고 샘플링하는 법.

### UV 매핑

3D 메시 표면을 2D 텍스처에 펼치는 과정. 각 버텍스에 텍스처 좌표(u, v)를 대응시켜, GPU가 각 픽셀에 텍스처의 어느 텍셀을 쓸지 알게 함. 두 가지만 기억하면 됨.
- UV는 텍스처 해상도와 무관하게 **0~1로 정규화**. 정점에만 UV를 저장하고 삼각형 내부 픽셀은 무게중심 보간으로 채움
- **텍셀**(텍스처의 점)과 **픽셀**(화면의 점)은 다른 말 — 둘의 대응 비율이 어긋나는 데서 밉맵·필터링 문제가 나옴

**언랩** — 3D 껍데기를 가위로 잘라 평면에 펴는 작업(전개도). 잘린 경계가 심(seam)이고, 여기서 한 정점이 UV를 둘 가져 정점이 쪼개짐.

**텍셀 밀도** — 실제 3D 표면 단위면적당 배정된 텍셀 수. 핵심은 UV 언랩이 진짜 전개도와 달리 **면적 비율을 보존하지 않는다**는 것.
- 텍스처 크기(예: 2048²)와 UV 정사각형은 고정 → 텍셀은 한정된 예산
- 얼굴처럼 눈이 가는 부위는 UV 조각을 실제 비율보다 크게 배치해 텍셀을 몰아줌(선명), 발바닥은 줄임(뭉개짐)
- 텍스처가 커지는 게 아니라 고정 예산의 재배분(제로섬)
- 체커보드 텍스처를 씌워 칸 크기가 균일한지로 밀도 점검

### 텍스처 래핑·주소 모드

UV가 0에서 1 밖으로 나갔을 때 텍셀을 어떻게 정할지의 규칙. Repeat는 무늬를 타일처럼 반복(바닥·벽), Clamp는 가장자리 텍셀을 늘려 이음매·번짐을 막음(스카이·그라디언트), Mirror는 뒤집어 반복해 경계를 매끄럽게. 아틀라스·타일맵에서 Clamp와 Repeat를 잘못 고르면 옆 타일이 새어 드는 경계 누출이 생김.

**경계 누출·서브픽셀 시프트** — 아틀라스 타일 경계에서 옆 타일 색이 새어 번쩍이는 현상.
- 원인: 카메라가 float으로 움직이면 화면 픽셀이 샘플하는 텍셀 좌표가 소수 단위로 밀림(서브픽셀 시프트) → 바이리니어가 경계에서 이웃 텍셀(옆 타일)을 물어 섞고, 그 비율이 프레임마다 요동쳐 번쩍임
- 근본 이유: GPU 바이리니어는 고정 기능 회로라 "타일"이란 개념 없이 좌표 근처 4텍셀을 무조건 섞음. "다른 타일이면 안 섞기"는 경계 메타데이터 + 매 샘플 분기가 필요해 그 단순함(속도)을 잃음

**막는 법**
- 타일 둘레 패딩(거터), UV를 안쪽으로 0.5텍셀 오므리는 하프텍셀 인셋
- 포인트 샘플링(안 섞음), 밉맵 끄기
- 근본책: 카메라를 정수 픽셀에 스냅하는 픽셀 퍼펙트 카메라(소수 시프트 자체 제거)
- 텍스처 배열(Texture2DArray): 타일을 독립 레이어로 저장 → 샘플러가 경계를 못 넘어 누출 구조적 불가, 드로우콜 절약은 유지(단 모든 레이어 동일 해상도)

### 밉맵과 텍스처 필터링 ★

미리 만들어둔 축소 버전 텍스처. 멀리 있는 면은 한 픽셀이 여러 텍셀을 덮는데, 밉맵 없이 그중 몇 개만 샘플링하면 카메라가 조금만 움직여도 찍히는 텍셀이 들쭉날쭉해 지글거림·모아레가 생김(언더샘플링/에일리어싱). 밉맵은 미리 평균낸 축소본을 거리별로 골라 써 샘플링을 안정시키고, 작은 텍스처라 텍스처 캐시 효율도 좋아짐. 단점은 메모리 약 33% 증가.

필터링은 Bilinear가 주변 4텍셀 보간, Trilinear가 거기에 밉맵 레벨 간 보간을 더해 레벨 경계를 부드럽게 함.

### 텍스처 압축 (BC / ASTC / ETC)

GPU가 압축된 채로 직접 샘플링하는 블록 기반 포맷. JPEG처럼 풀어 쓰는 게 아니라 블록 단위로 실시간 디코드 → VRAM 사용량·대역폭을 크게 줄임. 데스크톱은 BC(DXT) 계열, 모바일은 ASTC·ETC를 씀(플랫폼마다 지원 포맷이 달라 빌드 타깃별로 선택). 손실 압축이라 노멀맵·UI 등은 아티팩트에 주의.

## 깊이와 가시성

픽셀마다 무엇을 남길지 정하는 버퍼들.

### 깊이 버퍼 — 불투명은 순서 무관 ★

픽셀마다 지금까지 본 것 중 가장 가까운 깊이를 저장, 그보다 멀면 무시(Z-test). 프래그먼트가 어떤 순서로 도착하든 픽셀별 최종 승자(가장 앞)는 동일 → 불투명은 그리는 순서 무관(min을 고르는 연산이라 순서 불변). 반투명은 섞어야 해서 순서 의존(별도 정렬).

**깊이값 저장 — 비선형** — 0~1 정규화, 포맷은 D24(흔함, 스텐실과 묶여 D24S8)·D32F·D16(모바일).
- 저장값은 거리에 선형이 아니라 **1/거리 쌍곡선** 형태(원근 나눗셈의 부산물) → 정밀도가 카메라 근처에 몰빵, 먼 곳은 몇 단계로 뭉갬 → Z-fighting의 원인
- 왜 선형(실제 거리)으로 저장 안 하나: 비선형 z는 파이프라인에서 공짜로 나오고 **화면 공간에서 선형이라 싸게 보간**됨. 실제 거리는 화면에서 비선형이라 픽셀마다 원근 보정 나눗셈이 필요해 비쌈(W-buffer, 그래서 밀려남)
- **Reversed-Z**: near=1·far=0으로 뒤집고 float 깊이 → 1/z의 근처 몰빵과 float의 0 근처 정밀도가 상쇄돼 전 구간 균일. 정밀도 단점만 거의 공짜로 제거

**깊이 테스트 위치** — 프래그먼트 셰이더가 아니라 그 뒤 고정 기능(출력 병합/ROP) 단계. 스텐실·블렌딩과 한 묶음.

**Early-Z** — 깊이 테스트를 프래그먼트 셰이더 **앞으로** 당겨 가려진 픽셀의 비싼 셰이딩을 스킵(Hi-Z는 타일 단위로 통째 기각). "셰이더 전 판정이 셰이더 후에도 옳을 때"만 유효.
- 셰이더가 깊이를 쓰면(`gl_FragDepth`) 테스트할 값이 미정 → Late-Z로 밀림(Conservative Depth로 일부 구제)
- 셰이더가 discard/알파 테스트하면 조기 기각은 되나 조기 **기록**은 막힘(구멍 뒤가 가려지는 걸 방지) → 컷아웃이 불투명보다 비싼 이유

**앞→뒤 정렬이 이득인 이유** — 결과는 순서 무관이지만 성능은 다름.
- 가까운 것부터 그리면 먼 것이 Early-Z로 셰이딩 전에 탈락 → 오버드로우↓. 뒤→앞이면 먼 것 셰이딩이 낭비
- 극단이 Z 프리패스. 대충 앞→뒤면 충분하고, 머티리얼 배칭 순서와는 절충

### Z-fighting

거의 같은 깊이의 두 면을 깊이 버퍼 정밀도가 구분 못 해 깜빡이는 현상. 깊이 정밀도는 카메라에서 멀수록 나빠짐. 해결은 간격 띄우기, near 평면을 너무 가깝게 안 두기(far/near 비율 줄이기), 깊이 오프셋.

### 스텐실 버퍼

픽셀마다 정수 태그를 저장하는 화면 크기 버퍼. 그리기 전 스텐실 값을 기준으로 통과·기각을 정해 "어디에 그릴지"를 마스킹함. 특정 영역에만 렌더(포털·거울·UI 마스크), 아웃라인(오브젝트를 스텐실에 찍고 살짝 키운 실루엣을 그 밖에만 그림), 데칼 제한 등에 쓰임. 깊이 테스트와 함께 프래그먼트 단위로 동작.

## 투명과 블렌딩

뒤가 비치는 것을 어떤 순서로 섞을지의 문제.

### 반투명 렌더링 순서 ★

불투명은 깊이 버퍼로 가려진 픽셀을 버려 순서가 자유롭지만, 반투명은 뒤 배경에 블렌딩되므로 순서가 곧 결과. 블렌딩은 교환법칙이 성립 안 해서 "이미 그려진 뒤 색 위에 앞 색을 alpha 비율로 덧칠"하는 계산이 뒤가 먼저 깔려 있어야 성립함. 그래서 불투명을 다 그린 뒤, 반투명끼리는 앞→뒤가 아니라 뒤에서 앞(back-to-front)으로 그림. 보통 깊이 쓰기(ZWrite)도 끔.

### 알파 블렌딩 vs 알파 테스트

| | 방식 | 특징 |
| --- | --- | --- |
| 알파 블렌딩 | 뒤 색과 alpha 비율로 섞음 | 반투명(유리·연기), 정렬 필요·ZWrite 끔 |
| 알파 테스트(컷아웃) | alpha 임계값 미만 픽셀을 버림 | 불투명 취급이라 순서 무관·그림자 정상, 경계가 딱딱 |

나뭇잎·울타리처럼 구멍 뚫린 불투명은 컷아웃이 적합 — 픽셀을 통째로 버려 깊이·정렬 문제를 피함. 부드러운 반투명은 블렌딩이 필요하지만 정렬·오버드로우 비용이 붙음.

### 오버드로우

같은 픽셀을 여러 번 덧칠하는 것. 불투명은 깊이 버퍼로 가려진 게 일찍 버려져 적음. 반투명은 뒤가 비쳐야 해 깊이 버퍼로 못 버리고 겹친 것을 다 그려 색을 섞음(블렌딩). 파티클·이펙트가 화면을 겹쳐 덮으면 한 픽셀이 수십 번 칠해져 프레임 급락. 파티클 수·크기·겹침을 줄여 대응.

## 라이팅과 재질

표면이 빛을 받아 색이 되는 모델과 반사.

### 노멀 맵(Normal Map)

폴리곤을 안 늘리고 라이팅을 속여 굴곡을 표현. 텍스처 픽셀에 색 대신 법선 방향을 저장(RGB → 법선 xyz, 그래서 푸르스름). 라이팅 시 평면의 진짜 법선 대신 노멀 맵 법선으로 `dot(N, L)` 계산 → 픽셀마다 밝기가 달라져 입체로 보임. 한계는 실루엣·자기 그림자가 그대로라는 것(비스듬히 보면 평평함이 들통). 더 정교한 건 패럴랙스·변위 매핑.

### 디퓨즈 라이팅과 내적 ★

밝기 = `max(0, dot(N, L))`. 단위 벡터 N·L이 사이각의 cos이므로, 정면(각 0°)이면 1로 최대, 스칠수록(90°) 0, 뒤(90° 초과)면 음수라 0으로 클램프. 비스듬히 닿으면 빛이 넓은 면적에 퍼져 단위 면적당 에너지가 cos만큼 줄어듦(람베르트).

### 스페큘러 라이팅

디퓨즈는 시점 무관이지만 스페큘러 하이라이트는 반사광이 눈 쪽으로 튈 때 보임 → 시선 방향 V에 의존.

| | 계산 |
| --- | --- |
| Phong | `dot(R, V)^광택도` (R = 반사 벡터) |
| Blinn-Phong | 반벡터 `H = normalize(L + V)`로 `dot(N, H)^광택도` |

V가 들어가니 카메라가 움직이면 하이라이트도 이동.

### PBR (물리 기반 렌더링) ★

빛 반사를 물리 법칙(에너지 보존, 프레넬)에 맞춰 계산해, 어떤 조명 아래서도 재질이 일관되게 보이게 함. 재질을 알베도 + 메탈릭 + 러프니스로 기술하는 메탈릭·러프니스 워크플로가 표준 — 러프니스가 하이라이트 퍼짐을, 메탈릭이 금속/비금속을 가름. 아티스트가 조명마다 값을 손보던 과거와 달리 재질과 조명이 분리됨.

### 큐브맵과 환경 반사

주변 환경을 정육면체 6면 텍스처에 담아, 표면의 반사 방향으로 샘플해 비치는 풍경을 표현. 스카이박스와 금속·유리 반사가 대표 예. PBR에선 이 큐브맵을 흐림 정도별로 미리 필터링해 러프니스에 맞는 반사를 얻는 이미지 기반 라이팅(IBL)으로 간접광을 근사. 유니티의 반사 프로브가 위치별 큐브맵을 구워 지역 반사를 제공.

### 스크린 스페이스 리플렉션(SSR)

이미 렌더된 화면(색·깊이 버퍼)에서 반사 방향으로 광선을 행진시켜 반사색을 얻음 — 큐브맵과 달리 동적 물체가 실시간으로 그대로 비침. 화면에 없는(가려지거나 시야 밖) 대상은 반사할 정보가 없어, 가장자리·오프스크린에서 반사가 끊기는 게 근본 한계. 그 빈틈은 큐브맵·반사 프로브로 폴백. 물웅덩이·젖은 바닥·유리에 흔히 씀.

## 그림자와 간접광

직접광 바깥에서 장면을 채우는 빛.

### 앰비언트 오클루전

좁은 틈·구석처럼 주변에 가려 간접광이 덜 닿는 곳을 어둡게 해 입체감을 더함. 물체 접점·주름이 자연스럽게 그늘져 형태가 또렷해짐. SSAO는 깊이 버퍼에서 각 픽셀 주변을 샘플해 얼마나 가려졌는지 실시간 추정 → 화면 공간이라 씬 복잡도와 무관하지만 경계 노이즈·헤일로가 단점.

### 섀도우 맵 ★

광원 시점에서 가장 가까운 표면 깊이를 섀도우 맵에 저장. 카메라 픽셀을 광원 공간으로 변환해 그 깊이와 비교, 저장값보다 멀면 앞에 가리는 게 있는 것 → 그림자.

### 글로벌 일루미네이션과 라이트맵 ★

직접광만 계산하면 그림자 속이 새까맣지만, 실제로는 빛이 벽·바닥에 튕겨 간접적으로 채움 — 이 반사광이 GI. 실시간 계산은 비싸서 정적 씬·정적 광원은 미리 계산해 라이트맵(텍스처)에 구워두고 런타임엔 샘플만 함(베이킹). 동적 물체엔 라이트 프로브로 구운 간접광을 보간해 입힘. 실시간 GI는 복셀·SDF·레이 트레이싱 기반 기법으로 근사.

## 색공간과 후처리

라이팅 결과를 화면에 맞게 다듬는 끝단.

### 감마와 선형 색공간 ★

모니터는 sRGB(감마) 곡선으로 출력하고 텍스처도 sRGB로 저장됨. 그런데 빛 계산(덧셈·곱셈)은 밝기가 선형이어야 맞으므로, 샘플한 sRGB 텍스처를 선형으로 풀어 계산하고 결과를 다시 sRGB로 인코딩해 출력함. 이 변환을 빼먹으면 라이팅이 뿌옇거나 과하게 어두워짐. 노멀맵·마스크처럼 색이 아닌 데이터 텍스처는 선형으로 둬야 함.

### HDR와 톤매핑

라이팅 결과는 1.0을 넘는 밝기가 자연스럽게 나옴(태양·발광). HDR 버퍼(부동소수점)에 그대로 담아 계산하고, 마지막에 톤매핑으로 0~1 범위(LDR)로 압축해 화면에 맞춤. 단순 클램프는 밝은 부분이 뭉개지므로 ACES 같은 곡선으로 하이라이트를 부드럽게 말아넣음. 블룸·노출도 이 HDR 단계에서 처리.

### 포스트 프로세싱

씬을 다 그린 뒤 최종 이미지(렌더 타겟)에 화면 공간 효과를 입히는 단계. 블룸(밝은 부분 번짐)·톤매핑·색보정·비네트·모션 블러·피사계 심도가 여기서 처리. 지오메트리와 무관하게 픽셀 단위로 동작해 씬 복잡도와 비용이 분리되나, 전체 화면을 여러 번 훑어 대역폭을 먹음. HDR 버퍼 위에서 순서대로 체인처럼 적용.

### 안티에일리어싱 (MSAA / FXAA / TAA)

폴리곤 경계의 계단 현상(에일리어싱)을 완화. 밉맵이 텍스처 안쪽 에일리어싱을 다룬다면 AA는 실루엣 경계를 다룸.

| 기법 | 방식 | 특징 |
| --- | --- | --- |
| MSAA | 경계 픽셀만 여러 서브샘플로 커버리지 계산 | 품질 좋음, 비쌈, 디퍼드와 상성 나쁨 |
| FXAA | 렌더 후 이미지에서 경계를 찾아 블러 | 싸고 빠름, 전체가 살짝 뭉개짐 |
| TAA | 프레임마다 살짝 흔들어 샘플하고 이전 프레임과 누적 | 저비용 고품질, 움직임에서 잔상·번짐 |

## 성능 최적화

안 보일 것을 안 그리고 드로우콜을 줄이는 기법.

### 드로우콜 ★

CPU가 GPU에 "이 메시를 이 머티리얼로 그려라"라고 보내는 요청. 콜당 준비 비용(셰이더·머티리얼 상태 설정, 명령 버퍼 작성, 드라이버 검증)이 CPU에 걸림 — 삼각형 수가 아니라 **콜 개수에 비례**. 콜이 많으면 GPU는 놀고 CPU가 허덕이는 CPU 바운드가 됨. 상태(특히 머티리얼=셰이더+텍스처)가 바뀔 때마다 콜이 갈림. 저수준 API(Vulkan·DX12)는 명령 버퍼를 미리·멀티스레드로 기록해 콜당 비용 자체를 낮춤.

**배칭 vs 인스턴싱** — 둘 다 콜 개수를 줄이는 법.
- 배칭: 여러 메시를 한 정점 버퍼로 합쳐 한 콜(유니티 스태틱/다이내믹 배칭)
- GPU 인스턴싱: 같은 메시를 위치만 바꿔 그릴 때, 메시·머티리얼은 한 번만 보내고 인스턴스별 데이터(위치·색)만 배열로 넘겨 한 콜로 수천 개(나무·풀·군중)

**텍스처 아틀라스** — 여러 텍스처를 한 장에 모은 것. 텍스처를 통일하면 상태 변경이 사라져 여러 오브젝트가 한 콜로 묶임(배칭 전제). 각 오브젝트 UV는 자기 칸만 가리키게 리맵.
- 한계: 하드웨어 Repeat(타일링) 못 씀(1 넘으면 옆 칸으로), 경계 누출·밉맵 번짐(패딩 필요), 텍스처 크기 한계, 패킹 낭비
- 대안: 텍스처 배열(누출 없음·레이어별 Repeat 가능·동일 해상도), 바인드리스(합칠 필요 없이 인덱스로 샘플)
- 흔한 예: 스프라이트 아틀라스, 라이트맵 아틀라스

**UI·텍스트 배칭** — 글자 하나 = 폰트 아틀라스에서 뽑은 텍스처 쿼드. 같은 아틀라스를 쓰면 데미지 숫자 수백 개도 몇 콜로 배칭됨.
- SDF 방식이면 크기 변해도 또렷하고 여전히 배칭. 글자 색은 정점 색으로 넣어 머티리얼을 안 바꿔 배치 유지
- 유니티 uGUI는 배칭을 자동으로 하지만 "저절로 최적화"는 아님 — 스프라이트 아틀라스 설정·그리기 순서 정리는 수동
- UI의 진짜 병목은 드로우콜보다 **캔버스 리빌드**: 요소 하나만 바뀌어도 캔버스 전체 배치를 재생성 → 자주 갱신되는 요소는 별도 캔버스로 분리. Raycast Target 끄기·마스크 최소화도 챙길 것

### 프러스텀 컬링

카메라 시야(절두체) 밖 오브젝트는 렌더링에서 제외. 드로우콜 전에 걸러내 CPU(드로우콜 준비)·GPU(정점·프래그먼트) 양쪽 비용 절감.

### 백페이스 컬링

카메라를 등진 삼각형(뒷면)을 그리지 않아 처리할 삼각형·프래그먼트 수를 줄임(드로우콜이 아니라 처리량을 줄이는 것). 판별은 보통 화면 투영된 정점의 감김 순서(winding order)로 하며, 법선·시선 내적 부호와 같은 결과.

### Z 프리패스(뎁스 프리패스)

색을 칠하기 전에 깊이만 먼저 한 번 렌더해 깊이 버퍼를 채우는 사전 패스. 본 컬러 패스에서는 이미 가려진 프래그먼트가 Z-test로 일찍 탈락해, 비싼 픽셀 셰이더를 가장 앞 표면에만 실행 → 불투명 오버드로우 낭비를 제거. 대가는 지오메트리를 두 번 그리는 정점 비용이라, 픽셀 셰이더가 무거운 씬에서 이득이 큼. 반투명은 이 방식으로 못 걸러냄.

### LOD(Level of Detail)

멀면 화면에서 작아져 디테일이 안 보이니 단순 메시로 교체. 단순 메시는 정점·삼각형 수가 적어 GPU 정점 처리량·메모리 대역폭 절감. 작게 보이는 물체에 풀디테일은 픽셀당 수많은 삼각형을 헛계산하는 낭비.

### 빌보드와 임포스터

빌보드는 항상 카메라를 향하는 사각형에 텍스처를 붙여, 멀리 있는 나무·풀·연기를 폴리곤 없이 표현. 임포스터는 3D 모델을 여러 각도에서 미리 렌더해둔 텍스처로, 원경에서 실제 메시 대신 각도에 맞는 그림을 보여줌. LOD의 극단으로, 실루엣이 중요치 않을 만큼 작아진 물체의 정점 비용을 거의 0으로 낮춤. 가까워지면 실제 메시로 교체.

## 렌더링 구조

파이프라인을 어떻게 짤지의 큰 선택.

### 렌더 타겟과 MRT

화면 대신 텍스처(렌더 타겟)에 그려 그 결과를 다음 단계 입력으로 씀 — 그림자 맵·반사·포스트 프로세싱·미니맵이 이 오프스크린 렌더링. MRT(다중 렌더 타겟)는 픽셀 셰이더 한 번에 색·법선·깊이를 여러 타겟에 동시에 출력 — 디퍼드의 G-buffer가 대표. 대역폭이 비싸 타겟 수·포맷·해상도를 아끼는 게 관건.

### 포워드 vs 디퍼드 렌더링 ★

라이트를 언제 계산하느냐가 갈림.

| | 방식 | 강점 | 약점 |
| --- | --- | --- | --- |
| 포워드 | 물체를 그리며 그 자리에서 라이팅 | 투명·MSAA 자연스럽고 저사양·모바일에 유리 | 라이트 수가 늘면 물체×라이트로 비용 급증 |
| 디퍼드 | 색·법선·깊이를 G-buffer에 먼저 쓰고, 화면 픽셀 단위로 한 번에 라이팅 | 라이트 많아도 화면 픽셀 수에 비례 | G-buffer 대역폭 큼, 투명·MSAA 처리가 까다로움 |

라이트가 적으면 포워드, 동적 라이트가 많으면 디퍼드가 유리. 그 절충으로 Forward+, 타일·클러스터드 방식도 있음.

### 래스터화 vs 레이 트레이싱 ★

래스터화는 삼각형을 화면에 투영해 픽셀을 칠하는 방식 — 빠르고 GPU 파이프라인의 기본이나, 반사·그림자·간접광은 별도 기법으로 흉내내야 함. 레이 트레이싱은 픽셀마다 광선을 쏴 부딪힌 표면을 추적 → 반사·굴절·그림자가 물리적으로 정확하지만 광선당 교차 판정이 비쌈. 실무는 래스터화를 기본으로 두고 반사·그림자 등 일부만 레이 트레이싱으로 보강하는 하이브리드가 흐름.

### 셰이더 변형과 키워드

셰이더가 키워드(기능 on/off)마다 별도 코드로 컴파일된 것이 변형(variant). 조건 조합이 늘면 변형 수가 곱으로 폭발해 빌드 시간·용량·메모리를 잡아먹음. 안 쓰는 키워드를 정리하고 `shader_feature`(안 쓰면 빌드 제외)와 `multi_compile`(런타임 전환용 전부 포함)을 구분해 씀. 첫 사용 때 컴파일되면 렉이 생겨 미리 워밍업하기도 함.

### 더블 버퍼링과 VSync

화면에 그리는 도중 그 버퍼를 바로 표시하면 위아래가 어긋나 보이는 티어링이 생김. 앞 버퍼(표시)와 뒤 버퍼(그리기)를 나눠, 다 그린 뒤 통째로 교체(swap)하면 완결된 프레임만 보임. VSync는 이 교체를 모니터 주사율에 맞춰 티어링을 없애지만, 주사율을 못 맞추면 프레임이 배수로 뚝 떨어짐(60 → 30).
