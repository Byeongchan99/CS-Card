분야 핵심 개념을 얕고 넓게 정리한 노트. 쓱 훑어보며 복습한다.

## 스택 — 괄호 짝 검사

여는 괄호는 push, 닫는 괄호에서 pop해 짝을 비교. 괄호는 가장 최근에 연 것이 가장 먼저 닫히는 LIFO 중첩 구조라 스택이 자연스러움. 닫는데 스택이 비었거나, 끝났는데 안 비었으면 짝이 안 맞음.

## 덱(Deque)

양 끝에서 O(1) 삽입/삭제. "최근 N개 입력"처럼 앞에서 오래된 것을 버리고 뒤에서 최근 것을 꺼내야 하는 경우에 적합. 스택은 한쪽만, 큐는 한 방향(뒤 삽입/앞 삭제)만 되어 부족.

## 원형 버퍼(Circular Buffer)

고정 크기 배열에서 데이터를 안 옮기고 head/tail 인덱스만 회전(`% size`). 삽입 O(1), 가장 오래된 것 자동 덮어쓰기. 큐(동적)와 비교해 할당·GC가 없고 캐시 친화적이며 "최근 N개 유지"가 자연스러움. 대가는 크기 고정. 격투 게임 입력 버퍼에 최적.

## List vs LinkedList

인덱스 접근은 List가 O(1), LinkedList가 O(n). 더 중요한 이유는 캐시 지역성 — List는 연속된 메모리라 순회 시 캐시 친화적이고, LinkedList는 노드가 흩어져 있어 캐시 미스가 잦음. 그래서 단순 순회조차 실제로는 List가 빠름.

## 배열 vs 연결 리스트 — 중간 삽입

| | 중간 삽입 | 이유 |
| --- | --- | --- |
| 배열 | O(n) | 뒤 원소를 다 한 칸씩 밀어야 함 |
| 연결 리스트 | O(1) | 포인터만 교체 |

단 리스트의 O(1)은 삽입 위치를 이미 알 때고, 위치를 찾아가는 탐색은 O(n)이라 "탐색 후 삽입"이면 전체 O(n).

## List.Add의 분할 상환 O(1)

내부 배열이 가득 차면 두 배로 늘려 재할당(O(n) 복사). 두 배씩 늘리므로 복사가 기하급수적으로 드물어져, n번 추가의 전체 복사 비용 합이 약 2n = O(n). 추가당 평균 O(1). +1씩 늘리면 전체 O(n²)이 됨.

## 포함 여부 확인 — List vs Dictionary vs HashSet

| | 탐색 | 이유 |
| --- | --- | --- |
| List | O(n) | 앞에서부터 훑음 |
| Dictionary (`ContainsKey`) | 평균 O(1) | 키 해시로 바로 버킷을 찾음 |
| HashSet | 평균 O(1) | 같은 해시 방식 |

잦은 포함 여부 확인엔 HashSet. 대신 HashSet은 순서·인덱스 접근·중복 저장을 포기함. Dictionary의 O(1)은 키 검색이고, 값 검색(`ContainsValue`)은 딕셔너리도 O(n)(값은 색인 안 됨).

## Dictionary 키 — GetHashCode와 Equals

`GetHashCode`로 버킷을 찾고 `Equals`로 항목을 비교. 커스텀 클래스는 기본이 참조 기준이라 값이 같아도 다른 객체면 다른 키로 인식. 두 메서드를 일관되게 오버라이드하고(같은 객체 → 같은 해시), 키는 가급적 불변이어야 함.

## 해시 충돌과 최악 O(n)

서로 다른 키가 같은 버킷으로 몰리는 상황. 한 버킷이 길어지면 선형 탐색이 되어 O(n)으로 떨어짐. Load Factor(채워진 비율)를 관리해 임계치를 넘으면 크기를 키우고 재해싱하며, 좋은 분산을 주는 `GetHashCode`도 그만큼 중요.

| | 방식 | 장점 | 대가 |
| --- | --- | --- | --- |
| 분리 연결 | 같은 버킷에 연결 리스트로 이어붙임 | 구현 쉽고 테이블 크기 이상 수용 | 추가 메모리, 캐시 비효율 |
| 개방 주소법 | 빈 칸을 찾아 저장 | 캐시·메모리 효율 | 적재율 높으면 탐사 비용 증가, 삭제 시 tombstone 필요 |

C# `Dictionary`는 분리 연결.

## 블룸 필터

여러 해시 함수로 비트 배열에 표시해 원소의 존재 여부를 적은 메모리로 판단하는 확률적 구조. 없는데 있다고 하는 거짓 양성(false positive)은 생겨도, 있는데 없다고 하는 거짓 음성은 없음 → "확실히 없음"만은 보장. 원소 저장·삭제·열거는 못 하고 멤버십 질의만. 캐시·DB 앞단에서 "디스크를 뒤질 가치가 있는지" 걸러내는 데 쓰임.

## 최소 힙과 우선순위 큐

완전 이진 트리라 높이가 log n. 삽입은 끝에 넣고 부모와 비교하며 위로(sift up), 추출은 루트를 꺼내고 마지막 원소를 루트로 올린 뒤 더 작은 자식과 비교하며 아래로(sift down). 둘 다 한 경로(최대 높이)만 정리하므로 O(log n).

루트를 지우고 앞으로 당기는 시프트가 아님 — 그건 O(n) 배열 삭제. 시간을 키로 넣으면 예약 이벤트 처리에 맞고, 일반 큐(FIFO)는 시간 순 정렬 자체가 안 되며 정렬된 리스트는 삽입마다 O(n). 게임에서는 A* 오픈 리스트, 이벤트 스케줄링에 쓰임.

## BST 균형 붕괴

정렬된 순서로 삽입하면 한쪽으로만 자라 연결 리스트처럼 되어 O(n). AVL·Red-Black 트리는 회전으로 높이를 O(log n)으로 유지.

## AVL 회전

모든 노드의 좌우 서브트리 높이 차를 1 이하로 강제 → 트리가 한쪽으로 치우치지 못해 높이가 O(log n)으로 묶이고 연산도 O(log n). 회전 자체는 O(1).

## AVL vs Red-Black

| | 균형 | 탐색 | 삽입/삭제 |
| --- | --- | --- | --- |
| AVL | 엄격(높이 차 ≤ 1) | 트리가 더 낮아 빠름 | 회전이 잦아 느림 |
| Red-Black | 느슨 | 살짝 느림 | 회전이 적어 빠름 |

둘 다 O(log n) 보장. C# `SortedDictionary`/`SortedSet`이 Red-Black.

## B-트리와 B+트리

한 노드에 여러 키를 담아 자식을 많이 두는 다진 균형 트리 — 높이가 매우 낮아 노드 접근(디스크 읽기) 횟수를 줄임. 이진 트리 대신 디스크·DB 인덱스에 쓰이는 이유가 이 낮은 높이. B+트리는 실제 데이터를 잎에만 두고 잎들을 연결 리스트로 이어, 범위 검색(BETWEEN)과 순차 스캔이 빠름. 관계형 DB 인덱스의 표준.

## 트리 순회 용도

전위(루트 → 좌 → 우)는 트리 복사·직렬화 — 부모를 먼저 만들어야 위에서부터 재구성 가능. 중위(좌 → 루트 → 우)는 BST 오름차순 출력. 후위(좌 → 우 → 루트)는 트리 삭제·하위 결과 집계 — 자식부터 처리해야 안전.

## 트라이(Trie)

루트에서 문자를 하나씩 자식으로 내려가는 트리. 검색 시간이 저장된 단어 수와 무관하게 찾는 단어의 길이 L에 비례(O(L)). 해시 테이블은 완전 일치만 O(1)이고 접두사로 시작하는 것들을 찾으려면 전체를 훑어야 함. 접두사 노드까지 간 뒤 아래 서브트리를 순회하면 같은 접두사 단어가 다 나옴. 게임에서는 채팅 자동완성, 욕설 필터.

## 세그먼트 트리와 펜윅 트리

배열의 구간 질의(합·최솟값 등)와 값 갱신을 둘 다 O(log n)에 처리. 누적 합 배열은 질의가 O(1)이나 값 하나 바뀌면 뒤를 다 고쳐 갱신이 O(n)인데, 이 구조들은 트리로 부분 결과를 묶어 질의·갱신을 모두 로그로. 세그먼트 트리가 더 일반적(임의 결합 연산), 펜윅 트리(BIT)는 구간 합에 특화돼 더 간결·빠름.

## 인접 행렬 vs 인접 리스트

| | 메모리 | 간선 조회 | 유리한 곳 |
| --- | --- | --- | --- |
| 인접 행렬 | O(V²) | O(1) | 밀집 그래프 |
| 인접 리스트 | O(V+E) | 그 노드의 연결 수만큼 | 희소 그래프 |

격자 맵은 희소하므로 인접 리스트.

## 유니온-파인드(서로소 집합)

두 원소가 같은 집합인지(연결되어 있는지) 판단하고 집합을 합치는 자료구조 — "소속 판단"이 아니라 "연결성 판단"이 핵심. 경로 압축은 Find 때 거친 노드를 루트에 직접 붙여 트리를 평탄화. 압축 + 랭크 합치기를 하면 분할 상환으로 거의 상수 O(α(n))에 가까워짐(상수 O(1)은 아님). 게임에서는 연결 영역 판정, 미로 생성.

## LRU 캐시 — 이중 연결 리스트 + 해시맵

"가장 오래 안 쓴 것" 폐기는 큐만으로 안 됨(큐는 사용을 반영 못 함). 이중 연결 리스트로 사용 순서 유지(최근 쓴 것 맨 앞으로, O(1) 이동), 해시맵으로 키 → 노드 위치를 O(1) 조회. 둘을 조합하면 조회·갱신·삭제 모두 O(1).

## 공간 분할(쿼드트리/그리드) — 근접 검색

모든 쌍 검사는 O(n²)(대부분 멀어서 무의미한데도 다 비교). 월드를 칸으로 나눠 오브젝트를 칸에 등록하고, 같은 칸·인접 칸끼리만 비교하면 검사 대상이 확 줄어 평균 O(n)에 가까움. 물리 엔진 broad phase가 이 방식.
